# llm-wiki-shared-fact-criterion 작업 기록

- `context` 위키는 다양한 레포 담당자가 실행하는 컨텍스트 공유 저장소이며, '다른 레포가 알아야 하는' 기준이면 향후 추가되는 레포도 알아야 하고 구성 초기라 활성 레포가 하나뿐이어도 중요한 문서가 쌓여야 함 — llm-wiki 규약 1장 판정은 레포 밖(이후 추가될 레포 포함)이 알아야 하면 코드에 있어도 담고, 레포 안에서만 필요하면 코드로 알 수 있을 때 제외함
  - source: 사용자 확인 2026-09-26
- `context` 복잡한 판정 구조보다 간결한 판정 구조를 선호함 — llm-wiki 담는 판정은 위치별 분기나 도구별 예외 없이 1장 한 문장이 정하고, update 5장·audit 2장의 `git grep`은 레포 안 사실의 코드 확인 수단으로만 씀
  - source: 사용자 확인 2026-09-26
- `correction` llm-wiki 규약 1장 판정 "레포(코드·설정·테스트)를 읽은 에이전트가 같은 결론에 이르면 담지 않음"은 update 5장 검토가 근거 레포 코드만 `git grep`하므로, 도메인 루트에 둘 사실(다른 레포가 쓰는 요율·정책)도 출처 레포 코드에 있으면 삭제함 — 2026-09-26 pigeon-trade update에서 토스증권 수수료율 3건과 지갑 체결가 규칙이 이렇게 삭제됨
  - evidence: llm-wiki/references/doc-contract.md, llm-wiki/skills/update/SKILL.md
- `constraint` llm-wiki 1장 판정에 "레포 밖이 알 필요가 없고 … 같은 결론에 이르면 담지 않음"처럼 두 조건을 한 문장에 묶으면 sonnet 서브에이전트가 앞 조건을 건너뛰고 코드 대조만 적용함 — "레포 밖이면 코드에 있어도 담고, 레포 안이면 코드로 판정" 순서의 두 절로 적어야 함(골든 블라인드 판정 초기 도메인 11건에서 4/11에서 9/11로 개선)
- `constraint` llm-wiki 1장 "외부 명세 전사(소재와 함정만)"을 그대로 두면 sonnet이 도메인이 쓰는 외부 요율(수수료율)까지 명세 전사로 보고 제외하며, 새 판정만 넣고 "담지 않는 것"에 계약 모양(경로·필드·이벤트 이름)을 명시하지 않으면 호출 경로·응답 필드·이벤트 이름까지 문서로 담음
- `why` llm-wiki 담는 판정의 독자를 "현재 도메인에 등록된 레포"로 한정하는 안은 기각함 — 레포가 하나뿐인 초기 도메인에서는 출처 레포 코드에 있는 사실이 모두 제외되어 정책이 문서화되지 않고(현행 기준 골든 1/11), 새 소비처가 생길 때 필요한 권한 정책 같은 사실이 누락됨
- `context` 남은 모호 사례(CI에 흔적 없는 배포 순서의 확정 여부, 정책 사실에서 레포 내부 세부 분리, convention 유형 표의 "코드 구성 방식"과 1장 코드 판정 충돌)와 2026-09-26 update에서 삭제된 위키 불릿 4건 복원은 이번 llm-wiki 5.3.0 범위 밖이며, 골든 테이블은 플러그인에 보관하지 않음
  - source: 사용자 확인 2026-09-26
