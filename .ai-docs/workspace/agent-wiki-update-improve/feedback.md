# agent-wiki-update-improve 작업 기록

- `context` agent-wiki update 개선은 루트 `agent-wiki-update-feedback.md`의 9개 축을 담당 에이전트가 비판 검토해 수용 여부를 정하며, 사용자 문장은 "단 담당자로써 비판검토 후 수용여부 결정할것 추구하는 방향성은 간결한 구조와 프롬프트, SSOT, 안정적인 프로세스 진행, 토큰 절약"임 — 축별 판정은 그 문서의 `결정 상태`에 있고 구현 전 사용자 검토 대상임
  - source: 사용자 확인 2026-09-30
- `why` agent-wiki update는 초기 구축 전용 모드를 두지 않기로 함 — 머지 재생의 낡은 사실 잔존은 검토 check를 레포별 이번 실행의 마지막 처리 머지로 두는 것으로 해소하고, head 코드 전체 읽기는 register·감사 규모의 새 경로라 구조만 늘며, 작업 기록 기반 초기 구축은 `HEAD` 시작점과 `/agent-wiki:add`로 이미 가능함
- `why` agent-wiki update 검토는 diff 근거 사실(`input` 없음)이 check 시점 코드와 다르면 변경 의도 인용 없이 코드 값으로 고치기로 함 — update 4절의 "같은 실행 안의 값 변화는 뒤 머지 diff가 변경 근거" 원칙과 같은 기준이며, 사실별 근거 머지 시점 확인은 personal-stock-trading 실행에서 뒤 머지가 거짓으로 만든 사실(f9ee70a, 24ad786이 바꿈)을 통과시켰음
- `why` agent-wiki apply.md 재배정 루프와 update 원복 커서 규칙은 삭제하기로 함 — 재배정 사실 10건 중 5건이 재검토에서 다시 위치로 삭제되어 수렴하지 않았고, 원복 커서는 다음 실행이 같은 판정을 반복해 커서만 멈추며, 위치 삭제 불릿은 PR `위치 재배정` 행으로 add가 사용자 질문과 함께 처리함
- `why` agent-wiki 위키 PR 본문은 `추가`·`동일` 판정 행과 문서별 절을 싣지 않기로 함 — PR diff·문서별 커밋과 중복이고 personal-stock-trading 실행에서 본문이 GitHub 한도 65,536자를 넘은 주원인이었으며, 대가는 추출 사실과 문서 불릿의 대응을 본문에서 바로 볼 수 없다는 점임
- `why` agent-wiki 규약 4장 원본 줄에 "원본은 값을 정의하는 레포의 식별자" 조항을 두지 않기로 함 — 소비 레포 추출 에이전트는 diff 밖 정의 레포를 볼 수 없어 조항을 적용할 수 없고, 미러 타입 병합은 update 4절 같은 주장 병합이 맡음
- `why` agent-wiki 검토의 발견(구조 변경 제안·새 사실 후보)은 검토 출력 `notes`에서 PR `후속 확인` 절로 사람에게만 전달하고 add 자동 입력으로 넣지 않기로 함 — 추정이 섞인 발견이며, `검토 기각` 행도 같은 이유로 add 입력 목록에 넣지 않음
- `context` agent-wiki update 실행 규모 검토의 사용자 문장은 "업데이트할 커서가 많이 밀려있으니 되게 많은것을 한번에 처리하는 경우가 있었음 제한을 두면 좋을 듯 한데 한번에 처리하기 좋은 용량정도.. 간단한 구조 간결한 프롬프트 선호"와 "업데이트 할 때 바로 이어서 pr 머지된 항목에 같은 주제로 진행된 항목이 있으면 함께 처리하는것도 좋을거같긴해"이며, 둘 다 반영 의무가 없는 제안으로 담당 에이전트가 분석 근거로 수용 여부를 정함
  - source: 사용자 확인 2026-09-30
- `why` agent-wiki update 실행 예산은 단위를 머지 건수로 유지하고 `--max-merges` 기본값을 40에서 10으로 낮추는 안을 권장함 — personal-stock-trading 실행(위키 PR #3)의 머지 27건이 사실 313건·신규 문서 42장·에이전트 105회·PR 본문과 코멘트 약 15만 자를 만들어 머지당 약 5,600자로 10건이면 GitHub 한도 65,536자 안에 들며, diff 바이트 예산은 사실 수와의 상관이 스캐폴딩 머지를 빼면 0.81이나 포함하면 0.45라 건수보다 낫다고 보기 어려움, 대가는 밀린 머지 27건이 실행·PR 머지 3회로 나뉘고 같은 이력의 대체 34쌍 중 25쌍이 실행 경계를 넘어 4절 대체 대신 규약 7장 다른 값(변경 의도 근거 필요) 판정을 거친다는 점임
- `why` agent-wiki update에서 예산 경계 뒤 같은 주제 머지를 이어 붙이는 확장은 기각을 권장함 — personal-stock-trading의 대체 34쌍은 전역 시각 순 거리 3~12로 바로 다음 머지인 쌍이 없어 확장이 한 쌍도 잡지 못하고, 캔들 집계 주제(70f1e21·758b01e·f8fc090·935bc6c·6b9cca8)는 작업 기록 폴더명·이슈 번호가 모두 달라 기계 판정이 안 되며, 인접하지 않은 머지를 당기면 레포별 커서가 처리 머지의 앞부분이라는 전제가 깨짐
- `context` agent-wiki update 추출 단위 변경은 모범 답안 대조 테스트로 누락을 확인하며, 사용자 문장은 "권장안으로 일단 가보되 사실 추출 테스트 진행, 모범 답안 준비하고 서브에이전트로 돌려봐 누락 되는지.. 그리고 더 간단한 구조가 있을지 등도 열어놓고 검토 그래서 현 방식말고 에이전트 지침으로 테스트한번 해보는것도 좋을거같음"임
  - source: 사용자 확인 2026-09-30
- `correction` agent-wiki `collect_update_merges.py`의 제외 규칙 `:(exclude)**/package-lock.json` 형식은 glob 매직이 없어 루트 경로의 잠금 파일을 빼지 못함 — pigeon-trade 머지 7건과 pigeon-trade-dashboard 0365460·2896487이 루트 `package-lock.json` diff를 추출 입력에 담았고, `:(exclude,glob)`로 바꾸면 PR #3 머지 27건의 diff 합계가 2,472KB에서 1,952KB로 줄어듦
  - evidence: agent-wiki/scripts/collect_update_merges.py
- `constraint` Claude Code Read 도구는 1회 25,000토큰, 범위 없는 호출은 256KB 파일까지만 반환해 agent-wiki update 추출 에이전트는 큰 diff 파일을 offset·limit으로 나눠 읽어야 하며, 추출 미열람은 파일 하나의 크기보다 에이전트 1회 누적 입력량에서 생김 — PR #3에서 2,000줄 넘는 파일이 없던 25.1만 바이트 묶음도 끝까지 읽히지 않았고 9.1만 바이트 묶음은 끝까지 읽힘
- `why` agent-wiki update 추출 에이전트 1회 입력은 머지 1건(150KB 초과 머지는 파일 경계 조각)으로 두고 "묶음 1개·머지 3건 이하 메인 직접 추출" 예외는 삭제함 — 레포·sha만 넘기고 에이전트가 git으로 파일별로 읽는 안은 누적 입력량이 같아 미열람을 풀지 못하고 제외 규칙·머지 범위·딸린 커밋 메시지 수집이 프롬프트로 옮겨지지만, 더 간단한 구조 후보로 모범 답안 대조 테스트에서 함께 비교하며, 메인 직접 추출은 메인 컨텍스트에 diff를 싣는 경로이고 두 차례 검증에서 한 번도 실행되지 않았음
