# 워크플로 플러그인 3종 재작성

plan-workflow, pr-workflow, agent-wiki를 고칩니다. 이 문서의 `합의` 항목은 모두 사용자가 2026-11-11에 확인한 것이고, 각 항목의 버린 대안과 측정 근거는 같은 폴더의 `feedback.md`에 있습니다.

## 의도

- **왜**: 플러그인의 목적은 사용자의 암묵지를 저장·문서화하고 다시 활용하는 것인데, 합의되지 않은 내용으로 계획이 채워져 재계획이 반복되고, 질문 형태 때문에 선택이 뒤집히며, 여러 이슈와 레포를 한 번에 다루지 못하고, 근거 없는 절차와 프롬프트가 쌓여 있음
- **누가**: 세 플러그인으로 이슈를 계획·구현·리뷰하고 위키를 갱신하는 개발자(사내판 사용자 포함)
- **완료**: 아래 합의가 세 플러그인에 반영되어 각 검증을 통과한 PR 세 개가 머지되고, 사내판에 한 번에 반영됨
- **전제**: 세부 구조는 유지 대상이 아니며 완전 재작성과 삭제를 허용함. 바꾸지 않는 것은 `연결`의 외부 약속뿐임

## 합의

### plan-workflow

**PW-1 전체 흐름**

- **바꾸는 것**: planning과 execute가 이슈 목록을 받아 분류, 근거 확인, 합의, 계획 승인, 실행 순서로 진행함
- **모양**: 분류는 이슈별 대상 레포·관계·순서 표, 근거 확인은 이슈 본문·위키·앞 기록의 주장을 코드와 대조, 합의는 이슈 하나씩 한 결정씩(업무 전제, 구조, 세부 순), 계획은 이슈별 승인이며 계획에 처음 나오는 내용이 없고, 실행과 PR은 이슈와 레포의 조합마다 진행함. 이슈 하나는 길이 1인 목록으로 같은 절차를 따름
- **이유**: 조율 전용 스킬을 따로 두면 단일 이슈용과 묶음용 규칙이 두 벌이 되어 어긋남
- **적용 범위**: planning·execute 스킬 본문과 README

**PW-2 합의 단위와 질문·설명 작성 기준**

- **바꾸는 것**: 합의 단위를 동작·구조 한 덩어리로 정하고, planning과 execute가 함께 따르는 질문·설명 작성 기준을 문서 하나로 둠. 답변 처리 표, 합의 5상태 목록, 4분류 표, 6축 누락 점검을 이 문서로 대체함
- **모양**:
  - **묻기 전**: 요청·이슈에 있는 조건과 코드로 확인되는 사실은 묻지 않고 확인해 `확인한 사실`에 적고, 보안·데이터 손실에서 한쪽이 열등한 안은 선택지에 올리지 않고 정한 뒤 알림
  - **순서**: 업무 전제, 구조, 세부 순으로 묻고 "필요한가"를 "어디에 둘까"보다 먼저 확인하며, 한 이슈의 합의를 끝낸 뒤 다음 이슈로 넘어가고 한 이슈의 답은 그 이슈에만 적용함
  - **질문 하나**: 한 번에 한 결정, 선택지 하나에 결정 하나, 업무 사실은 업무 낱말로 묻고 코드 범위는 에이전트가 도출해 설명하며, 처음 나오는 개념은 질문 전에 설명하고, 기존 결정·지시가 기본값이며 뒤집는 안에는 권장 표시를 붙이지 않음
  - **검토한 세부**: 선택지를 나열하지 않고 검토한 안 하나를 버린 대안과 함께 제시해 확인받으며, 지금 동작, 무엇을 어디에 어떻게 바꾸는지와 코드 모양, 이 방식인 이유, 바뀐 뒤 달라지는 것을 설명하고, 구조를 제안하기 전에 기록된 설계 원칙을 적용하되 없으면 원칙부터 확인함
  - **답을 받은 뒤**: 메모가 선택과 어긋나면 메모 기준으로 다시 확인하고, 선택이 뒤집히면 그 뒤의 원칙을 `feedback.md`에 `constraint`로 기록함
  - **따라오는 범위**: 합의에서 그대로 따라오는 적용 범위(같은 방식을 적용할 파일, 관련 테스트)는 따로 묻지 않고 계획의 적용 범위로 적음
- **이유**: 한 결정씩 묻는 방식은 유지하고 질문 수는 감수하며, 고칠 대상은 질문의 내용·방식·순서임
- **적용 범위**: 새 기준 문서 하나와 planning·execute의 질문 관련 절. 누락 점검은 `plan.md`의 각 절이 합의로 채워졌는지 확인하는 것으로 함

**PW-3 이슈가 여러 개일 때의 순서** (위임에 따른 선택 — 위임 문장 "의존일 수 있고 병행 진행 가능할 수 있고 등등을 고려해서 권장안으로")

- **바꾸는 것**: 분류표의 관계에 따라 합의와 실행의 순서를 셋으로 나눔
- **모양**: 독립이면 합의는 순차, 실행은 병행함. 선행 관계면 뒤 이슈의 합의는 앞 이슈의 합의가 끝난 뒤 앞 계획의 계약을 가리켜 진행할 수 있고 실행은 앞 이슈의 결과물이 생긴 뒤 시작함. 공통 결정이면 그 결정을 가진 이슈를 먼저 구현해 결과를 사용자에게 확인받은 뒤 나머지 이슈의 합의를 시작함. 실행 중 나온 질문은 보관했다가 진행 중인 이슈의 합의가 끝난 뒤 이슈 키를 밝혀 물음
- **이유**: 이슈 사이 관계의 기본값은 독립이고, 공통 결정의 오류는 묶음 크기만큼 늘어남
- **적용 범위**: planning의 분류 절과 execute의 실행 순서 절

**PW-4 기록 위치**

- **바꾸는 것**: 기록 폴더 이름을 브랜치명이 아니라 이슈 키로 정하고, 여러 레포·이슈에 걸친 내용은 한 곳에만 쓴 뒤 나머지가 가리킴
- **모양**: 훅은 브랜치명에서 이슈 키만 뽑아 폴더를 찾고 키가 없으면 폴더를 정하지 않음. 이슈 키가 없는 작업은 주제의 kebab-case 이름, 한 이슈를 나눠 진행하라고 지정하면 `키-이름`, 같은 키의 기존 폴더가 있으면 이어 씀. 기록은 코드가 바뀌는 레포마다 그 이슈 키 폴더에 두며, 레포 사이 계약은 값을 정의하는 레포의 기록에 원문을 두고 받아 쓰는 레포는 의존 항목과 출처(레포·이슈 키·기준 커밋)만 적음. 외부 규격이 원문이면 양쪽이 그것을 가리키고, 머지·배포 순서만 관련 기록 모두에 한 줄씩 적으며, 공통 결정은 그 결정을 가진 이슈의 기록에 두고, 무관한 이슈끼리는 서로 가리키지 않음
- **이유**: 묶음 세션에서는 현재 브랜치가 다루는 이슈와 무관하고, 같은 이슈가 두 레포에 걸칠 때 같은 이름이어야 서로 찾을 수 있음
- **적용 범위**: 세션 훅의 폴더 판정, 기록 형식 문서, planning·execute의 기록 절

**PW-5 현재 상태만 기록**

- **바꾸는 것**: `plan.md`와 `feedback.md`는 현재 유효한 내용만 담고 바뀐 이력은 git에 맡김
- **모양**: 합의가 바뀌면 `plan.md`의 해당 부분을 고쳐 쓰고 Re-plan·추가 계획 절과 폐기 선언을 두지 않음. 틀린 것으로 드러난 `feedback.md` 항목은 그 항목을 고치되 틀렸던 가정을 같은 문장에 남김. 합의가 바뀐 부분만 고치고 주제가 다른 작업은 다른 폴더에 기록함
- **이유**: 덧붙이기만 하는 기록은 무엇이 지금 유효한지 읽는 쪽이 다시 판정해야 함. 파일만으로 변경 시점을 볼 수 없고 병렬 브랜치 충돌이 잦아지는 것을 감수함
- **적용 범위**: 기록 형식 문서, 계획 형식 문서, execute의 재계획 절

**PW-6 `plan.md` 구성**

- **바꾸는 것**: 절을 `의도`, `확인한 사실`, `합의`, `연결`, `검증`, `범위 밖`으로 함
- **모양**: `확인한 사실`은 코드·문서와 대조한 사실과 출처, `합의`는 단위마다 바꾸는 것·코드 모양·이유·적용 범위, `연결`은 다른 레포 의존·머지와 배포 순서·공통 결정·다른 레포에 요청할 일, `검증`은 명령과 통과 조건임. `합의` 항목은 모두 사용자가 확인한 것이고 판단을 맡긴 항목에만 위임 범위를 표시함
- **이유**: 합의 단위 하나가 작업과 커밋의 단위이므로 커밋 분해 표, 파일별 변경 표, 사다리 열, 파일별 설계 절이 필요 없고, 최소 코드 원칙은 각 합의 단위의 이유에서 설명함
- **적용 범위**: 계획 형식 문서, planning의 계획 작성 절, execute의 계획 읽기 절

**PW-7 두 파일의 역할과 기록 유형**

- **바꾸는 것**: `plan.md`는 이 이슈에서 하기로 한 것을, `feedback.md`는 이슈가 끝난 뒤에도 쓸 지식만 담음
- **모양**: 의도·범위·후속 작업과 이 이슈에서 고른 방식의 이유는 `plan.md`에만 적음. 새 `feedback.md` 항목은 `constraint`(업무·인프라 규칙, 함정, 환경 사실, 알려진 한계, 선택이 뒤집히며 드러난 설계 원칙), `correction`(그럴듯하지만 틀렸던 가정), `why`(이후 같은 선택 앞에 설 사람이 알아야 할 선택 이유) 세 유형만 쓰고 `context`는 쓰지 않음. 계획을 거치지 않은 작업도 확인한 의도는 `plan.md`의 `의도`에 적음. 판정 기준은 "이 이슈가 끝난 뒤 다른 작업을 하는 사람의 행동이 이 문장으로 달라지는가"이고, 다른 기록이나 주입 문서에 있는 사실은 다시 적지 않으며, 모든 항목에 누가 말했는지 또는 어디서 확인했는지를 하나 이상 적음
- **이유**: 기록 표본에서 이후에도 쓸 지식은 20~23%였고 나머지는 그 이슈의 진행 내용이었음
- **적용 범위**: 기록 형식 문서와 세션 훅의 규약 요약

**PW-8 플랜 모드 미사용**

- **바꾸는 것**: planning은 플랜 모드를 쓰지 않고 이슈별 승인을 질문으로 받음
- **모양**: 합의될 때마다 이슈 폴더의 `plan.md`·`feedback.md`에 바로 쓰고 커밋은 승인 뒤에 함. 이슈별 승인은 합의 항목 목록과 계획 파일 경로를 보이고 받으며, 승인 전 코드 수정 금지는 스킬 규칙으로 지킴. 플랜 모드로 시작한 세션은 분류표까지만 보인 뒤 플랜 모드를 끝냄
- **이유**: 플랜 모드는 파일 쓰기를 막아 합의가 대화에만 남고, 승인 화면이 계획 하나만 받아 이슈별 승인과 맞지 않음. 하네스가 승인 전 수정을 막아 주던 보호와 계획 전문 승인 화면을 잃는 것을 감수함
- **적용 범위**: planning 스킬, ExitPlanMode 훅과 그 스크립트 삭제, `runtime.md`의 Codex 계획 승인 문단

**PW-9 승인 뒤 실행**

- **바꾸는 것**: 이슈별 승인을 받으면 계획 스냅샷을 커밋한 뒤 같은 세션이 실행으로 넘어가고, 새 세션에서 execute를 부르는 방법도 남김
- **모양**: "계획까지만"이라고 하면 승인 뒤 멈춤. 구현을 본 세션이 직접 할지 서브에이전트에 맡길지는 에이전트가 판단하며(위임 문장 "필요에 따라 각 구현에는 서브에이전트 쓰던지"), 서브에이전트가 합의에 없는 결정을 만나면 멈추고 본 세션이 질문함. execute의 나머지 동작(검증 실패 시 정지, 합의 밖 결정은 질문, PR 생성은 요청 시에만)은 현행 규칙을 그대로 가져감
- **이유**: 승인 없는 구현은 이슈별 승인이 막으므로 세션을 끊을 이유가 없음
- **적용 범위**: planning의 승인 절, execute 스킬, `runtime.md`

**PW-10 세션 훅**

- **바꾸는 것**: 세션 시작 훅은 규약 요약과 기록 위치만 알리고 `feedback.md` 본문을 주입하지 않음
- **모양**: 규약 요약은 모든 세션에 적용되는 것(의도 확인 후 `plan.md`의 `의도`에 기록, 이후에도 쓸 지식을 `feedback.md`에 기록, 규모가 있거나 요구가 불분명하면 planning 스킬, 형식 문서 경로)만 담음. 브랜치명에서 이슈 키가 나오면 그 폴더 경로와 두 파일의 유무를 알리고, 파일이 있으면 작업 전에 읽으라고 지시함
- **이유**: 고쳐 쓰는 기록은 파일 끝이 최신이 아니고, 큰 파일일수록 잘려 들어가며, 묶음 세션은 폴더가 여러 개임
- **적용 범위**: 세션 훅 스크립트와 규약 요약 문서. 본문 주입, 4,000바이트 자르기, "원본을 다시 읽으라"는 규칙을 삭제하고 관련 테스트를 고침

**PW-11 검증에서 드러난 위반에 맞춘 보완** (위임에 따른 선택 — 위임 문장 "워크플로우 검증 다시 진행하고 위반항목 수정", "요구사항의 진위여부, 작업 필요여부 등도 테스트")

- **바꾸는 것**: 모의 진행의 판정에서 나온 위반과 스킬 문구의 빈 곳에 맞춰 planning·execute, 질문·설명 작성 기준, 계획 형식, 기록 형식에 규칙을 더함
- **모양**:
  - **질문**: 메시지 하나에 물음 하나이고 답에 따라 갈리는 다음 질문은 답을 받은 뒤에 물음. 대상마다 규칙이 다르면 대상마다 확인하고, "필요한가"와 원칙을 세부보다 먼저 확인하며, 요청 대상이 아닌 기능이 함께 쓰는 코드를 고치는 안은 그 범위부터 확인함. 보내기 전 점검에 가드를 약하게 하는 동작이 들어 있는지를 더함
  - **근거 확인**: 요구가 이미 충족돼 있거나 전제가 사실이 아니면 그 부분의 합의를 시작하지 않고 근거와 함께 알리며, 남은 요구가 없는 이슈는 계획 없이 끝냄. 다른 팀이나 시스템에 확인해야 하는 사실은 기다릴지 물음. 검증 명령과 제약은 요청의 완료 조건, 앞선 기록, 저장소에서 찾아 적고, 완료 조건을 찾지 못하면 물음
  - **분류**: 한 이슈가 여러 레포를 바꾸면 레포마다 한 행이고 값을 정의하는 레포가 먼저임. 코드를 볼 수 없는 레포는 합의를 시작하지 않으며, 공통 결정에서 계획까지만 하라고 했으면 그 결정을 가진 이슈의 승인 뒤 멈춤
  - **합의와 승인**: 요청과 이슈 본문이 정한 요구는 다시 확인받지 않고, 업무 결정과 구조 결정은 나눠 확인하며, 승인을 요청하기 전에 요구 항목을 하나씩 대조함
  - **형식**: 코드 변경이 따로 나오지 않는 결정은 합의 단위로 두지 않고, `이유`는 안마다 한 줄로 적으며, 새 기록 폴더는 저장소의 기존 이름 규칙과 달라도 이슈 키로 만듦
  - **execute**: 합의한 모양에 없는 동작·분기·테스트는 넣기 전에 묻고, 넣은 뒤에 `plan.md`를 고쳐 합의처럼 적지 않음
- **이유**: 사용자가 위반 수정을 맡겼음. 한 메시지에 여러 물음을 넣는 위반과 "필요한가"를 건너뛰는 위반은 문구를 고친 뒤에도 사례에 따라 남아 실제 사용에서 다시 확인해야 함
- **적용 범위**: planning·execute 스킬, 질문·설명 작성 기준, 계획 형식, 기록 형식, README

**PW-12 이슈 본문은 요구만 출발점으로 삼음**

- **바꾸는 것**: planning이 이슈 본문에서 요구만 뽑고, 대상 레포와 수정 위치는 계획 시점의 코드에서 도출함
- **모양**: 요구는 원하는 결과, 업무 규칙, 완료 조건임. 본문의 원인 분석, 수정 위치, 작업 항목, 구현 방법은 본문이 쓰인 시점의 주장으로 보고 코드와 대조함. 분류표에서 본문에만 적힌 대상 레포는 `미확인`으로 표시해 대조 뒤 확정함. 다시 확인받지 않는 것은 요구뿐이고, 본문이 적은 구현 방법과 수정 위치는 코드에서 도출한 안으로 확인받음. 사용자가 세션에서 직접 지시한 범위는 본문보다 우선함
- **이유**: 이슈 본문은 잘못된 분석으로 만들어졌거나 작성된 뒤 코드가 바뀌어 현재 상태와 맞지 않을 수 있음. 본문의 작업 항목을 다시 확인하느라 질문이 늘어나는 것을 감수함
- **적용 범위**: planning 스킬의 분류·근거 확인·합의 절, 질문·설명 작성 기준, README

### pr-workflow

**PR-1 이슈와 레포 목록 입력**

- **바꾸는 것**: create·review·fix가 현재 체크아웃의 저장소만이 아니라 이슈와 레포의 목록 또는 PR 목록을 받음
- **모양**: 다른 레포는 그 레포의 체크아웃이나 실행 때 만든 워크트리 경로에서 같은 절차를 실행하고 경로를 찾지 못하면 물음. 선행 관계가 있으면 선행 PR부터 만듦. `plan.md`의 `연결`에 내용이 있으면 PR 본문 끝에 `연결` 절을 두어 형제 PR(만들어진 것은 링크, 없는 것은 레포와 브랜치명)과 머지·배포 순서를 적고, 무관한 이슈의 PR에는 두지 않음. 외부 쓰기 승인은 PR마다 한 번 받고 사용자가 미리 필요 없다고 하면 생략함
- **이유**: 실행 단위가 이슈와 레포의 조합이므로 PR도 같은 단위여야 하고, 배포 순서가 PR마다 보여야 함
- **적용 범위**: 세 스킬과 공통 절차 문서. "다른 저장소의 PR은 거절" 규칙을 삭제함

**PR-2 PR 본문**

- **바꾸는 것**: 개요·작업 내역·영향도·검증 결과 네 절을 유지하고 내용의 출처를 `plan.md`로 맞춤
- **모양**: 개요의 배경은 `의도`에서, 작업 내역은 `합의` 단위마다 한 줄로, 검증 결과는 `검증` 명령을 실제로 실행한 결과로 채우고, 영향도는 지금처럼 diff에서 도출함. `의도`가 있으면 배경을 묻지 않고, 기록이 없을 때만 묻고 만들어 내지 않으며, 계획 없이 한 작업은 작업 내역을 파일이나 영역 단위로 씀. 세부 규칙은 절마다 "무엇을 담는가" 한 줄과 공통 원칙 세 가지(확인한 사실만 적기, 같은 사실은 한 절에만 적기, 리뷰어의 판단을 바꾸지 않는 내용은 빼기)로 줄임
- **이유**: 계획에 합의된 내용이 이미 있어 본문을 다시 추론할 필요가 없음
- **적용 범위**: create 스킬. 4불릿 상한, 영향도 4축 목록, 제외 항목 6종 목록을 삭제함. 줄인 규칙의 본문이 기존 규칙보다 길게 나온 비교 결과를 사용자가 확인하고 그대로 확정함

**PR-3 합의 대조 리뷰**

- **바꾸는 것**: review가 그 PR의 `plan.md`를 기준 문서에 더하고 "합의와의 어긋남"을 봄
- **모양**: diff에 있는데 `합의`의 어느 단위에서도 나오지 않는 변경과, 합의한 모양·범위와 다르게 구현된 부분을 지적함. 리뷰 의도는 PR 설명 대신 `plan.md`의 `의도`와 `합의`에서 가져오고, `합의` 절이 있을 때만 적용하며, 코멘트는 기존 형식에 구분 값 `합의`만 더함
- **이유**: "합의된 것만 구현된다"를 구현 뒤에 확인하는 단계가 없었고, 구현한 쪽이 스스로 대조하는 것은 확인이 되지 않음
- **적용 범위**: review 스킬과 서브에이전트 지시, 코멘트 형식 문서의 구분 값

**PR-4 반증 단계 삭제**

- **바꾸는 것**: 도구 없는 서브에이전트가 diff만 보고 틀린 지적을 제외하던 반증 단계를 삭제함
- **이유**: 요약 코멘트 24개에서 제외가 0건이었고, 유지 조건이 넓어 제외가 드물 수밖에 없으며, 의도된 동작을 지적하는 유형은 diff만으로 가릴 수 없음
- **적용 범위**: review 스킬의 반증 절과 소규모 PR 경로의 문구, 스킬 설명, 서브에이전트 지시, 보고 항목, 요약 코멘트 `리뷰 범위` 줄의 `반증 제외` 항목, README. 다음 실행이 읽는 `리뷰 스냅샷` 줄은 그대로 둠

**PR-5 같은 결함의 일관 처리**

- **바꾸는 것**: 한 번의 실행에서 다루는 범위(한 PR의 파일들, 묶어서 받은 PR들) 안에서 같은 결함을 하나로 처리함
- **모양**: review는 지적을 모은 뒤 같은 원인의 결함이 여러 파일·PR에 있으면 본 세션이 등급 판정 질문을 한 번 적용해 등급을 맞추고 바꾼 등급을 보고에 표시함. fix는 수용·기각 표에서 같은 결함을 한 줄로 묶어 한 번 판정하고, 코드 사정이 달라 판정이 갈리면 이유를 적음
- **이유**: 등급이 갈리면 반영 여부까지 갈려 같은 결함이 일부 PR에만 남음
- **적용 범위**: review의 보고 절과 fix의 판정 절. 따로 실행한 리뷰끼리는 맞추지 않음

**PR-6 유지하는 것**

- **유지**: 자기 PR을 스스로 리뷰하고 반영할 때도 지적과 반영 결과를 줄별 코멘트로 남기며, 코멘트를 주고받는 방식과 승인 절차, 리뷰 절차의 나머지(파일별 서브에이전트, 스택별 체크리스트, 줄 위치 확정, 기존 코멘트와의 중복 제거, 재리뷰 판정)를 그대로 둠
- **이유**: 코멘트 유지는 사용자 결정이고, 나머지는 바꿀 근거가 없음

### agent-wiki

구조는 다시 쓰지 않고 아래 다섯 가지만 고칩니다. 프롬프트 정리는 뜻이 바뀌지 않는 범위로 합니다.

**AW-1 세션 주입**

- **바꾸는 것**: 주입에서 문서 이름 목록을 빼고 문서 장 수와 문서 색인 경로만 주며, 등록 레포 전부에 같은 형태로 적용함
- **모양**: 주입은 규칙, 레포 지도, 문서 장 수와 색인 경로, 다른 도메인 목록만 남김. 색인 파일은 문서 색인(전용 문서 먼저, 이름과 description)과 레포 책임 파일로 나눔. 규칙 문구는 요청이 도메인의 업무 사실과 관련되면 문서 색인을 읽고 맞는 문서를 골라 읽으라는 내용으로 바꿈
- **이유**: 이름 목록은 문서 수에 비례해 늘어 같은 속도면 4주 안에 한도를 넘음. 대가는 문서를 찾는 세션마다 문서 색인을 한 번 읽는 것이며 그 양은 문서 수에 비례함
- **적용 범위**: 세션 훅, 주입 생성기 3종, 문서 규약의 도입 문장, README, 관련 테스트

**AW-2 update 실행 끝 질문**

- **바꾸는 것**: `건너뜀`·`미해결 충돌` 행을 머지 뒤로 넘기지 않고 update가 반영을 마친 뒤 PR을 만들기 전에 세션에 표로 보여 주고 행마다 물어 같은 PR에 반영함
- **모양**: 질문은 add가 쓰는 형식(기존 값과 새 값, 코드로 확인되면 현재 코드 값 병기)이고 선택지는 `새 값`·`기존 유지` 둘임. 판단이 서지 않으면 `기존 유지`로 확정해 PR 표에 그 결과로 남김
- **이유**: 머지 뒤 add를 따로 실행하는 경로가 한 번도 쓰이지 않았고, update가 자기 완결로 끝나야 함
- **적용 범위**: update 스킬, PR 본문 양식의 액션 표

**AW-3 위치 판정**

- **바꾸는 것**: 위치 때문에 옮겨 간 문서의 두 번째 검토는 위치를 판정하지 않고 나머지 기준만 봄
- **모양**: 사실은 첫 검토가 지정한 문서에 기록되고 `위치 재배정` 액션은 없어짐
- **이유**: 덜 맞는 문서에 기록된 사실은 옮길 수 있지만 기록되지 않은 사실은 되찾을 수 없음
- **적용 범위**: 반영 절차 문서의 재배정 장과 검토 지시, PR 본문 양식

**AW-4 add의 update PR 행 경로 삭제**

- **바꾸는 것**: add가 update PR 행을 입력으로 받는 부분을 삭제함
- **적용 범위**: add 스킬 설명의 트리거, 입력 집합, 추출·질문 절의 PR 행 문구, 게시 절차 문서의 PR 읽기 장, PR 본문 양식의 안내 문장
- **이유**: AW-2와 AW-3으로 update가 넘기는 행이 없어짐
