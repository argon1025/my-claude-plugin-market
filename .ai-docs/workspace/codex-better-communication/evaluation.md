# better-communication 개선 평가

## 결론

기존 4.1.0의 명사형 종결·고정 보고 골격·굵은 라벨 강제를 없애고, 짧은 완전한 문장으로 결론과 필요한 근거를 전달하도록 4.2.0을 작성했다. 실제 Claude Code로 미적용·기존·수정안을 비교하고, 두 차례 보완했다.

최종 비교 15건의 전체 응답 길이는 기존 대비 약 35% 줄었다. 다만 길이는 보조 지표다. 상세 요청의 설명 깊이, 필수 사실, 미검증 상태, 지정된 양식도 함께 확인했다. 문체가 나아져도 모호한 요구사항을 정확하게 해석하거나 추측을 완전히 막는 것은 보장하지 않는다. 아래의 남은 문제를 함께 보아야 한다.

## 먼저 정한 기준

- 첫 문장에서 질문에 답하거나 결과를 말한다.
- 자연스러운 존댓말과 구체적인 동사를 쓴다. 명사만 나열한 보고 문체를 강제하지 않는다.
- 간단한 질문에는 짧게 답하고, 상세 설명 요청에는 필요한 근거를 충분히 제공한다.
- 조건·적용 대상·실패·미검증 상태를 줄이지 않는다.
- 사실·추천·미확인 사항을 구분하고, 합의되지 않은 동작을 채워 넣지 않는다.
- 사용자의 양식을 따르고, 반복 요약·불필요한 후속 질문·가상의 기능 설계를 덧붙이지 않는다.

평가는 실행 성공 여부와 분리했다. CLI가 정상 종료했다고 좋은 답변으로 판정하지 않았으며, 사람이 응답의 의미와 문체를 읽고 판단했다. 단어 일치만으로 합격 점수를 만들지 않았다.

## 과거 작업 기록에서 가져온 평가 관점

사용자가 지정한 두 작업 기록 디렉터리의 Markdown 파일 82개(44개·38개)를 검색하고, 조건·책임·범위가 바뀐 대표 기록을 읽었다. 명시적인 Re-plan 제목은 3개였으며, 다른 수정 결정은 feedback에 누적되어 있었다. 모든 파일을 정독하거나 모든 재작업 원인을 확정한 것은 아니다.

회사 프로젝트의 이름·원문·경로·식별자는 평가 입력이나 이 저장소의 자료로 옮기지 않았다. 다음과 같이 일반화한 상황만 사용했다.

| 관찰한 변경 유형 | 평가에서 확인할 점 |
|---|---|
| 필수값 검사와 변경 이력 기록이 같은 “검증”으로 불림 | 제거할 실제 동작을 나눠 설명하고 범위를 확인하는가 |
| 형식 검사와 버전별 필수 여부의 책임이 다시 정해짐 | 기존 요청이 차단되는 영향과 담당 계층을 설명하는가 |
| 관리자 조건과 사용 해제 조건의 결합이 바뀜 | OR와 AND의 차이를 행위자·동작별로 보여 주는가 |
| 값 없음에 기본값을 넣는 정책을 되돌림 | 미선택과 명시적인 부정을 같은 값으로 바꾸는 의미를 설명하는가 |
| 설치 후 타입 변경, 실행 후 렌더링 한계를 발견함 | 초기 설명을 정정하고 새로 확인한 영향과 미검증 상태를 말하는가 |

이 기록만으로 사용자의 불만 원인이나 모든 재작업을 문체 탓으로 단정할 수는 없다. 기술 조사 부족과 새로 발견한 제약은 문체 규칙 외에 코드 확인·요구사항 인터뷰가 필요한 문제다.

## 실행 방법

- 날짜: 2026-11-05
- CLI: Claude Code 2.1.318
- 모델: 모든 실행에서 `claude-opus-5-5`로 고정하고 초기화 이벤트에서도 같은 모델을 확인했다.
- 조건: 대상 플러그인 미적용 / 기존 4.1.0 / 수정 중간안 / 최종 4.2.0.
- 사용자·프로젝트 설정을 제외하고 MCP를 비웠다. CLI 내장 플러그인은 모든 조건에 남아 있었으므로 “미적용”은 대상 및 사용자 설정 플러그인을 제외했다는 뜻이다.
- 기존·수정 조건은 실제 `--plugin-dir`로 로드했다. SessionStart·UserPromptSubmit 훅의 성공을 확인했다. 규칙을 사용자 프롬프트에 직접 붙인 실험이 아니다.
- 작업 설명은 가상 기록이다. 코드 원인 설명 1건만 격리된 실제 파일을 Read 도구로 읽게 했으며, 모든 조건에서 파일 해시가 유지되었다. 실제 회사 저장소에서 구현하거나 브라우저를 조작한 시험은 아니다.
- 최종 세 조건은 같은 15개 입력으로 45회 실행했다. 중간안 12회·14회를 포함하면 본 평가 실행은 71회이며, 별도 훅 연결 확인 1회가 있었다. 각 조건·사례는 한 번씩 실행했고 반복 표본 통계는 아니다.

사용한 주요 명령 형태:

```sh
claude -p --model claude-opus-5-5 \
  --setting-sources '' --strict-mcp-config \
  --mcp-config '{"mcpServers":{}}' --tools '' \
  --disable-slash-commands --permission-mode dontAsk \
  --permission-prompts none --no-session-persistence \
  --output-format stream-json --verbose --include-hook-events \
  --max-budget-usd 2 --plugin-dir /path/to/plugin < prompt.txt
```

미적용 조건은 `--plugin-dir`를 제외했다. 코드 확인 사례만 `--tools Read,Glob,Grep --allowedTools Read,Glob,Grep`를 사용했다. 원래 파일은 아래와 같다.

```js
export function canReserve(start, end, bookings) {
  return !bookings.some((booking) =>
    start <= booking.end && end >= booking.start
  );
}
```

[입력과 평가 관점](./cases.json), [실제 응답과 실행 정보](./responses.json)를 함께 보관했다. 세션 ID 등 원시 스트림 메타데이터는 제외했고 임시 경로는 치환했다. `execution_success`는 CLI 실행 성공만 뜻한다.

## 수정 과정

1. **기존 4.1.0**: 미적용보다 짧아지는 효과는 이미 있었다. 그러나 `미수행 상태임`, `정합성 확보` 같은 문체, 모든 불릿의 라벨, 상태를 반복하는 보고 구조가 남았다.
2. **첫 수정안**: 자연스러운 문장과 문단을 기본으로 했다. 문장은 나아졌지만 같은 사실을 반복하고 가상 위험을 늘려 분량이 증가했다. [첫 수정안](./rules-first.md)에 보존했다.
3. **두 번째 수정안**: 일반 질문은 2~4문장을 기본으로 하되 필요한 사실과 상세 요청은 예외로 두었다. 이유·예시·후속 분기를 자동으로 늘어놓지 않도록 했다. 별도로 추가한 2개 입력에서도 길이는 줄었지만, 값 없음의 의미에서 입력 누락 처리 정책까지 추측하는 문제가 발견됐다. [두 번째 수정안](./rules-second.md)에 보존했다.
4. **최종안**: 입력에 없는 계약을 만들지 않는 규칙, 모호한 문장을 확정하지 않는 규칙, 관례적인 후속 질문을 붙이지 않는 규칙을 보완했다. 괄호와 OR·AND를 명시한 추가 사례로 조건 설명도 확인했다. [최종 규칙](../../../better-communication/rules/agent-guide.md)이 제품에 반영된 내용이다.

기존 규칙은 [수정 전 원본](./rules-before.md)에 보존했다. 중간안과 최종안은 같은 4.2.0 개발 중 버전이므로 `responses.json`의 condition과 rules_sha256으로 구분한다. 처음 두 추가 입력은 두 번째 수정안에서 처음 사용했고, 이후 최종안에서는 회귀 확인 입력으로 재사용했다. 따라서 독립된 대규모 미사용 평가 세트로 볼 수 없다.

## 실제 응답 예

빌드가 중단된 상황의 기존 응답은 `아직 완료로 볼 수 없음`으로 시작하고 상태 불릿과 완료 조건을 이어 붙였다. 최종 응답은 다음과 같다.

> 아직 끝났다고 보기는 어렵습니다. 코드 수정은 마쳤고 단위 테스트 41개도 모두 통과했습니다. 다만 빌드가 의존성 다운로드 중 `ENOTFOUND registry.npmjs.org` 오류로 멈춰서 성공하는지 확인하지 못했고, 브라우저 확인도 아직 하지 않았습니다. 지금까지 다른 원인 코드가 있다는 증거는 없으니, 네트워크 연결을 확인한 뒤 빌드와 브라우저 확인을 마치면 완료로 볼 수 있습니다.

제거 범위를 확인하는 최종 응답은 설명과 질문을 134자로 정리했다.

> 이 필드에는 지금 두 가지 동작이 있습니다. 값이 비어 있으면 제출을 막는 필수값 검사와, 값이 바뀔 때 변경 이력을 남기는 기록입니다. 말씀하신 '검증'이 필수값 검사만 뜻하는지, 변경 이력 기록까지 함께 없애자는 뜻인지 알려 주시겠어요?

## 의미 검토와 남은 한계

- 완료 보고·빌드 중단·PR·초기 설명 정정·진행 보고는 주어진 완료/미완료 사실과 수치를 유지했다. 실제 파일 설명은 경계 포함 연산자와 사례를 연결했고 파일을 고치지 않았다.
- 상세 API 비교는 두 방법, 배포 순서, 두 필드 처리, 제거 조건, 롤백을 모두 설명했다. 다만 앱 스토어 배포나 다른 소비자의 존재를 가정하고, 구버전 트래픽을 합의된 임계치로 처리하는 추가 정책도 제안했다. 요구된 항목이 있다는 사실이 기술 정책의 완전한 타당성을 뜻하지는 않는다.
- 범위 확인은 필수값 검사와 이력 기록을 구분해 질문했다. 책임 분담 사례도 기존 요청이 거부되는 영향과 계층별 역할을 유지했다.
- 캐시 사례는 오래된 가격과 캐시 미스의 비용을 설명했지만, 최종 응답에서 명시적인 갱신·무효화 방안 설명은 약해졌다. 더 짧아졌다는 이유로 필수 관점이 모두 충족됐다고 평가하지 않았다.
- 자연어 조건 사례는 “관리자”의 적용 범위를 한쪽으로 해석하는 문제가 남았다. 초기 평가 기준 자체도 애매한 문장에서 OR 해석을 정답으로 기대한 문제가 있었다. 이 사례는 논리 정확도 점수에서 제외했다. 별도로 OR·AND를 명시한 입력에서는 관리자/일반 사용자와 설정/해제의 네 조합을 정확히 구분했고, 미정인 반영 시점을 만들지 않았다.
- 값 없음 사례는 미선택을 수신 거부로 바꾼다는 핵심을 보존했다. 그러나 동의 화면·통계를 추가로 가정하고 발송 판단 규칙도 제안했다. 최종안에서도 추측과 범위 확장이 완전히 사라지지 않았다는 반례다.
- 추천안 사례는 미확정 추천과 질문 하나를 구분했지만, ID 복제 후 참조 이동이라는 추가 설계를 붙였다. 모든 상황에서 최소한의 답변만 한다고 보장할 수 없다.

이 평가는 한 모델의 단일 응답 표본이다. 모델·세션 길이·다른 플러그인과의 조합에 따라 달라질 수 있다. 회사 커뮤니케이션 플러그인이나 설치된 캐시는 수정하지 않았다. 계획 인터뷰 전체나 실제 개발 결과물의 만족도를 측정한 실험도 아니다. 문체는 이 규칙으로 개선하고, 정책과 범위는 plan-workflow의 사실 확인·한 결정씩 합의 절차로 확정해야 한다.

## 파일 검증과 반영 상태

플러그인·훅·마켓플레이스 JSON 파싱, 훅 두 개의 `bash -n`, 실제 훅 실행과 JSON 내용, 문서 상대 링크·코드 펜스, `git diff --check`를 확인했다. 71개 기록의 실행 성공·모델·훅·파일 미변경 상태를 대조했으며, 최종 15개 실행에 기록된 규칙 해시가 제품에 저장한 파일과 일치한다.

최종 규칙 SHA-256: `0c64c087f41a1d2535d9e1d195efa7aeb61029b83befd894a651c8f95853d2f1`.

`better-communication`은 4.2.0으로 올렸다. 앞서 수정한 `plan-workflow`와 마켓플레이스의 미커밋 변경은 유지했다. 커밋·푸시·마켓플레이스 게시·설치본 업데이트는 하지 않았다.
