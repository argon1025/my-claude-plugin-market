# llm-wiki 담는 기준 단일화와 update 사후 검토 v4.1.0

## 의도

- **왜**: `/llm-wiki:update` 1회 실행(pigeon-trade `b292dfa..e9a2341`)에서 추출 사실 21건이 전부 `추가`되어 코드로 알 수 있는 사실·작업 범위 서술·린터 설정 전사가 위키에 들어갔고, 기존 문서 description의 트리거가 소실됨
- **누가**: 위키를 매 세션 주입받는 계획·구현 에이전트가 저가치 불릿과 좁아진 트리거로 주입 토큰 낭비와 문서 탐색 실패를 겪음
- **완료**: 규약 1장이 도구·입력 종류와 무관한 판정 질문 하나로 담을지를 가르고, update가 반영 뒤 검토 에이전트로 그 질문과 문체·description 규약 위반을 걸러 삭제 사유를 보고함

## 배경

진단은 리뷰 문서(`llm-wiki-update-review.md`)의 원인 기술을 실제 위키 커밋(`3885a62`, `772b5fd`, `9211a7f`, `f2302f6`)과 원천 노트(pigeon-trade `e9a2341:.ai-docs/workspace/toss-invest-integration/feedback.md`)로 대조해 다시 도출함.

| 증상 | 확인한 원인 |
|---|---|
| f10·f15·f17·f21 등 코드로 알 수 있는 사실 반영 | 1장 grep 테스트가 "검색 한 번"이라는 수단 기준이라 설정 파일·테스트·코드의 부재(미구현 범위)로 드러나는 사실을 가르지 못함, 추출은 코드 조회가 금지되어 판정 수단도 없음 |
| 담지 않는 것 목록의 모호함 | 타입·린터·CI·다른 시스템 원본 등 사례 나열이라 린터·CI가 없는 프로젝트에 맞지 않고, "린터 예외만 담음"·"다른 시스템 원본 제외"가 담는 것의 "외부 서비스 제약"과 충돌 |

| `toss-openapi-constraints.md` description의 "리플레이 구간" 트리거 소실 | 7장 병합 방식 "뜻이 달라지면 description도 다시 씀"이 `추가`에도 재작성을 열어 둠 |
| `토스인베스트 폴더(toss-invest)` 음차 | 5장 "업무 낱말 우선·식별자 괄호 병기"가 업무 낱말이 없는 폴더명에도 낱말 창작을 유도 |
| 150자 초과 불릿, `</content>` 잔여 줄, 도메인 루트 중복(f14) | 반영 뒤 문서를 규약 전체로 읽는 단계가 없음 |

## 확정 결정 (사용자 확인 2026-09-25)

- **slug**: `.ai-docs/workspace/wiki-update-review-gate/`에 `plan.md`(신규)·`feedback.md` 기록
- **담는 기준**: 1장을 "머지 시점 레포를 읽은 에이전트가 이 불릿 없이 같은 결론에 이르는가" 한 질문으로 다시 쓰고, 사례 나열(심볼 정의·린터·CI·다른 시스템 원본)은 그 질문에 흡수해 삭제
- **입력 무제외**: 추출 입력은 테스트를 포함한 git diff 전체와 커밋 메시지·노트 그대로이며 입력 종류별 조항을 두지 않음 — 현행 `update.py`는 잠금 파일·빌드 산출물만 제외하므로 변경 없음
- **게이트 원칙**: 기계식 검사는 현행 `catalog.py --check`(frontmatter·경로·제목·description 길이·중복)만 유지하고 새 스크립트 검사를 더하지 않음, 의미 판단 위반은 반영 뒤 검토 에이전트 한 단계가 잡음
- **중복 게이트 제거**: 반영 에이전트의 자체 `catalog.py --check`·`blocked`·`check` 필드를 없애고 메인 전수 검사 한 곳으로
- **추출 무변경**: 추출 출력 칸과 모델(Sonnet) 유지
- **리뷰 개선안 기각**: 4.1 검색 문구 기재, 4.2 유형별 처리표, 4.3 기각 칸, 4.4 배정표 확장, 4.5 신규 문서 최소 3건, 4.6 소비 레포 수 기반 배치, 4.7 스크립트 검사, 4.8 추출 Opus 전환 — 단일 판정 질문과 사후 검토가 같은 위반을 포섭하며, 토스 응답 형식의 도메인 루트 배치는 외부 서비스 사실이라 옳았음

### doc-contract.md

1장 세 불릿을 아래로 교체함.

```markdown
- **판정**: 머지 시점 레포(코드·설정·테스트)를 읽은 에이전트가 이 불릿 없이 같은 결론에 이르면 담지 않음 — 판정 단위는 불릿, 결정은 코드에 보이는 선택을 뺀 버린 대안·이유로 판정, 여러 레포가 같은 값·방식을 지켜야 하는 사실은 한 레포만 읽어서는 드러나지 않아 담음
- **담는 것**: 판정을 통과한 버린 대안과 이유, 코드 밖 맥락(도메인 정책·외부 서비스 제약·계정·인프라), 레포 사이 맞출 값, 코드가 강제하지 않는 규칙·함정·반복 절차
- **담지 않는 것**: 판정에 걸리는 것과 지금 참이 아닌 것(변경 서사·미확정 계획), 외부 명세 전사(소재와 함정만), 일반 지식, 비밀값, 레포 소관·책임·의존(9·10장 그래프로)
```

- **5장 업무 낱말 우선**: `업무 낱말이 없는 폴더·패키지명은 원형만` 덧붙임
- **7장 병합 방식**: `뜻이 달라지면 description도 다시 씀` → `추가는 description을 바꾸지 않고, 교체로 뜻이 달라질 때만 기존 트리거 낱말을 유지해 다시 씀`

### update/SKILL.md

- **4장 반영 프롬프트**: `검사:` 줄 삭제, 출력 JSON에서 `"blocked"`·`"check"` 삭제
- **5장 검토 — 문서 1장 = 에이전트 1회**(신설, 기존 5·6장은 6·7장으로): 반영이 끝난 문서마다 한 메시지에 병렬 Agent 호출, 모델은 메인 상속(audit 진단과 같음), 에이전트는 커밋하지 않음

````
update가 방금 고친 위키 문서 한 장을 규약으로 검토하고 위반만 고칩니다.

입력: 문서 {doc_abs}, 이번 변경 `git -C {WIKI_ROOT} diff -- {doc_abs}`(신규 문서는 전체), 근거 레포 {repo_path}·머지 {최신 sha}, 도메인 루트 목록 `python3 {catalog_py} --root {WIKI_ROOT}/knowledge/{domain} --shallow`.
기준: `sed -n '/^## 1\./,/^## 8\./p' {doc_contract_path}` — 1~7장, 1장 판정은 `git -C {repo_path} grep`·`git show {sha}:{경로}`로 머지 시점 레포를 읽어 수행.
범위: 이번 변경 줄과 description — 기존 줄은 무인 삭제 대상이 아님(audit 몫).
금지: 새 사실 추가, 이 문서 밖 편집.

출력: {review_dir}/{doc_slug}.json에 Write — {"doc","removed":[{"bullet","reason"}],"rewritten":N}. 응답은 건수만.
````

- **6장 검증**: 되돌림 조건을 "`catalog.py --check` 에러가 남은 편집 문서"로 바꾸고, 검토 뒤 본문 절이 빈 신규 문서는 파일째 삭제
- **7장 보고 기각**: `담지 않는 것` 건수는 검토 `removed` 합계이며 삭제 불릿 원문 표를 함께 실음 — 오삭제 복구 근거, `검사 실패`는 6장 되돌림
- **`--dry-run`**: 3장까지로 변동 없음
