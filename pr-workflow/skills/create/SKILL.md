먼저 [실행 환경 연결](../../references/runtime.md)을 읽고 패키지 경로·질문·위임 도구를 확정합니다.

대상마다 그 레포의 피처 브랜치로 **원본 저장소**의 베이스 브랜치를 대상으로 PR을 만듭니다. 로컬 `origin`이 개인 fork여도 PR 대상은 항상 원본 저장소입니다. 대상이 여럿이면 `pr-protocol.md`의 `대상`을 따라 선행 PR부터 하나씩 만듭니다.

## 계약 로드

- `{PLUGIN_ROOT}/references/pr-protocol.md` — 대상, 사전 조건, 저장소 좌표, 승인 게이트, 금지 행동
- `{PLUGIN_ROOT}/references/host.md` — 호스트 도구, 원본 저장소·베이스, 리뷰어·제목 관례, push·생성 절차

## 가드레일

- **배경 창작 금지**: 브랜치가 담지 않은 PR 맥락을 만들어 내지 않음. 커밋 로그를 산문으로 옮긴 것은 배경이 아님
- **베이스 고정**: 베이스 브랜치를 조용히 바꾸지 않음. 다른 베이스가 필요하면 사용자에게 먼저 확인함
- **리뷰어 추측 금지**: 리뷰어는 `host.md` 5장으로만 정함
- **승인 전 외부 쓰기 금지**: 6절 승인 전에는 push도 PR 생성도 하지 않음. PR 본문을 편집할 수 없는 호스트가 있으므로 초안은 생성 전에 검토받음

## 1. 브랜치 맥락 수집

```
git branch --show-current
git remote -v
git log --oneline <base>..HEAD
git diff --name-status <base>...HEAD
```

- **코드 변경**: 리뷰어가 볼 대상. 코드 경로는 전체 diff를 읽음
- **계획 문서**: 이 이슈의 `plan.md`를 브랜치의 변경 파일이나 세션 컨텍스트가 알려 준 기록 위치에서 찾아 읽음. 본문은 이 문서의 `의도`, `합의`, `검증`, `연결`에서 가져옴

## 2. 배경 게이트

- **계획에 `의도`가 있을 때**: 그 내용을 배경으로 쓰고 묻지 않음
- **없을 때**: 다른 절을 쓰기 전에 `## 개요`의 `배경`을 지금 채울 수 있는지 판정함. 초안 문장에서 "무엇을 바꿨는지"를 지우고 남는 것이 없으면 배경이 없는 것이며(`재시도 로직을 추가함`은 작업 내역의 재서술, `게이트웨이 타임아웃에서 주문이 유실되던 것을 막기 위함`이 배경), 브랜치명의 티켓 ID, 커밋 메시지의 증상, diff가 만지는 영역으로 후보를 만들어 고르거나 고치게 함
- **확보 불가**: 사용자가 배경을 제시하지 못하면 PR을 만들지 않고 중단함. 사용자가 배경 없이 진행하라고 명시한 경우에만 `## 개요` 절을 통째로 생략하고, 생략 사실과 지시를 보고에 남김. 어느 경우에도 커밋 로그 요약으로 그 절을 채우지 않음

## 3. 원본 저장소·베이스 확인

`pr-protocol.md` 1절로 원본 저장소 좌표와 베이스 브랜치를 확정하고, `host.md` 2장의 존재 확인으로 베이스 브랜치가 원본 저장소에 있는지 확인합니다.

## 4. 리뷰어

리뷰어와 PR 제목 관례는 `host.md` 5장을 따릅니다.

## 5. 제목·본문 초안

초안만 작성하며, 이 시점에 밖으로 나가는 것은 없습니다.

- **제목**: `[<TICKET>] <사실 요약>`. 브랜치명이 티켓 ID면 그것을 쓰고, 없으면 4절에서 확인한 관례를 따름
- **문체**: 이 스킬은 절 구성과 절별 정보량만 정함. 문장 종결은 세션에 작성 규약이 주입돼 있으면 그것을 따르고, 없으면 불릿을 명사형으로 종결함
- **관례 비참조**: 문체를 저장소의 기존 PR 본문에서 가져오지 않음. 이 스킬이 쓴 PR이 관례로 읽히면 어긋난 문체가 굳음

```markdown
## 개요
- **배경**: <이 변경 없이는 무엇이 안 되거나 잘못되는지. 한 문장>
- **변경**: <그래서 무엇을 했는지, 결론만. 한 문장>

## 작업 내역
- **<합의 단위 또는 영역>**: <바뀐 결과. 한 줄>

## 영향도
- **<영향 대상>**: <바뀐 사실>로 <달라지는 동작>. <병합 전 확인이 필요하면 별도 문장으로>

## 검증 결과
- **<검증명>**: <실행한 결과. 한 줄>

## 연결
- **<형제 PR 또는 순서>**: <링크, 아직 없으면 레포와 브랜치명> · <머지·배포 순서>
```

### 절마다 담는 것

- **개요**: 배경은 계획의 `의도`에서, 변경은 결론만 각 한 문장으로 적음
- **작업 내역**: 계획의 `합의` 단위마다 한 줄로 바뀐 결과를 적음. 계획 없이 한 작업은 파일이나 영역 단위로 적음
- **영향도**: diff에서 도출한, 기존 동작·소비처·데이터·설정 가운데 달라지는 것과 병합 전에 확인할 것을 적음. 달라지는 것이 없으면 `- 기존 동작에 영향 없음` 한 줄만 적음
- **검증 결과**: 계획의 `검증` 명령을 실제로 실행한 결과를 적음. 이 세션에서 실행한 결과가 없으면 실행해서 얻고, 실행하지 못한 검증은 결과로 적지 않고 7절 보고에 남김
- **연결**: 계획의 `연결`에 내용이 있을 때만 두고, 형제 PR(만들어진 것은 링크, 아직 없는 것은 레포와 브랜치명)과 머지·배포 순서를 적음. 무관한 이슈의 PR에는 두지 않음

### 공통 원칙

- **확인한 사실만**: 계획과 diff, 실행 결과에 있는 사실만 적음. 확정하지 못한 것은 단정하지 않고 확인할 대상으로 적음
- **한 절에만**: 같은 사실을 두 절에 적지 않음
- **판단을 바꾸는 것만**: 리뷰어의 판단을 바꾸지 않는 내용은 뺌

## 6. 승인 1회

대상 좌표, `from → to`, 리뷰어, 제목, 본문 전문을 보여주고 `pr-protocol.md`의 게이트로 한 번 묻습니다. 2절에서 배경을 사용자에게 받았으면 개요가 그 답변에서 나왔음을 밝힙니다.

## 7. push·생성·확인

- **승인 시**: `host.md` 6장대로 push하고 PR을 생성한 뒤, 다시 조회해 베이스·소스 브랜치·리뷰어를 확인하고 PR URL을 보고함. 대상 저장소는 3절의 원본 저장소, 베이스는 확정한 베이스 브랜치, 리뷰어는 4절의 결과임
- **거절 시**: 아무것도 push되지 않고 PR도 없음을 그대로 보고함
- **핸드오프**: 마지막 한 줄 `리뷰: /<플러그인>:review 실행`. `<플러그인>`은 이 스킬을 부른 이름의 콜론 앞부분임
