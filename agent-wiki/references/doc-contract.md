# 위키 문서 규약

위키 문서는 코드를 계획·구현·리뷰하는 에이전트가 작업 전에 읽는 현행 사실입니다. 에이전트는 세션 주입이 알려 준 문서 색인의 `이름 — description`으로 열 문서를 고르고, 색인에서 못 찾으면 본문을 grep합니다. 문서를 새로 쓰거나 고치는 모든 경로가 이 규약을 따릅니다.

## 1. 담는 사실

문장마다 적용 대상, 앞으로도 지켜야 하는 내용, 그것을 뒷받침하는 근거를 확인한다.

- 규격이나 결정권자의 확정된 결정에 누가 어떤 조건에서 무엇을 보장해야 하는지 명시돼 있으면 필수 정책·계약으로 기록한다. 특정 어드민의 권한별 노출처럼 적용 대상이 하나인 정책도 포함한다. 외부 API에서 거부할 값이 정해졌어도 내부 함수까지 그 값을 거부해야 한다고 확대하지 않는다.
- 해당 레포에서 같은 작업을 할 다음 담당자의 행동을 바꾸며 코드·설정·테스트만으로 알기 어려운 개발 지식을 기록한다. 예를 들어 빌드 전에 Jenkins에 특정 Node 버전을 설치해야 하는 제약과 그 이유가 해당한다.
- API·DB·메시지의 값이나 예외가 코드에 보인다는 사실만으로 보장할 동작이라고 판단하지 않는다. 현재 동작과 유효한 정책이 어긋나면 적용 범위와 후속 결정을 확인해 차이를 실행 결과에 보고한다. 코드에만 있는 편의 기능, 호출 순서·필드 목록, 일반적인 라이브러리 사용법은 문서에서 제외한다.
- 구현·배포 진행 상황, 일정, 미확정 계획과 일회성 검증 결과는 위키에 쓰지 않는다. 외부 규격은 이 도메인이 지킬 계약과 원문 위치·판본만 인용한다. 외부 시스템의 내부 계산 방식과 화면 시안·배치·단순 문구는 제외한다. 비밀값과 개인정보를 기록하지 않는다. 현재 레포 소관과 의존은 9장의 지도로 보내고, 서비스 간에 보장할 의무는 결정 시점에 공통 문서에 쓴다.

## 2. 위치와 이름

| 위치 | 경로 | 주입되는 세션 | 담는 사실 |
|---|---|---|---|
| 도메인 루트 | `knowledge/{domain}/{name}.md` | 도메인의 모든 레포 | 적용 대상이 분명한 필수 정책·계약 |
| 레포 폴더 | `knowledge/{domain}/{slug}/{name}.md` | 그 레포 | 코드만으로 알기 어려운 반복 가능한 개발 지식 |

한 자료에 정책과 구현 제약이 함께 있으면 문장을 나눈다. 미등록 외부 시스템과의 계약도 같은 기준으로 판정하고 적용 대상에 상대 시스템을 적는다.

- **폴더**: 두 위치 아래에 하위 폴더를 두지 않음 — 문서 색인이 한 단계만 읽음
- **파일명**: 주제를 나타내는 2~5단어 kebab-case 명사구(영문 소문자·숫자·하이픈), 레포 폴더 문서에는 레포명을 넣지 않음

## 3. 문서 단위와 description

- **한 주제**: 업무 주제 하나가 문서 한 장이며, 규칙·코드값·함정처럼 성격이 다른 사실은 문서를 나누지 않고 4장의 절로 가름
- **description**: 요약이 아니라 "어떤 작업을 할 때 여는가" 한 문장 — "때"로 끝내고 40자 목표·60자 상한, 이 문서에만 있는 업무 낱말 1개 이상, 다른 문서와 같은 문장 금지 (`주문 취소를 요청하거나 취소 사유·이력을 다룰 때`)
- **분할**: description 한 문장이 본문을 덮지 못하면 나눔 — "관리", "처리" 같은 범주어로 올려 여러 주제를 덮지 않음
- **병합**: 같은 주제이고 항상 함께 읽히는 두 문서는 하나로 합침
- **역커버리지**: 본문이 제목·description의 범위를 덮지 못하면 제목·description을 좁힘

## 4. 문서 모양

frontmatter는 `description` 하나만 두고, 첫 줄은 `# 제목`입니다. 절은 아래 이름과 순서를 쓰고 내용이 있는 절만 둡니다.

| 절 | 담는 사실 |
|---|---|
| `## 적용 대상` | 사실이 참인 레포·모듈·채널과 제외 범위 — 도메인 루트 문서는 필수 |
| `## 규칙` | 허용·금지·판정 기준, 레포 사이 의무, 같은 종류의 이후 작업이 따를 구현 방식 |
| `## 코드값` | 코드와 뜻의 표 — 상태 코드 포함 |
| `## 상태와 전이` | 전이 조건과 전이를 일으키는 주체 — 상태 코드 자체는 `## 코드값` 표 |
| `## 절차` | 순서가 있는 단계와 실패 시 분기 |
| `## 함정` | 버그처럼 보이는 정상 동작, 코드가 막지 않는 실수, 라이브러리·인프라 함정 |
| `## 외부 참조` | 외부 명세의 `리소스`·`접근 방법`·`참조 시점` 표와 명세 자체의 오류 |
| `## 결정` | 버린 대안과 버린 이유 |

- **하위 절**: 한 절 안에서 같은 축(레포·채널·상태 묶음)의 불릿이 4개 이상이면 `###`로 묶음
- **표**: 같은 술어를 반복하는 불릿이 3개 이상이면(코드와 뜻, 조건과 결과) 표로 바꿈
- **원본 줄**: `## 코드값` 표마다 바로 위에 `` 원본: `{정의 식별자}` — 일부 ``를 두고, 근거가 정의 전체(현행 규격의 전체 코드표 등)를 보여 준 경우만 `` 원본: `{정의 식별자}` 전 N종 ``으로 쓰며 표 행 수가 N — 에이전트가 표에 없는 값을 없는 값으로 판단해도 되는지 가름
- **집합 표기**: 닫힌 집합(enum·공통코드·상태·허용 채널처럼 원소가 정의된 값) 원소의 뜻을 말하는 사실은 개수와 무관하게 `## 코드값` 표로 씀 — 문장 속 나열은 원본 줄을 붙일 자리가 없음, 규칙 문장이 조건·결과로 인용하는 코드는 표로 옮기지 않고 5장 식별자 병기로 씀
- **뜻 미확인**: 해당 표의 근거 원문에서 뜻을 확인하지 못한 원소는 뜻 칸을 `뜻 미확인`으로 둠 — 행을 빼면 표가 일부가 됨
- **정책 출처**: 정책 문장이나 같은 출처를 쓰는 표 곁에 규격의 원문·판본 또는 결정 기록의 위치를 붙인다. 대화에서 확정했으면 확인한 날짜와 결정 내용을 식별할 수 있게 쓴다. 변경 이력은 8장의 커밋으로 추적한다.

도메인 루트 문서 예시 (`knowledge/example-shop/order-cancel-reason.md`)

```markdown
---
description: 주문 취소를 요청하거나 취소 사유·이력을 다룰 때
---

# 주문 취소 사유

## 적용 대상

- 사유를 보내는 shop-admin, 검증·저장하는 shop-api, 취소 이력을 적재하는 shop-worker

## 규칙

- 주문 취소 요청(단건·일괄)의 취소 사유 코드(cancelReasonCd)는 CR 공통코드 문자열이며, shop-api가 요청 단계에서 미등록 코드를 거부함
- shop-admin은 운영자 취소 사유 코드 CR01을 항상 보냄 — shop-api는 기본값을 채우지 않아 빠지면 이력의 사유 코드가 빔
- 환불 금액은 사유 코드로 산정함 — 사유명은 운영자 언어와 입력 문구에 따라 달라짐

정책 출처는 주문 취소 규격 v2의 ‘취소 요청과 이력’ 절이다.

## 코드값

원본: 공통코드 `CR` — 일부

| 코드 | 뜻 | 환불 |
|---|---|---|
| `CR01` | 운영자 취소 | 전액 |
| `CR02` | 구매자 변심 | 배송비 차감 |

## 함정

- 결제 만료로 자동 취소된 이력은 사유명·사유 코드가 모두 비어 있는 것이 정상 — 사람이 입력하는 사유가 없는 전이임
- 일괄 취소 요청에 배송이 시작된 주문이 섞이면 배치 전체가 롤백됨(의도된 동작) — 호출 측이 취소 가능한 주문만 골라 보냄
```

레포 폴더 문서 예시 (`knowledge/example-shop/shop-worker/jenkins-build.md`)

```markdown
---
description: 주문 워커의 Jenkins 빌드 노드를 준비할 때
---

# 주문 워커 Jenkins 빌드

## 함정

- 주문 워커를 빌드할 Jenkins 노드의 도구 목록에 Node 20을 먼저 설치함 — 이 레포에 배정된 노드는 빌드 중 외부 다운로드가 차단됨
```

## 5. 문장

- **판정 문장**: 불릿 하나에 사실 하나를 `조건이면 결과 — 이유` 순서로 씀 — 에이전트가 코드·diff와 대조해 참과 거짓을 가를 수 있게 조건과 값을 밝힘
- **이유 꼬리**: 이유는 ` — ` 뒤에 붙이고 "~때문에 ~함" 순서로 쓰지 않음 — 이유가 있어야 에이전트가 문서에 없는 경우를 판단함, "사용자 지시"·"팀 결정" 같은 출처는 이유가 아니므로 이유를 모르면 꼬리를 두지 않음
- **식별자 병기**: 업무 낱말 뒤 괄호에 코드 식별자(클래스·필드·코드값·API 경로)를 원형으로 적고, 업무 낱말이 없으면 원형만 씀 — grep과 diff 대조의 열쇠, 파일 경로는 쓰지 않음
- **레포 주어**: 레포 사이 사실은 행위하는 레포를 주어로 씀 (`shop-admin은 CR01을 항상 보냄`)
- **의도 표시**: 이상해 보이지만 정상인 동작은 `정상`·`의도된 동작`으로 밝힘 — 리뷰 에이전트가 수정 대상으로 오인하지 않게 함
- **모호 금지**: "적절히"·"일부"·"필요시"는 조건과 수치로 바꾸고, 정해지지 않은 것은 "아직 정해지지 않음"으로 씀
- **어미**: 음·함·됨 또는 명사구로 끝냄
- **길이**: 150자를 넘으면 사실이 둘 이상인지 확인해 나눔

## 6. 겹치는 사실

한 정책은 도메인 공통 문서 한 곳에 둔다. 프로젝트 문서에서 그 정책이 필요하면 상대 링크로 가리키고 해당 레포의 제약만 설명한다. 적용 대상별 예외가 확정된 경우에는 공통 문서에서 예외의 범위를 밝힌다.

## 7. 고칠 때

- **대조**: description과 핵심 식별자로 기존 문장과 적용 대상, 그 근거를 확인한다. 본문에 출처가 없으면 문장의 커밋 근거도 확인한다. 대상·조건이 다르면 별개의 사실로 다룬다.
- **정책 변경**: 같은 대상의 현행 규격이나 기존 결정을 대체하는 후속 결정이 확인되면 구현·배포 전에도 추가·교체·삭제한다. 파트너 규격은 해당 판본을 확인한다. 이미 확정된 결정에는 재승인을 요구하지 않는다.
- **코드와 차이**: 머지 순서, 코드 삭제, 테스트 기대값, 구현 의도만 설명하는 커밋은 정책 변경 근거가 될 수 없다. 후속 결정 없이 같은 경계의 코드가 정책을 위반하면 유효한 정책을 유지하고 코드를 고칠 대상으로 보고한다. 원문끼리 충돌하고 이번 작업에서 보장을 정해야 할 때만 미결 사항 하나를 결정권자에게 묻는다.
- **프로젝트 지식**: 반복되는 제약의 추가·변경·해소를 확인한 근거로 그 문장만 고친다. 내부 이름이나 호출 구조만 달라졌으면 편집하지 않는다.
- **집합 범위**: 정책의 코드값 표에는 규격·결정이 보장하는 원소만 담는다. 구현 enum의 증감으로 표의 행이나 완전성 표기를 바꾸지 않는다.
- **현재 값만**: 확인된 변경과 같은 범위에서 거짓이 된 문장만 함께 고친다.
- **description**: 사실을 더할 때는 고치지 않고, 주제의 뜻이 바뀔 때만 기존 트리거 낱말을 남겨 다시 씀
- **구조 변경**: 확정된 폐지·해소로 마지막 사실이 사라진 문서는 삭제한다. 그 밖의 문서 삭제·분할·병합·이름 변경은 따로 제안한다.

## 8. 커밋

문서 한 장을 커밋 한 개로 남깁니다.

```
docs({domain}): {knowledge/{domain} 기준 상대 경로} {요약}

{근거}
기존 {값} / 새 {값}
```

- **근거**: 원문을 다시 찾을 수 있는 값을 사실마다 한 줄로 둠 — 머지에서 찾은 정책은 결정 원문 위치와 `{slug}@{sha7}`, 레포 제약은 근거 위치, 자료는 파일 경로(등록 레포 파일은 `{slug}@{sha7} {경로}`)·페이지 URL·자료 제목처럼, 대화는 `사용자 확인 YYYY-MM-DD`이며 형식은 예시일 뿐 역추적되면 됨
- **교체 줄**: 기존 문장의 값을 바꾼 경우에만 둠

## 9. 레포 지도

레포 지도는 `registry.json`의 노드(`domains.{domain}.repos.{slug}`)와 `deps.json`의 간선 블록(`deps.{domain}/{slug}`)입니다. 세션 주입은 `summary`와 간선의 `to`로 만든 의존 표식을 싣고, `responsibilities`는 레포 책임 색인에 실립니다.

- **편집 주체**: register는 노드 7키 전체와 자기 간선 블록, update·add는 `responsibilities`·`hosts`·자기 레포 간선만 고침 — `stack`·`summary`·`remote`·`defaultBranch`·`status`는 레포 전수 조사가 필요한 값이라 register가 맡음
- **stack**: 언어·주 프레임워크만, 버전은 주 항목만 쓰고 빌드 도구·DB·개별 라이브러리 좌표는 넣지 않음 — 스택 식별용이며 의존 목록은 빌드 파일이 원본임
- **summary**: 이 레포가 맡는 일 한 줄 — 세션 주입에서 레포를 고르는 한 줄임
- **responsibilities**: 이 레포를 참고해야 할 작업 단위를 기능 단위 짧은 문장으로 쓰고 헬스체크·공통 설정·빈 스텁은 넣지 않음 — 색인에서 작업할 레포를 고르는 열쇠임
- **hosts**: `qa`·`stg`·`prod` 키에 이 레포 자신이 요청을 받는 호스트 리터럴만 쓰고, 호출하는 API·DB·브로커·캐시 주소는 넣지 않으며 못 찾은 환경은 키를 생략하고 서빙 호스트가 없으면 `{}` — 호출 주소는 간선이 맡음
- **간선**: 현재 레포의 코드·빌드·설정이 대상 레포의 API·메시지 토픽·테이블·라이브러리를 호출·구독·조회·의존하면 `{"to": "{domain}/{slug}", "desc": "대상의 무엇을 현재 레포 어디에서 쓰는지 한 줄"}`로 둠 — 대상이 현재 레포를 호출하는 역방향 흔적(CORS 허용 origin 등)과 README·주석·문서의 이름 언급은 해당하지 않고, 대상 레포 코드에서 실재를 확인함
- **변경 근거**: 추가·교체는 diff·자료·대화가 계기가 되고 코드에서 실재를 확인한 값만, 삭제는 기준 시점 코드에 사용처·기능이 남아 있지 않음을 확인한 경우만 함 — 자료만으로는 지도를 바꾸지 않으며, 확인하지 못하면 바꾸지 않고 보고함
- **교체**: 기존 책임 문장·`desc`는 새 코드에서 거짓일 때만 그 문장을 고치고, 표현만 다르면 두지 않음 — 지도 diff가 실제 변경만 보이게 함
- **커밋**: register는 `chore(register): {slug} → {domain}`, update·add는 실행마다 한 커밋 `docs(graph): {domain} 책임 N건 · 간선 M건 · 호스트 K건`이며 본문은 8장 근거 줄
