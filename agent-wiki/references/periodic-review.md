# 주제 점검과 정기 실행

update의 준비 단계에서 만든 위키 clone과 작업 폴더를 사용한다. 실제 실행은 준비 시 [게시 절차](publish.md) 1절 통과 후 `wiki-update/{domain}-{base 전체 SHA}` 브랜치를 만든다. 작업 중 기준 판본과 원문을 고정하고, 같은 도메인의 변경을 한 번에 제안한다.

## 수집

`--periodic`은 다섯 경로를 모두 선택한다. `--paths`는 `merges,decisions,wiki,code,docs` 중 일부를 선택한다. 직접 점검은 `--topic`만 넘긴다. 코드·문서 기본 분량은 각 1개이며 `--max-code`와 `--max-docs`로 조절한다. 기존 `--max-merges`와 시작점 처리도 쓸 수 있다.

```sh
python3 "{PLUGIN_ROOT}/scripts/collect_update_review.py" --wiki "{tmp}" --workspace "{workspace.root}" --domain "{domain}" --out "{work}" --config "{PLUGIN_ROOT}/config.json" --paths merges,decisions,wiki,code,docs --decision-feed "{work}/decision-feed.json"
```

결정을 포함하면 호출자가 제공한 운영 설정의 `decisionSources`에서 도메인별 이름과 조회 범위를 읽는다. 예를 들어 `{"decisionSources":{"shop":{"refund-board":"project = SHOP"}}}`은 shop에서 확인할 Jira 검색 범위다. 다른 운영 설정 파일은 `--config`로 넘긴다. 저장된 출처의 조회 범위를 바꿀 때는 새 이름과 최초 조회 기간을 지정한다. 등록되지 않은 출처를 임의로 정하지 않는다.

- 조회를 시작할 때 서비스의 판본이나 조회 종료 시각을 고정한다. `state/review/{domain}.json`의 `decisions:{출처}.through` 다음부터 종료점까지 변경된 기록을 호스트에서 직접 조회한다. Jira는 updated 조건에 맞는 이슈의 본문·댓글과 수정 이력을 페이지 끝까지 읽고, 규격 저장소는 지정한 브랜치·경로의 변경 판본을 읽는다. 동률 시각은 경계를 포함해 ID·판본으로 중복을 제거한다. 시각 커서의 조회는 시작 시각을 포함하고 고정한 종료 시각 직전까지다. 예를 들어 Jira에서는 등록한 JQL에 updated의 시작·종료 조건과 `ORDER BY updated ASC, key ASC`를 붙인다. Jira가 해석하는 시간대와 정밀도에 맞춰 양쪽 경계를 고정한다. 최초 조회는 최근 7일을 기본으로 하며 운영 범위가 지정됐으면 그 범위를 쓴다. 조회 기간을 결과에 적는다.
- 각 기록에 원문 위치·ID, 판본, 작성자·결정권자, 날짜·대상·조건을 판단할 수 있는 원문을 싣는다. 제안과 상태 변경도 조회에서 누락시키지 않고 추출 단계에서 판정한다. 인증·권한·페이지·원문 조회가 실패하면 해당 출처의 오류를 남긴다. 결정이 다른 문서를 인용하면 인용한 판본도 확인한다.
- 호스트 조회 결과는 아래 형태로 `{work}/decision-feed.json`에 쓴다. 성공한 응답의 `scope`는 등록한 실제 조회 범위와 같아야 한다. 최초 `from`은 null이다. 빈 결과는 범위 끝까지 읽은 경우에만 `records: []`로 쓴다. 실패한 출처는 `{"error":"실패한 조회와 원인"}`으로 쓴다. 모의 호스트는 같은 형식을 사용한다.

```json
{"refund-board":{"scope":"project = SHOP","from":null,"through":"2026-06-01T09:00:00Z","complete":true,"records":[
  {"id":"SHOP-17#42","revision":"댓글 수정 시각 또는 규격 판본","url":"원문 위치","text":"작성자, 적용 대상과 조건을 포함한 원문"}
]}}
```

수집기는 `review.json`의 `sources`에 원문 위치와 경로별 오류를, `proposed`에 검토 후 기록할 수 있는 위치를 쓴다. 오류 코드 1이면 해당 오류를 미확인으로 보고하고 성공한 경로는 계속 검토한다. 결과 파일 생성 자체가 실패하면 완료 처리하지 않는다. 머지 시작점 미설정은 기존 스킬 2절의 후보로 확정한 뒤 재수집한다. 자료 0건인 경로는 다른 경로의 종료 조건이 아니다.

## 근거 대조

| 출발점 | 읽을 원문과 찾을 대상 |
| --- | --- |
| 서비스 머지 | update 3·4절대로 각 묶음에서 결정·코드 관찰·지도 후보를 추출한다. 머지밖에 단서가 없는 새 주제에도 문서를 배정한다. |
| 결정 변경 | 이슈 상태·최신 시각으로 결정 여부를 추측하지 않는다. 권한과 대상, 이전 판본을 대체한다는 문구를 원문에서 확인한다. 해당되는 위키가 없으면 새 공통 문서도 후보에 넣는다. |
| 위키 변경 | 최초 7일, 이후 마지막으로 확인한 위키 판본 다음부터 기준 브랜치의 변경 전후 텍스트·제거된 경로·링크를 함께 읽는다. 편집자와 무관하게 결정 원문을 찾아 확인한다. |
| 코드 순회 | 선택된 등록 레포 파일의 진입점·계약·소비자에서 출발한다. 같은 기능의 테스트와 근거가 되는 규격·결정·운영 제약을 찾아서 위키와 대조한다. 새 머지나 위키가 없어도 진행한다. 정렬 같은 편의 기능과 내부 호출 순서는 정책에서 제외한다. |
| 문서 순회 | 선택된 문서 전체를 읽고 문장별 적용 범위, 연결된 결정·현재 코드·테스트와 함께 쓰는 문서를 확인한다. 구현이 사라진 경우에도 폐지 근거를 확인한다. |
| 직접 점검 | 검색된 파일은 시작점이다. 주제의 업무 용어·식별자를 좁혀 관련 문서와 원문을 찾고, 관련 레포의 현재 기본 브랜치 판본과 비교한다. 관련 문장만 다룬다. 후보를 특정하지 못하면 검색어·판본·미확인 범위를 보고한다. |

기능과 문서의 정기 순서는 독립이다. 관련 문서를 참고로 읽거나 제한 때문에 미검토 항목이 남으면 그 사실을 결과에 남긴다. 참조로만 읽은 파일, 직접 점검, 한 문장만 확인한 문서를 다음 정기 순회 위치로 기록하지 않는다.

모든 출발점에서 공통·프로젝트 문서의 description과 본문을 업무 용어, 식별자, 기존 값, 변경된 파일명으로 검색한다. 관련 문서의 역방향 링크와 앵커도 찾는다. 같은 이름이라도 대상·채널·조건을 원문에 맞춰 판정한다.

`{work}/checks.json`에 검토할 문장마다 문서 경로(신규 포함), 대상·조건, 주장과 기존·새 값, 근거의 원문 위치·판본, 확인할 코드 판본, 발견 경로를 적는다. 같은 판본의 같은 문서·주장·대상·조건·근거인 행만 한 번 검토하고 발견 경로를 합친다. 추가 근거, 다른 예외, 다른 코드 판본은 따로 대조한다. 같은 문서의 여러 판정은 한 번의 문서 검토에 함께 배정한다. 메모와 중복 키는 작업 폴더에만 둔다.

## 문서 편집과 독립 검토

정책·프로젝트 지식은 [문서 규약](doc-contract.md)과 [공통 반영 절차](apply.md) 0~5장에 따라 배정·반영·독립 검토한다. `facts.json`의 `input`은 실제 결정/규격·제약 원문, `check`는 선택한 서비스 판본이다. 머지 주장은 수집 마지막 머지 판본을 유지한다. 다른 경로에서 현행 판본도 확인했다면 두 판본을 구분한다. 같은 대상의 유효한 정책과 현재 구현이 다르면 정책과 코드값·근거를 결과에 남긴다. 위키에 배포 진행 상태를 쓰지 않는다.

문서 정리가 있으면 같은 작업에서 함께 읽는지 확인하고 관련 파일을 한 묶음으로 편집한다. 파일별 병렬 편집과 같은 파일에 동시에 쓰지 않는다.

1. 각 옛 문장을 유지·추가·교체·이동·삭제·미확인으로 판정한다. 폐지 결정 없이 정책을 지우지 않는다. 코드 전사와 일회성 기록을 삭제할 때에는 어떤 코드·기록을 그대로 옮겼는지 기록한다.
2. 중복 정책은 공통 원문과 출처를 확인한 뒤 사본만 상대 링크로 바꾼다. 문서를 합칠 때 이동할 고유 제약과 예외, 출처, 옛 경로·앵커에서 새 경로·앵커로의 대응을 기록하고, 도메인 밖을 포함해 위키의 기존 참조를 함께 수정한다. 문서 이름만 같은 별도 적용 대상은 유지한다.
3. 반영자가 아닌 검토자에게 묶음의 변경 전 원문, 실제 변경 후 문서 전체, diff, 결정·코드 판본과 모든 참조를 넘긴다. 기존 문구와 배치가 이미 정확한 문서는 그대로 둔다. 참고로 읽은 문서에서 별개 주제를 발견하면 결과에 참고 사항으로 남긴다. 이번 배정과 관계없는 편집은 그 편집만 되돌린다. 고유 사실·출처와 유효한 예외가 남는지, 변경한 링크·앵커가 실제로 열리는지 확인한다. 한 근거로 묶인 이동·삭제·참조 수정이 일부라도 실패하면 그 묶음 전체를 되돌리고 이유를 보고한다. 다른 독립 변경은 보존한다.
4. 원문 충돌·조회 실패·미확인 범위와 완료한 검토를 구분한다. `{work}/pr.md`에는 유지·제외·병합의 이유, 관련 경로 및 근거를 사실 행에 넣는다. 지도 후보는 기존 apply 6장을 사용한다.

## 진행 위치와 게시

확정 변경을 독립 검토한 뒤, 결과를 모두 확인한 범위의 `proposed` 키만 골라 같은 임시 clone에 적용한다. 한 출처라도 조회·원문 확인이 덜 된 범위의 키는 빼고 사유를 남긴다. 충돌과 미확인은 각각 두 값이 실제로 어긋난 경우와 한쪽을 입증할 수 없는 경우로 보고한다. 경로별 미확인 항목도 통합 결과에 남기며, 다른 문서 판정이 성공해도 미확인 경로의 커서를 전진시키지 않는다. 정상적으로 결과가 없거나 코드 편의 기능으로 제외한 범위는 진행할 수 있다.

```sh
python3 "{PLUGIN_ROOT}/scripts/collect_update_review.py" --wiki "{tmp}" --domain "{domain}" --out "{work}" --finalize "{완료한 키를 쉼표로 나열}"
```

기록할 키가 없으면 호출을 생략한다. 직접 점검에서는 모든 키가 비고, 문서만 순회하면 `docs`만 가능하다. 최종 위치는 기준 브랜치에 반영된 커서다. dry-run은 결과·변경 문서·제안 위치와 PR 초안을 남기고 커밋·push·게시하지 않는다. 실제 실행은 바뀐 문서·지도와 진행 위치를 같은 브랜치 하나에 커밋한다. 내용이 같은 범위를 재검토해 diff가 없으면 게시하지 않는다. 정상 점검으로 다음 범위가 달라진 경우에는 위치만 바뀐 점을 PR에 표시한다. [게시 절차](publish.md)에서 열린 PR과 기준 브랜치의 판본을 다시 확인한다.

비교 시 개별 실행은 각 경로마다 동일 기준 사본에서 시작한다. 통합은 한 사본에서 같은 예산·같은 원문까지 처리한다. 실제 산출물에서 고유 문서·원문 판본, 중복 문장 검토, 준비·수집·모델·게시 호출, 경과 시간, 제공되는 토큰 사용량과 양쪽만 찾은 사실·충돌을 센다. 측정할 수 없는 값과 모의 호스트 호출은 따로 밝힌다.
