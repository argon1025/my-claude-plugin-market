# auto-flow-planning-loop 계획 루프 스킬 3종

## 의도

호출자가 이전 대화나 스킬 호출을 재현하지 않고도 계획 작성, 한 저장소의 기술 검토, 전체 계획의 독립 검증을 각각 시작할 수 있어야 한다. 단순 문구 수정과 여러 저장소의 정책 변경에서 각 담당자가 무엇을 근거로 다음 작업을 시작하거나 보류할지 판정하면 된다.

## 확인한 사실

- `AUTO-FLOW.md`의 ‘계획 작성과 검토 루프’와 1B는 원래 요청을 보존한 Jira 이슈 본문 하나를 계획의 기준으로 삼고, 변경된 완료 조건은 영향받는 담당 영역 검토와 독립 검증을 다시 거치도록 정한다.
- 개인판과 사내판 체크아웃을 대조했다. `plan-workflow/skills/planning/SKILL.md`와 `pr-workflow/skills/review/SKILL.md`는 각각 사내판과 내용이 같다. 기록 경로는 `plan-workflow/config.json`, PR 호스트별 절차는 `pr-workflow/references/host.md`에서 다르다. 두 환경은 같은 `references/runtime.md`에서 Claude Code와 Codex의 경로·호출 방식을 찾는다.

## 합의

### 1B의 책임과 범위

- 바꾸는 것 — 신규 플러그인에 계획 작성·조정, 담당 영역 검토, 독립 계획 검증을 분리한다. 기존 개발 흐름 플러그인을 유지한다.
- 모양 — 계획 작성은 원래 요청과 정책·답변을 출처로 Jira 본문 한 곳에 목표, 조건별 실행·검증 담당, 의존 관계와 검증 방법을 갱신하고 끝난다. 영역 검토는 현재 조건과 코드 판본을 대조하여 실행 가능성, 실제 경로·소비자와 계약 충돌, 추가 조사 대상을 반환한다. 독립 검증은 원래 요청부터 조건별 검증 방법까지 대조하여 착수 가능한 범위와 보완이 필요한 조건·이유를 반환한다.
- 이유 — `AUTO-FLOW.md`와 사용자 요청에서 각 책임을 따로 호출하거나 필요한 부분만 다시 맡길 수 있어야 한다고 정했다.
- 적용 범위 — 질문의 영향을 받는 담당자만 다시 참여한다. 정책 경계 안의 구현 방식은 담당자가 정한다. 세 스킬 본문과 호출 설명에는 PM이나 봇을 언급하지 않는다. 호출·배정·재참여는 스킬 외부에서 조정하고, 도구 사용법은 환경별 지침에서 다룬다. 의미가 달라진 완료 조건은 관련 영역 검토와 독립 검증 대상으로 남기며, 무관한 조건의 근거는 재사용한다.

## 검증

- 단순 문구 수정과 여러 레포의 정책 변경을 각각 대입해 세 책임의 시작 근거, 종료 지점, 인계 결과, 보류·재실행 대상을 대조한다.
- `python3 -m unittest discover -s tests`로 패키지 계약을, `python3 tests/check_codex.py`로 임시 설치본에서 스킬이 발견되는지 확인한다. 이와 별도로 선행 호출 이력을 주지 않고 스킬별로 직접 실행해 실제 반환 결과를 확인한다.
- 보급형 모델에서도 같은 결과를 내는지 `gpt-6.2-sol`의 낮은 추론 설정으로 세 스킬을 각각 직접 호출한다. 각 실행에는 해당 스킬과 패키지 참조, 모의 이슈와 코드만 전달한다.

### 모의 실행 결과

[모의 입력](eval-inputs.json)에는 원래 요청과 코드 사본이 들어 있다. 각 실행에서는 대상 스킬 하나와 그 참조만 복사했다. `source`의 본문을 기준으로 계획을 작성하고, 조정에는 `previous_plan`, 두 검토에는 `review_plan`을 현재 계획으로 제공했다. 호출 간 대화나 기대 판정은 제공하지 않았다.

| 모의 요청 | 최종 스킬을 gpt-6.2-sol, 낮은 추론 설정으로 직접 실행해 확인한 결과 |
| --- | --- |
| 회원 목록 문구 수정, 검토된 PR까지 전달 | 계획에는 회원 문구와 주문 기존 문구, 최신 PR 검토를 연결했다. 영역 검토는 두 빈 상태 함수가 같은 상수를 참조한다는 코드 위치를 찾았다. 독립 검증은 두 실제 진입점을 대조하면 주문 회귀도 판별할 수 있다고 판단했다. |
| 파트너 채널 B 허용, 포털에서 보낸 값의 실제 API 수락 확인 | 계획에서 portal·edge의 변경과 sink 계약을 구분했다. 영역 검토는 두 경계가 현재 B를 거부하고 portal 사본에는 실제 전송 호출자가 없음을 확인했다. 독립 검증은 제공된 검토용 계획에서 일반 채널의 portal 조건 누락과 파트너 채널의 모의 화면·별도 API 호출이 같은 요청임을 입증할 수 없는 점을 찾았다. edge 자체 검증은 진행할 수 있다고 판단했다. |
| 정책 결정 대기와 저장 응답 유실 | `pending_plan`과 미확정 정책을 주자 파트너 B 변경만 결정권자 답변에 연결하고 기존 조건의 검증 준비를 분리했다. 이미 저장된 회원 목록 계획의 재호출에서는 JSON 파일이 바이트 단위로 같았다. |

초기 실행에서 새 입력도 기존 입력의 상태 코드를 내야 한다는 조건을 추가한 사례가 있었다. 입력별 결정 출처와 실제 관찰값을 분리하는 예시를 스킬에 추가한 뒤, 새 세션의 Sol은 파트너 B의 기준을 ‘수락’으로 두고 실제 응답 코드는 실행 증거로 남겼다. 두 저장 결과에서 이슈 원문과 `description` 이외 필드가 그대로이고 현재 계획이 하나인지 별도로 확인했다.

Sol이 작성한 정책 변경 계획을 새 Sol 세션에서 검증했다. 초안에는 일반 A의 portal 전송과 edge 응답이 같은 요청인지 확인하는 방법이 빠져 있었다. 검증 결과와 기존 이슈만 건넨 별도 실행에서 계획 작성 스킬이 C3에 일반 A를 추가했다. 실제 API의 경로·환경, 같은 요청을 식별할 정보, 파트너 B의 수락을 관찰할 근거는 관련 검증의 미결사항으로 남겼다.

패키지 테스트 14개와 세 스킬의 형식 검사가 통과했다. Codex CLI 0.171.0 임시 설치에서 전체 12개 스킬 중 신규 3개를 확인했다. Claude의 플러그인·마켓플레이스 검증도 통과했고 디렉터리 제출용 아이콘 누락 경고가 있었다. Jira 쓰기는 로컬 사본으로 모의했다.
