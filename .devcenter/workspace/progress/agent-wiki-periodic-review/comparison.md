# 위키 정기 점검 dry-run 비교

개별 실행과 통합 실행은 같은 계약, 운영 제약과 정책·구현 불일치를 찾았다. 통합 실행은 기존 문서를 6회, 근거를 7회 덜 읽었다. 모의 위키에는 두 방식 모두 문서 9개가 남았다. [통합 PR 초안](dry-run/pr.md) · [실제 변경 패치](dry-run/combined.patch) · [경로별 측정값과 근거 ID](dry-run/measurements.json)

## 입력과 결과

등록 서비스 3개, 기존 위키 문서 8개, 미처리 서비스 머지 1건, Jira 모의 원문 3건(제안·결정·상태 변경), 위키 변경 1건으로 시작했다. 각 실행은 같은 기준 브랜치의 독립 clone에서 시작했다. 코드 시작점 1개, 문서 시작점 5개, 기존 머지 예산 10개를 사용했다. 실제 선택한 서비스 머지는 1건이었다. [입력 생성기](../../../../tests/wiki_review_fixture.py)

## 비용

문서와 근거 수는 작성 단계가 대조한 기존 본문과 사실 근거의 판본을 고유 ID로 셌다. 파일 목록·도구 지침·PR 메타데이터·작성한 문서는 제외했다. 근거 17개는 서비스 파일 12개, Jira 기록 3개, 서비스와 위키의 diff 각 1개다. 개발 도구 호출과 토큰에는 독립 검토자의 재확인 비용도 포함했다.

| 같은 입력, 1회 측정 | 개별 5회 합계 | 통합 1회 |
| --- | ---: | ---: |
| 기존 문서 고유 / 각 실행 내 고유 수의 합 | 8 / 14 | 8 / 8 |
| 근거 판본 고유 / 각 실행 내 고유 수의 합 | 17 / 24 | 17 / 17 |
| 작성 단계 문장 판정 행 | 26 | 19 |
| 같은 온라인 24시간 사본의 링크 교체 검토 | 2 | 1 |
| 위키 clone / 수집기 실행 | 5 / 5 | 1 / 1 |
| 모델 세션(작성 + 독립 검토) | 5 + 5 | 1 + 1 |
| 세션에서 완료한 셸 도구 호출 | 137 | 41 |
| clone과 수집 경과 시간 합계 | 1.75초 | 1.03초 |
| 작성과 독립 검토 경과 시간 합계 | 1,106.77초 | 415.02초 |
| 입력 토큰(캐시 포함) | 2,640,316 | 674,607 |
| 그중 캐시 입력 토큰 | 2,153,600 | 559,104 |
| 출력 토큰 | 44,874 | 18,252 |
| 외부 PR 게시 호출 | 0 | 0 |

각 경로에서 수집기를 실제 실행한 후 Codex CLI의 별도 세션이 자료를 읽고 편집안을 작성했다. 새 세션이 변경 전후 문서·결정·코드를 다시 읽어 검토했다. 같은 주제의 문서는 묶어서 검토했다. 토큰은 CLI가 보고한 turn.completed.usage, 시간은 프로세스 시작부터 종료까지의 monotonic 경과 시간이다. 개별 시간은 작업량을 보려고 더한 값이며, 제한적으로 병렬 실행한 전체 실험의 벽시계 시간이 아니다. 내부 모델 API 요청 수와 사람 검토 시간은 측정하지 않았다. 실제 운영에서 문서별로 워커를 더 나누거나 Jira·Git 네트워크가 느리면 비용이 달라진다.

## 누락과 재실행

- 두 방식 모두 승인된 정책·제약, 서비스 지도 변경, 온라인 환불의 정책 8일 대 코드 3일 차이를 찾았다. 처음 통합 초안은 최종 송신 파일의 UTF-8 여부를 미확인 목록에서 빠뜨렸다. 문서 단독 초안은 같은 관찰을 불일치와 미확인에 중복 기록했다. 코드에는 행 수를 세는 함수만 있어 송신 인코딩을 검증할 수 없다. 독립 검토 후 양쪽에 미확인으로 남겼다.
- 독립 검토가 배정 범위 밖의 이미 유효한 공통 문장이나 별도 단말 예외까지 다시 쓰려고 한 편집은 제외했다. 병합 과정에서 생긴 한 줄짜리 하위 제목은 규약의 규칙·함정 절로 정리했다. 두 링크의 절 구분, 예외 원문과 고유 제약을 최종 개별 합집합과 통합 사본 양쪽에서 검사했다. 새 공통 문서의 영문 파일명은 실행별로 달랐다.
- 해당 서비스의 머지 커서를 HEAD로 둔 실행은 머지 0건이어도 결정·위키·코드·문서 후보를 반환했다. Git 조회 실패, 결정 조회 오류·불완전 페이지·기준 커서나 범위 불일치, 불완전한 PR 목록을 실패로 구분했다. 다른 성공 경로는 계속 검토했다.
- 회당 1개씩 두 번 순회해 코드는 archive-api/src/archive.py에서 batch-api/src/notice.py로, 문서는 batch-api/export-batch.md에서 batch-api/export-replay.md로 진행했다. 주제 직접 점검은 모든 위치를, 문서만 점검한 실행은 머지 커서를 바이트 단위로 보존했다.
- 열린 update PR은 기존 링크를 돌려준다. 이미 결정이 들어간 add·수동 PR도 게시 직전 최신 head의 대조 결과로 중복을 막는다. 모의 기준 브랜치에 실제 통합 패치를 커밋한 뒤 환불 주제를 새 세션에서 다시 읽었다. 코드 3일 차이는 다시 보고했으며 문서 변경은 0건, 게시 검사는 코드 10(게시할 변경 없음)으로 끝났다. 실험에서 원격 PR 생성은 실행하지 않았다.

## 운영 제안

평일 1회에 코드 시작점 1개와 문서 시작점 5개를 권한다. 이 분량에서 실제 머지 1건과 최근 변경을 함께 점검하는 데 약 7분이 들었다. 211문서 도메인은 회당 서로 다른 5개를 완료하면 약 43회에 한 바퀴가 돌아온다. 열린 PR이나 재시도 때문에 위치를 보존한 회차는 제외한 계산이다. 중요한 확정 결정은 그날 add로 제안할 수 있다. 기존 머지 예산은 별도로 조절하며, 10건을 꽉 채운 실행 시간은 이번에 측정하지 않았다.

## 재현

저장소 루트에서 빈 임시 경로에 입력을 만들고 보관한 통합 패치를 적용하면 문서, 삭제, 링크와 앵커를 다시 검사할 수 있다. 경로별 패치는 각각 변경 전 위키에 적용한다.

```sh
case_dir=$(mktemp -d)
python3 tests/wiki_review_fixture.py "$case_dir"
proposal="$PWD/.devcenter/workspace/progress/agent-wiki-periodic-review/dry-run/combined.patch"
git -C "$case_dir/wiki" apply "$proposal"
python3 tests/check_wiki_review_result.py "$case_dir/wiki"
python3 -m unittest discover -s tests
```
