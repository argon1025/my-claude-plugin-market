# 이슈 루프 플러그인 재구성

## 의도

plan-workflow와 pr-workflow는 사용자가 단계마다 스킬을 직접 호출하고 단계마다 승인을 받는 플러그인이다. auto-flow는 이슈 자동화를 목표로 0.5.0까지 만들었지만 사용자의 기대와 달라 처음부터 다시 기획한다.

만들려는 것은 책임을 위임받은 봇들이 승인 게이트를 최소화해 이슈를 끝까지 진행하는 루프이며, 같은 루프를 봇도 사용자도 실행할 수 있어야 한다. (사용자 확인 2026-11-25)

- **봇 구성**: 플러그인 사용자마다 다르다. 사용자가 직접 호출하는 경우, PM 봇과 백엔드·프론트 담당자 봇을 두는 경우, Teams 응대 봇과 PM 봇과 담당자 봇을 두는 경우가 모두 가능해야 한다.
- **최종 플러그인 구성**: 사용자는 최종적으로 위키 플러그인과 새 프로세스 플러그인을 쓴다. plan-workflow와 pr-workflow는 기존 사용자가 계속 쓸 수 있게 이번에는 지우지 않고 공존시키며, 사용자들에게 공지하고 완전히 대체된 뒤에 삭제한다. 새 플러그인은 두 플러그인을 쓰지 않는 상태에서 사용하도록 안내한다. 새 플러그인 자체는 이전 판(auto-flow 0.5.0 이하)과의 하위 호환을 고려하지 않는다.
- **위키**: 위키도 이 루프 위에서 지속적으로 갱신돼야 한다.

사용자가 제시한 루프는 다음과 같다. 누락된 단계가 있을 수 있다고 사용자가 밝혔다.

1. **이슈 생성**: Teams 문의, 다른 사람이 사용자에게 한 이슈 할당, 사용자의 직접 생성으로 이슈가 들어온다.
2. **이슈 검토**: 현재 상태, 변경 범위, 미결 사항을 검토해 계획을 계속 갱신한다. 사용자 본인이 확인할 결정과 다른 담당자(기획, 사업, 디자인)가 확인할 사항을 관리하고, 확인되면 이슈에 기록한다. 미결 사항이 없을 때 개발을 시작한다. 위키를 지속적으로 갱신한다. 검토는 여러 번 반복될 수 있다.
3. **이슈 해결**: 개발하고 완료를 이슈에 기록한 뒤 PR을 올린다.
4. **이슈 리뷰**: 코드 리뷰를 하고, 이 루프에서 AI가 실수한 부분이 있는지 점검한다.
5. **사용자 머지**: 사용자가 PR을 머지하면 이슈가 끝난다.

- **Teams 자동화**: 이슈 생성과 검토는 Teams로 자동화할 수 있지만 이것을 스킬로 만들지는 않는다. 봇으로 만들 수 있다. Teams 봇을 두면 미결 사항의 담당자에게 확인을 요청할 수도 있지만 이번 루프의 고려 대상이 아니다.
- **이슈 템플릿**: 루프를 추적·관리할 수 있는 이슈 템플릿이 필요하다.
- **집중할 범위**: 이슈 하나의 상태를 관리하면서 그 이슈를 해결하는 데 집중한다.
- **사람을 기다리는 지점**: 미결 사항에 대한 답, 계획을 세울 때의 질문, PR 머지 세 곳이다. 그 밖의 단계는 승인 없이 진행한다.
- **보편 스킬과 환경별 지침**: 스킬은 어디서든 쓸 수 있게 보편적으로 만든다. 회사인지 개인 프로젝트인지에 따라 달라지는 것(담당자를 어디서 찾는지, 미결 사항을 누구에게 어떻게 확인하는지)은 스킬에 넣지 않고 봇의 지침에 맡긴다. 미결 사항의 확인 방식은 나중에 정한다.
- **이슈 생성**: 나중에 이슈 생성을 추가할 수 있어야 한다. 이슈를 만들 때 확인할 사항을 어디서 찾는지는 환경마다 다르므로, 플러그인은 무엇을 채워서 이슈를 만들어야 하는지에 집중한다.
- **기존 스킬의 문제**: 스킬이 과도하게 쪼개져 있고, 이 루프에 맞는지 의심스러우며, 계획을 어떤 식으로 세워야 하는지에 대한 좋은 방향이 빠져 있다.

## 합의

### 이슈의 상태와 전이

- **바꾸는 것**: 이슈 하나의 진행을 다섯 상태로 관리한다. 이슈 생성은 다섯 상태에 들지 않으며 상태는 이슈가 만들어진 뒤부터 관리한다. 이슈는 `create-issue`로 만들거나 직접 만든다.
- **모양**:

  | 상태 | 하는 일 | 넘어가는 조건 |
  | --- | --- | --- |
  | 검토 | 계획을 세우고 미결 사항을 관리한다. 반복될 수 있다. | 미결 사항이 0건이고 검토 단계의 끝내는 조건을 채우면 해결로 |
  | 해결 | 계획대로 개발·검증하고 이슈에 기록한 뒤 PR을 올린다. | PR을 올리면 리뷰로 |
  | 리뷰 | 코드 리뷰와 AI 실수 점검을 반복한다. | 차단 지적이 있으면 해결로, 없으면 머지 대기로 |
  | 머지 대기 | 사용자의 머지를 기다린다. 사람이 실행할 것은 사용자의 반영을 기다린다. | 사용자가 머지하거나 반영을 알리면 완료로 |
  | 완료 | 이슈가 끝났다. | |

  해결이나 리뷰 중에 새로 결정할 것이 생기면 검토로 돌아간다. 미결 사항이 남아 있으면 해결은 동작하지 않는다.
  모든 요구가 이미 충족돼 바꿀 것이 없는 이슈는 근거와 함께 "변경 없이 끝낼지"를 미결 사항에 올리고, 그렇게 하라는 답이 오면 완료로 바꾼다. 일부 레포만 바꿀 것이 없으면 그 레포의 줄만 "변경 없음"으로 완료 처리한다.
- **이유**: 사용자가 제시한 루프의 단계를 그대로 옮겼다. 결정 대기를 별도 상태로 두는 안은 버렸다. 미결 사항 목록이 비었는지로 이미 구분되고 상태가 늘면 템플릿과 전이만 복잡해진다.
- **적용 범위**: 이슈 템플릿, 네 스킬.

### 레포가 여럿인 이슈의 상태

- **바꾸는 것**: 합의한 상태 모델에 레포가 여럿인 경우의 규칙을 더한다.
- **모양**: 검토는 이슈 전체에 하나이며 미결 사항이 하나라도 있으면 어느 레포도 새 구현을 시작하지 않는다. 해결부터는 레포마다 단계를 가지며 "레포별 계획"의 레포 절에 단계, 담당, 브랜치, PR 줄을 둔다. 이슈의 상태 줄은 가장 뒤처진 레포의 단계를 따르고 모든 레포가 완료되면 완료다. 앞 레포의 머지나 배포를 기다려야 하는 레포는 레포별 계획에 그 조건을 적고 조건이 채워질 때까지 해결을 시작하지 않는다. 레포가 하나인 이슈는 레포 절이 하나다. 미결 사항이 생겨 검토로 돌아가도 레포마다의 단계는 그대로 둔다. 미결 사항이 풀리면 계획이 바뀐 레포만 해결로 돌리고 나머지 레포는 있던 단계에서 이어 간다.
  상태 줄은 요약이며 실행자는 다음 순서로 할 일을 고른다. 미결 사항이 있으면 검토가 먼저다. 없으면 레포마다 그 단계에서 지금 할 수 있는 일을 하고, 한 레포가 순서 조건이나 머지를 기다린다고 다른 레포의 일을 멈추지 않는다. 계획이 바뀌어 레포를 해결로 돌릴 때는 끝난 작업 단위의 결과를 지우지 않고 더 할 일을 새 작업 단위로 더하며, 다시 확인할 완료 조건만 미실행으로 바꾼다. 이미 머지된 PR은 PR 줄에 남긴 채 새 PR을 더한다.
- **이유**: 이슈 전체가 한 단계로만 움직이면 앞 레포의 PR이 머지·배포된 뒤에야 뒤 레포가 이어 가는 이슈를 표현할 수 없다.
- **적용 범위**: 이슈 템플릿, 공통 문서, 해결·리뷰 단계 문서.

### 상태 줄과 라벨

- **바꾸는 것**: 루프가 다루는 이슈를 표시하고 나중에 찾을 수 있게 한다.
- **모양**: 본문 맨 위 "진행" 절의 첫 줄에 다섯 상태 중 하나를 적고(예: `상태: 리뷰`) 스킬은 이 줄로 현재 단계를 판단한다. 그 아래 줄에는 지금 누구의 무엇을 기다리는지를 적는다. 이슈에 템플릿을 처음 적용할 때 `auto-flow` 라벨을 붙인다. 완료된 이슈의 목록은 이 라벨과 상태 줄로 뽑고, 봇이 정기 실행에서 다룰 이슈를 고를 때도 같은 라벨을 쓴다.
- **이유**: 라벨 없이 본문의 절 제목을 검색해 찾는 안은 버렸다. 호스트의 본문 검색 방식에 기대게 되고, 루프가 다루는 이슈와 우연히 같은 낱말이 들어간 이슈를 가를 수 없다.
- **적용 범위**: 이슈 템플릿, 공통 문서.

### 이슈 본문의 구성과 두 수준의 계획

- **바꾸는 것**: 계획과 진행을 `plan.md`가 아니라 이슈 본문에 기록하고, 계획을 이슈 전체 계획과 레포별 계획 두 수준으로 나눈다. 본문만 읽고 진행 상황, 담당, 지금까지의 일, 세부 계획을 알 수 있어야 한다.
- **모양**: 이슈 본문은 아래 열 절을 이 순서로 둔다.

  | 절 | 담는 것 | 채우는 쪽 |
  | --- | --- | --- |
  | 진행 | 상태 한 줄(`상태: 검토`)과 기다리는 것 한 줄(`{누구} — {무엇}`). 레포마다의 단계는 레포별 계획에 둔다. | 모든 단계 |
  | 요청 | 요청자와 요청일, 요청이 온 곳, 관계자, 원하는 결과(번호를 붙임), 하지 않을 것, 배경, 기한, 요청자가 본 원인과 해결 방법, 참고 자료. 원문은 붙이지 않는다. | 이슈를 만들 때 |
  | 미결 사항 | 항목마다 질문, 답할 사람, 막힌 것. 답이 오면 지우므로 항목이 없으면 미결 0건이다. | 모든 단계 |
  | 완료 조건 | 항목마다 조건 문장, 나온 곳, 확인 방법, 확인할 레포, 결과. 확인 방법은 실행자가 머지 전에, 사람이 머지 전에, 머지 뒤에 가운데 하나다. | 이슈 전체 계획, 결과는 해결 |
  | 관련 정책 | 표(번호, 정책, 출처, 새 정책, 위키 반영) | 이슈 전체 계획과 레포별 계획, 리뷰 |
  | 결정 | 번호를 붙인 결정 항목(맥락, 대안, 이유, 정한 사람) | 이슈 전체 계획과 레포별 계획 |
  | 레포별 계획 | 레포마다 단계, 담당, 브랜치, PR, 사람이 실행할 것, 기준 커밋, 순서 조건, 현재 동작, 검증 환경, 범위 밖에서 본 것과 작업 단위(바꿀 내용, 검증, 결과) | 레포별 계획, 결과는 해결 |
  | 리뷰 기록 | 지적마다 번호, 열림·닫힘, 회차, 레포, 리뷰한 커밋, 등급, 지적과 위치, 해결 쪽 답, 다음 회차의 확인 | 리뷰와 해결 |
  | 에이전트 개선 피드백 | 표(구분, 처음 판단, 바로잡은 내용, 발견한 곳) | 모든 단계 |
  | 이력 | 본문을 바꾼 실행마다 한 줄(날짜와 시각, 스킬, 실행자, 한 일) | 모든 단계 |

  같은 사실은 한 절에만 적고 다른 절에서는 번호(요청 n, Q-n, AC-n, P-n, D-n, U-n, R-n)로 가리킨다. 실행자가 확인한 완료 조건의 결과는 작업 단위 번호만 적고 명령과 출력은 작업 단위에 둔다. 나중에 다른 실행자가 채우는 항목(미결 사항, 완료 조건, 작업 단위, 리뷰 기록)은 표가 아니라 목록으로 쓰고, 표로 남는 관련 정책과 에이전트 개선 피드백은 빈 칸을 `-`로 채운다.
  이슈 전체 계획은 이슈 전체를 담당(PM 봇 또는 직접 쓰는 사용자)이, 레포별 계획은 레포를 담당(담당자 봇 또는 같은 사용자)이 쓴다. 스킬 문서는 봇 이름 대신 "이슈 전체 계획"과 "레포별 계획"으로 적는다.
- **이유**: 사용자가 참고로 든 강의 정리의 스펙(무엇을)·ADR(왜)·플랜(어떤 순서와 조건으로) 구분을 따랐다. 구현 뒤에 사용자가 템플릿을 정리하도록 했다. 맨 위의 레포별 표를 없애 레포의 상태와 계획을 한 곳에 두고, 요청 원문을 붙이지 않으며, 절 사이의 중복을 없애고, 쉬운 낱말로 쓴다. 개정안은 Opus 에이전트가 가상 실행의 실제 본문과 대조해 검토했고 수용 판단은 사용자가 맡겼다(위임). 받아들인 것은 다음과 같다. 상태 한 줄만으로는 누구를 기다리는지 보이지 않아 "기다리는 것" 줄을 두고 단계 뒤의 대기 괄호를 없앴다(가상 실행 사례 D에서 상태는 해결인데 실제로는 사람을 기다렸다). 다른 실행자가 나중에 채우는 표가 Jira에서 깨졌으므로 목록으로 바꿨다(가상 실행 사례 C와 D). 완료 조건의 근거를 가리킬 수 있게 요청의 원하는 결과에 번호를 붙였다. 본문만으로 지난 실행 뒤의 변화를 판단할 수 있게 이력을 뒀다. "스펙"과 "인수 조건"은 "완료 조건"으로, "맡은 쪽"은 "담당"으로, "PR 없는 산출물"은 "사람이 실행할 것"으로 바꿨다.
- **적용 범위**: 이슈 템플릿, 공통 문서, 검토·해결·리뷰 단계 문서, `create-issue`.

### 결정 절과 관련 정책 절

- **바꾸는 것**: 이슈 본문의 "관련 정책" 절에 이 이슈가 기대거나 건드리는 정책을 모두 적고, 이 이슈로 바뀌는 것만 새 정책을 채운다. "결정" 절에는 이유만 남긴다.
- **모양**: 결정 항목은 번호를 붙이고 맥락(왜 정해야 했는가), 대안(검토한 선택지), 이유, 정한 사람(이름과 날짜, 에이전트가 정했으면 "에이전트")을 적는다. 관련 정책은 아래 표다.

  | 칸 | 적는 내용 |
  | --- | --- |
  | 번호 | P-1부터 |
  | 정책 | 문서에 적힌 지금의 정책 한 문장. 문서로 정해진 것이 없으면 "없음"으로 적고 지금의 동작은 레포의 현재 동작에 둔다. |
  | 출처 | 그 정책이 적힌 곳(위키 문서, 규격의 위치와 판본) |
  | 새 정책 | 이 이슈로 바뀌거나 새로 생기는 정책 한 문장과 그것을 정한 곳. 바뀌지 않으면 `-`, 답을 기다리면 `미정 (Q-n)` |
  | 위키 반영 | 새 정책을 위키에 적은 위치. 새 정책이 없는 줄과 위키가 없는 환경에서는 `-`, 적지 못했으면 `미반영: 사유` |

  적는 기준은 이 이슈의 변경이 어길 수 있거나 완료 조건과 결정이 기대는 정책이다. 화면 배치와 단순 문구, 이 이슈 안에서만 쓰는 구현 세부는 적지 않는다. 찾은 문서가 없어도 이 이슈로 생기는 정책은 줄을 만든다. 리뷰는 이 목록을 코드와 대조하고 빠진 정책을 찾으면 줄을 더한다. 리뷰의 위키 반영 누락 점검과 완료 시의 add는 새 정책이 있는 줄을 본다.
  에이전트가 정한 것은 다른 선택지가 실제로 있었고 그 선택이 다음 작업자나 다른 레포에 영향을 줄 때만 결정에 적고, 대안이 없던 단순한 배치는 작업 단위에만 적는다.
- **이유**: 정책의 전후를 결정 항목 안의 줄로 두는 안은 사용자의 제안으로 별도 절로 바꿨고, 바뀌는 정책만 적던 것도 사용자의 제안으로 관련 정책을 모두 적게 바꿨다. 조사해서 찾은 정책이 한곳에 보여야 이 이슈가 어떤 정책 위에 있는지 한 번에 확인할 수 있다. 같은 사실이 두 곳에 적히지 않도록 결정에는 이유만 두고 새 정책은 결정 번호를 가리킨다. 빈 칸은 "바뀌지 않음", "답 대기", "위키 없음", "아직 반영 안 함"으로 달리 읽혀 위키 반영 누락 점검을 틀리게 하므로 값을 정해 적는다. 완료 조건에 전후를 함께 적는 안은 버렸다. 완료 조건은 앞으로 참이어야 할 동작 한 가지만 적어야 검증과 일대일로 대응한다.
- **적용 범위**: 이슈 템플릿, 공통 문서, 검토·리뷰 단계 문서.

### 에이전트 개선 피드백

- **바꾸는 것**: 에이전트의 실수와 도중에 바뀐 결정을 나중에 절차와 지침을 고치는 데 쓸 수 있도록 이슈 본문에 남긴다.
- **모양**: 이슈 본문의 "에이전트 개선 피드백" 절에 드러난 즉시 그 단계를 수행하던 쪽이 한 줄씩 덧붙인다.

  | 칸 | 적는 내용 |
  | --- | --- |
  | 구분 | `에이전트 실수` 또는 `결정 변경`(사람이 앞서 정한 것을 바꿈). 에이전트 실수에는 무엇을 잘못했는지(문서를 확인 없이 믿음, 프레임워크 동작을 가정함, 영향 범위를 덜 찾음, 검증이나 환경을 가정함, 그 밖)를 함께 적는다. |
  | 처음 판단 | 틀렸던 가정이나 처음 정했던 결정 |
  | 바로잡은 내용 | 확인된 사실이나 바뀐 결정과 그 이유 |
  | 발견한 곳 | 검토, 해결, 리뷰, 사용자의 PR 확인 중 하나 |

  결정 절에는 지금 유효한 결정만 남기고 바뀌기 전 내용은 여기에 둔다. 실수를 남긴 쪽은 그 실수가 가리키는 본문의 문장(현재 동작, 계획, 결정)도 함께 고친다. 리뷰의 개선 등급 지적이나 기능 제안은 여기에 적지 않는다.
- **이유**: plan-workflow에서는 `feedback.md`의 `correction` 항목이 맡던 역할이며, plan-workflow 없이 쓰는 auto-flow에는 그 기록이 갈 곳이 없다. 처음 이름인 "에이전트 개선 피드백"은 무엇을 적는 곳인지 드러나지 않아 사용자의 제안으로 바꿨다. 결정 변경을 결정 항목 안으로 옮기자는 리뷰의 안은 받지 않았다. 사용자가 바뀐 결정도 개선의 재료로 모으기로 했다. 이슈 댓글에 표식을 붙여 남기는 안은 버렸다. 이슈 본문 하나로 상태를 관리하는 구성과 어긋나고 모아 볼 때 이슈마다 댓글 전체를 읽어야 한다.
- **적용 범위**: 이슈 템플릿, 검토·해결·리뷰 단계 문서.

### 공통 절차의 시작과 멈춤

- **바꾸는 것**: 네 스킬이 함께 따르는 공통 절차로, 이슈 하나를 받아 시작하고 사람을 기다리는 지점이나 맡은 단계의 끝에서 멈춘다.
- **모양**:
  1. 이슈 지정: 이슈 키나 URL을 받아야 시작한다. 없으면 묻는다. 봇은 자기 지침에 따라 이슈를 골라 하나씩 호출한다.
  2. 도구: 세션에 있는 이슈·PR 도구를 쓴다. 해당 호스트를 다룰 도구가 없으면 시작하지 않고 그 사실을 알린다.
  3. 템플릿이 없는 이슈: 기존 본문을 바탕으로 "요청" 절을 템플릿 항목에 맞춰 정리해 쓰고 본문을 템플릿으로 바꾼다. 원문은 본문에 남기지 않고 댓글 하나로 남긴 뒤 "요청이 온 곳"에 그 위치를 적는다. 라벨을 붙이고 상태를 검토로 둔다.
  4. 본문을 고칠 때: 저장 직전에 본문을 다시 읽고 이번 실행이 맡은 절만 바꾼다.
  5. 멈추는 곳: 미결 사항, 머지 대기, 스킬이 맡은 단계의 끝에서 멈춘다. 멈출 때 현재 상태, 기다리는 것, 다음에 할 일을 알린다.
  저장한 뒤에는 본문을 다시 읽어 자기 변경이 들어갔는지와 다른 실행자의 변경을 덮어쓰지 않았는지 확인하고, 덮어썼으면 되살려 다시 저장한다. 질문은 묻기 전에 미결 사항에 먼저 적으며 서로 무관한 질문은 한꺼번에 적는다. `run-issue`만 적은 뒤 세션에서 한 번에 하나씩 이어 묻고, 단계별 스킬은 적고 멈춘다. 답할 사람 칸에는 사람의 이름이나 역할, 계획을 다시 써야 풀리는 항목은 "검토 담당", 한 레포의 계획이 필요한 항목은 "{레포} 담당"을 적는다. 미결 사항 번호는 다시 쓰지 않는다. 스킬은 자기가 맡은 단계의 일이 없으면 어느 절도 고치지 않고 알린 뒤 멈춘다. 사람을 기다리는 일만 남았고 지난 실행 뒤로 새 댓글, PR 변화, 새 커밋이 없을 때도 아무것도 고치지 않고 멈추며 같은 검증을 다시 돌리지 않는다. 시작할 때는 미결 사항의 답과 함께, 사람이 확인하기로 한 완료 조건의 결과와 사람이 실행할 것을 반영했다는 알림이 왔는지도 찾는다.
- **이유**: 이슈를 지정하지 않으면 라벨이 붙은 이슈를 모두 순회하는 안은 버렸다. 이슈 하나에 집중하기로 했고 어떤 이슈를 고를지는 환경마다 달라 봇 지침의 몫이다. 원문을 본문에 인용으로 남기던 것은 사용자가 바꿨다. 본문에는 정리한 요청만 두어 읽기 쉽게 하고, 정리가 틀렸을 때 대조할 수 있도록 원문은 댓글로만 남긴다.
- **적용 범위**: 공통 문서, 이슈 템플릿.

### 머지 대기와 완료

- **바꾸는 것**: 리뷰를 통과한 레포의 PR을 사용자가 머지할 때까지 기다리고, 머지를 확인해 완료로 바꾼다.
- **모양**: 네 스킬 중 어느 것이 실행되든 공통 절차에서 그 레포의 PR 상태를 확인한다.

  | PR의 상태 | 하는 일 |
  | --- | --- |
  | 머지됨 | 그 레포의 PR 줄에 머지 커밋을 적고 그 레포의 단계를 완료로 바꾼다. |
  | 변경을 요구하는 새 코멘트가 있음 | 리뷰 기록에 열린 지적으로 옮겨 적고(출처에 코멘트 위치) 그 레포의 단계를 해결로 되돌린다. 계획을 바꾸는 요청이면 에이전트 개선 피드백에 `결정 변경`을 남기고 미결 사항에 올린다. 확인이나 단순 질문처럼 변경을 요구하지 않는 코멘트, 이미 옮긴 코멘트, 스킬이 남긴 `[auto-flow]` 코멘트는 건너뛴다. |
  | 리뷰를 통과한 뒤 PR에 새 커밋이 생김 | 그 레포의 단계를 리뷰로 되돌린다. 리뷰하지 않은 커밋이 이미 머지됐으면 완료로 바꾸되 그 사실을 리뷰 기록에 남긴다. |
  | 머지 없이 닫힘 | 멈추고 미결 사항에 남긴다. |
  | 사람이 실행할 것을 실행했다는 알림이 옴 | 그 레포의 "사람이 실행할 것" 줄에 알림의 위치를 적고, PR이 없거나 이미 머지됐으면 단계를 완료로 바꾼다. |
  | 변화 없음 | 아무것도 하지 않는다. |

  모든 레포가 완료되면 이슈의 상태 줄을 완료로 바꾼다. 스킬은 PR을 승인하거나 머지하지 않는다. Jira 워크플로 전환이나 GitHub 이슈 닫기 같은 호스트의 이슈 상태는 스킬이 바꾸지 않고 환경별 지침에 맡긴다.
  이 확인은 기록과 단계만 바꾸며 코멘트의 판정과 코드 반영은 해결 단계가 한다. 완료 처리는 완료 시의 위키 반영을 먼저 하고 그 뒤에 상태 줄을 완료로 바꾼다.
  머지 뒤에 확인하기로 한 완료 조건의 결과가 아직 없어도 모든 레포가 완료면 이슈를 완료로 바꾸되, "기다리는 것"에 `{확인할 사람} — AC-4 머지 뒤 확인`을 남긴다. 결과가 오면 그 조건의 결과를 채우고 그 항목을 지운다. 사람이 실행할 SQL이나 설정 변경은 리뷰를 통과하면 단계를 머지 대기로 두고 "기다리는 것"에 실행할 사람을 적으며, 실행했다고 알리면 완료로 바꾼다.
- **이유**: 호스트의 이슈 상태까지 스킬이 바꾸는 안은 버렸다. 전환 규칙이 프로젝트마다 다르고, 환경마다 다른 것은 스킬에 넣지 않기로 했다. 머지 뒤에도 Jira 이슈는 지침이나 사람이 전환하기 전까지 기존 상태로 남는다. 머지 뒤 확인이 끝날 때까지 완료를 미루는 안은 버렸다. 배포 일정에 따라 이슈가 머지 대기에 계속 남게 되며, 가상 실행(사례 A)에서는 확인이 남았다는 표시 없이 완료가 됐다. 사람이 실행할 것의 경로는 가상 실행(사례 C)에서 SQL만 있는 레포가 머지할 PR이 없어 완료로 가지 못한 데서 나왔다.
- **적용 범위**: 공통 문서, 리뷰 단계 문서.

### 검토 단계의 절차

- **바꾸는 것**: plan-workflow의 planning이 가진 계획 수립 지침을 루프의 검토 단계로 가져오고, 계획 전체에 대한 승인 질문은 두지 않는다.
- **모양**:

  | 묶음 | 하는 일 |
  | --- | --- |
  | 이슈 전체 계획 | 1. 본문·댓글에서 요구(원하는 결과, 업무 규칙, 완료 조건)만 출발점으로 삼는다. 원인 분석·수정 위치·구현 방법은 주장으로 두고 코드와 대조한다. 2. 완료 조건에 번호를 붙여 쓴다. 한 문장에 요구 하나를 "누가 어떤 조건에서 무엇을 해야 한다" 형태로 적고, 조건마다 성공과 실패를 가르는 확인 방법을 붙인다. 3. 완료 조건마다 맡을 레포와, 레포 사이에 주고받는 계약과 순서를 정한다. 값을 정의하는 쪽이 먼저다. |
  | 레포별 계획 | 4. 진입점에서 소비자까지 코드를 따라가 현재 동작을 위치와 함께 적는다. 이미 충족된 요구는 근거와 함께 제외한다. 5. 더 적은 코드로 되는 방법부터 검토한다(만들 필요 없음, 이미 있는 코드, 표준 라이브러리, 설치된 의존성, 최소 코드 순). 6. 작업 단위마다 바꿀 내용, 관련 완료 조건, 레포에서 실제로 확인한 검증 명령을 적고, 계획을 쓴 기준 커밋을 함께 적는다. 구현 코드를 미리 쓰지 않는다. |
  | 질문과 미결 사항 | 7. 정해지지 않은 정책과 값은 추정으로 채우지 않는다. 질문 대상은 한 번에 하나씩 묻는다. 8. 답할 사람이 그 자리에 있으면 바로 묻는다. 없으면(봇의 정기 실행, 다른 담당자의 결정) 미결 사항에 질문, 답할 사람, 걸린 완료 조건을 적고 멈춘다. 9. 답이 오면 결정 절에 적고, 영향받는 완료 조건과 레포별 계획을 고쳐 쓴다. |
  | 끝내는 조건 | 10. 미결 사항이 0건이고, 모든 완료 조건이 작업 단위에 대응하며, 모든 작업 단위에 검증이 있으면 상태를 해결로 바꾼다. |

  검토를 실행한 세션이 코드를 읽을 수 있는 레포의 계획까지 모두 쓴다. 읽을 수 없는 레포만 계획이 필요하다고 남기고 그 레포를 담당이 이어 쓴다.
  계획에 적기 전에 네 가지를 확인한다. 문서의 문장은 그것이 가리키는 코드를 열어 확인한다. 계획이 기대는 프레임워크 동작은 기존 사용례·테스트·실행으로 확인하고, 확인하지 못한 가정은 그렇게 적고 그 가정을 가르는 검증을 넣는다. 고치려는 코드를 쓰는 곳은 검색으로 전부 찾고, "사용처 없음"은 같은 검색이 아는 사용처를 찾아내는지 확인한 뒤 검색 범위와 함께 적는다. 검증 칸에는 지금 그 레포에서 실제로 실행해 본 명령만 적는다. 코드를 읽을 수 없는 레포는 미결 사항에 "{레포}의 레포별 계획 필요"를 올리고, 그 레포를 담당이 검토 단계를 자기 레포로 좁혀 수행해 채운다. 위키와 코드가 다르면 먼저 그 위키 문장의 출처를 확인해, 아직 구현 중인 확정된 결정이면 질문하지 않고 그 정책을 기준으로 계획한다.
  가상 실행에서 계획을 빠져나간 누락을 막기 위해 네 가지를 더한다. 완료 조건마다 그 조건이 만드는 상황(입력, 저장된 데이터, 응답)을 현재 경로에 넣어 끝까지 따라가고, 바꾸지 않는 코드가 그 상황에서 조건을 깨면 작업 단위에 넣는다. 검사하거나 조회하는 대상을 넓히거나 좁히는 변경이면 기존 규칙이 대상을 거르는 축(상태, 유형, 플랫폼 등)을 찾아 축마다 이번 범위에 드는지를 질문 대상으로 다룬다. 허용 범위나 판정 기준을 바꾸면 그 규칙을 설명하는 문구, 같은 기준을 쓰는 다른 레포의 정의, 이미 저장된 데이터 가운데 결과가 달라지는 대상을 검색해 적는다. PR로 올리지 않고 사람이 실행할 일이 있으면 그것을 쓸 레포와 실행할 사람을 정해 레포별 계획에 적는다.
- **이유**: 1·4·5·7번은 plan-workflow의 지침을 옮긴 것이고 2번의 문장 규칙은 강의 정리에서 가져왔다. 계획 전체 승인을 남기는 안은 버렸다. 사람을 기다리는 지점을 세 곳으로 합의했고 사용자가 판단할 결정은 7~8번에서 하나씩 묻는다. 담당자 봇이 각자 레포별 계획을 쓰는 안은 기본값으로 두지 않았다. 계획이 구현 직전에 쓰여 코드와 덜 어긋나지만 질문이 봇마다 흩어지고 레포 사이의 계약을 다시 맞추는 왕복이 생긴다.
- **적용 범위**: 검토 단계 문서. 여러 이슈를 분류하는 절차와 `plan.md` 스냅샷 커밋은 옮기지 않는다.

### 위임과 질문의 경계

- **바꾸는 것**: 계획을 세울 때 사용자에게 묻는 결정과 에이전트에게 위임하는 결정을 나눈다.
- **모양**:

  | 구분 | 대상 | 처리 |
  | --- | --- | --- |
  | 질문 | 밖에서 보이는 동작을 바꾸는 결정(값, 규칙, 응답과 오류, 화면 문구), 요청 대상이 아닌 기능이 함께 쓰는 코드를 고치는 일, 검증·가드를 약하게 하는 변경(실행자가 할 수 있는 확인을 사람의 확인이나 머지 뒤 확인으로 돌리는 것 포함), 요청과 코드·문서가 어긋나 어느 쪽이 맞는지 정해야 하는 경우 | 계획 수립 시 사용자에게 묻고 답을 받기 전에는 미결 사항으로 둔다. |
  | 위임 | 그 안에서의 구현 방식(어느 클래스와 메서드, 내부 구조) | 에이전트가 정하고 이슈의 결정 절에 위임으로 고른 것임과 이유를 남긴다. |

  위임한 부분은 세 가지로 잡는다. 레포별 계획의 현재 동작은 코드에서 확인한 위치와 함께 적고 문서의 주장만으로 적지 않는다. 구현 중 계획의 가정이 틀린 것으로 드러나면 계획을 고쳐 쓰고, 완료 조건이나 질문 대상에 닿으면 검토로 돌아간다. 리뷰의 AI 실수 점검은 기존 기록에서 반복된 네 오판 유형(문서를 확인 없이 믿음, 프레임워크 동작을 잘못 가정, 영향 범위를 잘못 잡음, 검증 명령과 환경을 잘못 가정)을 기준으로 이슈 기록과 실제 코드를 대조한다.
- **이유**: 구현 방식까지 모두 사용자에게 확인받는 안은 버렸다. 사람을 기다리는 지점이 다시 늘어나고, 기존 기록의 오판 사례는 그런 확인이 아니라 코드 대조와 리뷰에서 드러났다.
- **적용 범위**: 검토·해결·리뷰 단계 문서.

### 해결을 시작할 때의 대조와 중단

- **바꾸는 것**: 해결을 담당이 받은 계획을 그대로 믿지 않고 현재 코드와 대조하며, 어긋나면 멈춰서 검토로 되돌린다.
- **모양**: 해결을 시작할 때 기준 커밋 이후의 변경과 계획의 "현재 동작"이 지금도 참인지를 코드와 대조한다. 구현 방식 안에서 끝나는 차이면 레포별 계획을 고쳐 쓰고 진행한다. 완료 조건, 질문 대상, 레포 사이의 계약에 닿으면 구현을 멈추고, 미결 사항에 어긋난 점과 코드 근거를 적은 뒤 상태를 검토로 되돌린다. 구현 도중에 이상을 발견한 경우도 같은 규칙을 따른다. 계획이 틀렸던 경우에만 에이전트 개선 피드백에 `에이전트 실수` 한 줄을 남기고, 코드가 그사이 바뀐 것이면 오판으로 적지 않는다.
- **이유**: 검토 시점과 구현 시점의 코드가 다를 수 있고 계획이 잘못 쓰였을 수 있다. 멈춘 이유를 미결 사항에 두면 다음 검토 실행이 사람이든 봇이든 그 항목부터 이어받는다.
- **적용 범위**: 해결 단계 문서, 검토 단계 문서.

### 해결 단계의 절차

- **바꾸는 것**: plan-workflow의 execute와 pr-workflow의 create가 하던 구현과 PR 게시를 루프의 해결 단계로 가져오고, PR 게시 전의 승인은 두지 않는다.
- **모양**: 레포 하나를 단위로 수행한다.
  1. 시작 조건: 미결 사항이 0건이고 그 레포의 순서 조건이 채워졌을 때만 시작한다. 아니면 이유를 알리고 멈춘다.
  2. 시작 전 대조: 기준 커밋 이후의 변경과 계획의 현재 동작을 코드와 대조한다.
  3. 작업 단위: 단위 하나를 구현하고 그 단위의 검증을 실행한 뒤 커밋 하나를 남긴다. 주변 코드의 관례를 따르고 계획에 없는 동작이나 분기는 넣지 않는다.
  4. 검증 실패: 검증을 우회하거나 테스트를 건너뛰지 않는다. 자기 변경을 고쳐 다시 검증하고, 같은 실패의 원인을 좁히지 못하거나 계획대로는 통과시킬 수 없으면 멈춰서 미결 사항에 남긴다. 변경 전부터 깨져 있던 검증은 그 사실과 근거를 기록한다.
  5. 이슈 기록: 작업 단위의 결과에 커밋과 실행한 검증 명령·결과를, 완료 조건의 결과에 완료 조건별 확인 결과를 적는다. 실행하지 못한 확인은 미실행으로 적는다.
  6. PR 게시: 승인 없이 push하고 PR을 만든다. 대상은 원본 저장소의 베이스 브랜치이고 force-push는 하지 않는다. 본문에는 이슈 링크, 배경, 작업 내역, 영향도, 검증 결과, 다른 레포의 PR과 순서를 적는다.
  7. 끝: 브랜치 줄과 PR 줄을 채우고 그 레포의 단계를 리뷰로 바꾼다.
  시작 조건에는 그 레포의 작업 단위가 있어야 한다는 것이 더해진다. 순서 조건 가운데 앞 레포 PR의 머지처럼 직접 확인할 수 있는 것은 확인하고, 배포처럼 확인할 수 없는 것은 미결 사항에 올린다. 작업 브랜치에는 이 이슈의 커밋만 있어야 하고, 다시 시작할 때는 결과와 브랜치의 커밋을 대조해 남은 단위부터 이어 간다. 같은 검증이 세 번 실패하면 멈춘다. 게시 직전에 이슈를 다시 읽어 그사이 미결 사항이 생기지 않았는지 확인하고, 그 레포의 PR 줄에 PR이 있거나 같은 브랜치의 열린 PR이 있으면 새로 만들지 않고 그 브랜치에 push한다. 리뷰의 열린 지적은 이 단계가 고침·고치지 않음·이미 고쳐짐로 판정해 반영하며 지적을 닫지는 않는다.
  사람이 실행할 SQL이나 설정 변경처럼 PR로 올리지 않으며, 레포별 계획의 그 레포 절에 "사람이 실행할 것"으로 쓰고, 실행할 수 있는 범위에서 검증해 결과를 적은 뒤 단계를 리뷰로 바꾼다. 데이터를 바꾸는 것은 데이터 변경 체크리스트(사전 상태 확인, 다시 실행해도 안전한지, 되돌리기, 순서와 번호, 사후 확인, 코드와의 순서)를 따른다. 사람이 머지 전에 확인하기로 한 완료 조건이 있으면 PR을 올린 뒤 이슈 댓글로 확인할 사람에게 무엇을 어떤 데이터로 보면 되는지 알리고 결과에 "확인 요청함"을 적는다. 검증 명령은 줄이지 않고 실행한 그대로 적는다.
- **이유**: 3번과 PR 본문 구성은 execute와 create에서 가져왔다. 검증 실패 시 바로 멈추고 보고하던 execute의 규칙을 유지하는 안은 버렸다. 사람이 없는 봇 실행에서는 단순한 실수 하나로도 루프가 멈춘다.
- **적용 범위**: 해결 단계 문서, 데이터 변경 체크리스트.

### 리뷰 단계의 절차

- **바꾸는 것**: pr-workflow의 review와 fix가 하던 리뷰와 반영을 루프의 리뷰 단계로 가져오고, 코멘트 게시 전의 승인과 기각 판정의 사용자 승인은 두지 않는다.
- **모양**: 레포 하나를 단위로 수행한다. 리뷰 대상은 코드, 위키와 다른 내용, 계획의 실수 세 가지다.
  1. 누가: 구현한 맥락을 물려받지 않은 쪽이 리뷰한다. 다른 봇이나 새 세션이 맡고, 한 세션이 루프를 이어 가는 경우에는 서브에이전트에 맡긴다.
  2. 코드 리뷰: PR의 변경을 파일별로 보며 버그, 기존 소비처에 미치는 사이드이펙트, 레포별 계획·결정과 다르게 구현된 부분을 찾는다. 스택별 체크리스트를 기준으로 삼는다.
  3. 위키 대조: 변경과 이슈의 결정이 위키 문서와 다른 부분을 찾는다.
  4. 계획 실수 점검: 네 오판 유형으로 이슈 기록과 실제를 대조한다. 계획의 "현재 동작"과 근거가 코드와 일치하는가, 변경이 기대는 프레임워크 동작을 실제로 확인했는가, 바뀐 공용 코드의 다른 호출부와 "사용처 없음" 주장이 맞는가, 결과에 적힌 검증이 실제로 실행됐고 잘못 구현해도 통과하는 검증은 아닌가.
  5. 등급: Blocker와 Bug가 차단 지적이다. 개선은 기록만 하고 반영하지 않는다.
  6. 리뷰 루프: 차단 지적이 있으면 그 레포의 단계를 해결로 되돌린다. 해결하는 쪽은 지적마다 고침·고치지 않음·이미 고쳐짐을 근거와 함께 판정해 반영하고, 리뷰는 바뀐 부분을 다시 본다. 3회차에도 고칠지 말지가 갈리는 지적은 미결 사항으로 올린다.
  7. 기록: 지적과 처리 결과는 이슈의 "리뷰 기록" 절에 적는다. PR에는 리뷰를 통과했을 때 요약 코멘트 하나만 남기며 여기에 반영하지 않은 개선 제안이 들어간다. 드러난 오판은 에이전트 개선 피드백에도 한 줄 남긴다.
  8. 끝: 그 레포의 차단 지적이 모두 닫히고, 그 레포가 확인할 완료 조건 가운데 실행자가 머지 전에 확인하는 것이 모두 통과면 PR 줄에 리뷰한 head 커밋을 적고 단계를 머지 대기로 바꾼다. 실패나 미실행이 있으면 차단 지적으로 적는다. 사람이 머지 전에 확인하기로 한 조건과 머지 뒤에 확인하는 조건은 통과를 막지 않는다. 사람의 확인은 지적으로 만들지 않고 PR의 요약 코멘트에 "머지 전에 확인할 것"으로 적어 넘기며, 확인한 사람이 문제를 찾으면 PR에 변경 요청을 남기고 그것이 다음 실행에서 지적으로 들어온다.
  재리뷰는 직전에 리뷰한 커밋 이후의 변경과 열린 지적 전부를 본다. 고쳤다고 답한 지적은 고친 커밋에서 해결됐을 때, 고치지 않음과 이미 고쳐짐은 이유를 코드에서 확인해 받아들일 때 닫는다. 완료 조건을 가르는 유일한 검증이 잘못 구현해도 통과하면 Bug로 본다. 코드는 맞고 계획의 문장만 틀렸으면 지적하지 않고 에이전트 개선 피드백만 남긴다. PR에 남기는 요약 코멘트는 `[auto-flow]`로 시작한다.
  코드 리뷰는 추가된 줄만 보지 않고, 완료 조건이 만드는 상황을 변경 뒤의 경로에 넣어 고치지 않은 코드까지 끝까지 따라간다. 지적이 없는 회차도 리뷰 기록에 남긴다. 사람이 실행할 것도 같은 절차로 리뷰하며 요약은 이슈 댓글로 남긴다. 사람이 실행할 것에 대한 지적은 개선 등급이라도 열어 두어 해결 단계가 반영하게 한다.
- **이유**: 코드 리뷰의 렌즈와 등급, 판정과 3회차 규칙은 pr-workflow의 review와 fix에서 가져왔다. 지적을 PR 인라인 코멘트로 다는 기존 방식은 버렸다. AI가 올린 PR에 AI의 지적과 답글이 쌓여 사용자가 머지할 때 읽을 것이 늘어나고, 코멘트를 고칠 수 없는 호스트에서는 되돌릴 수 없다. 사람의 머지 전 확인까지 리뷰 통과 조건에 두던 것은 가상 실행 뒤에 바꿨다. 가상 실행 사례 D에서 사용자의 로컬 화면 확인을 기다리는 동안 해결과 리뷰를 오가며 같은 실행이 다섯 번 헛돌았고, 사람을 기다리는 지점이 합의한 세 곳을 넘게 된다. 사람의 확인은 PR을 머지하는 사람이 머지 전에 하는 일로 본다.
- **적용 범위**: 리뷰 단계 문서, 스택별 체크리스트, 데이터 변경 체크리스트.

### 위키 연동

- **바꾸는 것**: 루프가 네 지점에서 위키를 읽거나 쓴다. 위키에 쓸 때는 agent-wiki의 add를 부르고 PR 없이 바로 반영한다.
- **모양**:

  | 시점 | 하는 일 |
  | --- | --- |
  | 검토를 시작할 때 | 세션에 위키 문서가 있으면 계획의 근거로 읽는다. 위키와 코드가 다르면 한쪽을 고르지 않고 질문 대상으로 올린다. |
  | 결정이 확정될 때 | 여러 이슈에서 다시 쓸 정책·계약이면 관련 정책 절에 적고 그 시점에 add로 위키에 반영한 뒤 위키 반영 칸을 채운다. 미결 사항에 걸려 있는 정책은 답을 받은 뒤에 반영한다. |
  | 리뷰할 때 | 위키와 다른 점은 세 경우로 처리한다. 코드가 틀렸으면 차단 지적으로 "리뷰 기록" 절에 적고 해결로 되돌려 고친다. 결정은 확정됐는데 위키 반영만 빠졌으면 "리뷰 기록" 절에 적고 리뷰하는 쪽이 바로 add로 반영한 뒤 관련 정책 절의 위키 반영 칸을 채우며 단계는 바꾸지 않는다. 근거가 되는 확정된 결정이 없으면 미결 사항에 올려 검토에서 결정한 뒤 위키에 반영한다. |
  | 이슈가 완료될 때 | 관련 정책 절의 반영 누락을 확인하고, 결정, 에이전트 개선 피드백, 리뷰 기록에서 다음 작업자의 행동을 바꿀 프로젝트 지식을 뽑아 add로 한 번 반영한다. |

  미결 사항에는 풀리기 전에는 진행할 수 없는 것만 적는다. 머지된 코드의 반영은 루프가 부르지 않고 agent-wiki update의 정기 실행에 맡긴다. 위키 플러그인이 없는 환경에서는 위 네 가지를 건너뛴다.
  위키에 반영할 때는 근거로 이 이슈의 위치를 넘긴다. 반영하지 못하면 위키 반영 칸에 "미반영: 사유"를 적고, 반영하려면 사람의 판단이 필요하면 세션에서 묻지 않고 미결 사항에 올린다.
- **이유**: 완료 때 한 번만 반영하는 안은 버렸다. 위키의 문서 규약이 서비스 사이의 의무를 결정 시점에 적도록 하고, 이슈가 끝나기 전에는 다른 이슈의 검토가 그 결정을 볼 수 없다. update는 명시 호출 전용이고 머지 커서로 처리하지 않은 머지를 스스로 찾으므로 루프가 부를 필요가 없다.
- **적용 범위**: 공통 문서, 검토·리뷰 단계 문서.

### agent-wiki add의 바로 반영

- **바꾸는 것**: add가 위키 PR을 열지 않고 기준 브랜치에 바로 push한다. 루프가 부르든 사용자가 직접 부르든 같다. update는 지금처럼 위키 PR을 연다.
- **모양**: add는 임시 clone의 기준 브랜치 위에 문서별 커밋을 만들고 원격 기준 브랜치로 push한다. 원격이 앞서 있어 push가 거부되면 원격을 받아 그 위에 다시 올리고, 충돌하면 멈춰서 보고한다. PR 링크 대신 push한 커밋과 사실 목록을 실행 결과로 보고한다. `--dry-run`은 지금처럼 커밋과 push를 하지 않는다.
  push가 거부돼 원격을 받았을 때 그사이 들어온 커밋이 이번에 고친 문서나 같은 정책을 건드렸으면 그 문서에 대해 반영 절차를 다시 수행한 뒤 올린다. push한 커밋이 원격 기준 브랜치에 들어간 것을 확인한 뒤에 반영을 보고한다.
- **이유**: 사용자가 add의 변경을 PR로 올려 승인받는 절차를 없애기로 했다. add는 출처가 있는 확정된 결정과 지식을 더하는 일이고 반영 전에 add 안의 독립 검토를 거친다. update는 코드에서 사실을 추출해 기존 문서를 고치거나 지우므로 PR을 확인 지점으로 남긴다.
- **적용 범위**: `agent-wiki/skills/add/SKILL.md`, `agent-wiki/references/publish.md`, `agent-wiki/README.md`, agent-wiki의 관련 테스트.

### 네 진입점과 한 벌의 단계 문서

- **바꾸는 것**: 루프를 네 스킬로 나누고, 단계의 방법은 문서 한 벌로 둔다. 세션 훅은 두지 않는다.
- **모양**:

  | 스킬 | 하는 일 | 쓰는 쪽 |
  | --- | --- | --- |
  | `run-issue` | 이슈 하나를 상태에 따라 검토, 해결, 리뷰 순서로 이어 가고 사람을 기다리는 지점에서 멈춘다. | 직접 쓰는 사용자, 혼자 다 맡는 봇 |
  | `plan-issue` | 검토 단계만 수행하고 멈춘다. | 이슈 전체를 맡은 봇 |
  | `resolve-issue` | 한 레포의 해결 단계만 수행하고 멈춘다. 리뷰 지적 반영도 여기서 한다. | 레포 담당자 봇 |
  | `review-issue` | 한 레포의 리뷰 단계만 수행하고 멈춘다. | 리뷰를 맡은 봇 |

  검토·해결·리뷰 단계 문서와 공통 문서(이슈 읽기와 쓰기, 상태, 템플릿)는 하나씩만 두고, 네 스킬의 본문은 공통 절차를 따르고 해당 단계 문서만 수행한다는 짧은 진입점이다. 머지 확인과 완료 처리는 공통 절차에 두어 어느 스킬로 들어오든 머지 대기 중인 PR의 상태를 먼저 반영한다. 단계는 스킬로 정해지므로 호출 문장으로는 레포만 좁힌다. 호출은 `/auto-flow:run-issue ABC-123` 형태다.
  `plan-issue`는 레포를 함께 받으면 그 레포의 레포별 계획만 다루며, 레포 담당자 봇도 자기 레포의 계획이 필요할 때 이 방식으로 부른다. 공통 문서에는 스킬 이름과 인자만 쓰고 호출 예시는 README에 런타임별로 둔다.
- **이유**: 스킬 하나가 호출 문장의 범위 지정으로 단계를 가르는 처음 안은 바꿨다. 봇의 역할 경계가 "해결만 하라"는 문장에 달려 있어, 그 문장이 빠지면 담당자 봇이 검토를 다시 하거나 자기 코드를 스스로 리뷰하게 된다. 단계별 스킬만 두는 안은 직접 쓰는 사용자가 단계마다 다시 불러야 해서 `run-issue`를 함께 둔다. `run-issue` 대신 세션 훅으로 이어 가는 규칙을 주입하는 안은 버렸다. 훅은 설치한 모든 세션에 들어가 담당자 봇의 세션에도 이어 가라는 규칙이 실리고, 이슈와 무관한 세션에도 매번 주입되며, Codex에서는 훅을 따로 신뢰해야 실행된다. 이름은 기존 관례를 따르지 않고 하는 일이 드러나게 지었으며, Claude Code의 내장 `/plan`·`/review`와 구분되도록 `-issue`를 붙였다.
- **적용 범위**: `auto-flow/skills/` 네 폴더, `auto-flow/references/`의 공통 문서와 단계 문서.

### 플러그인 구성과 이름

- **바꾸는 것**: auto-flow를 새 루프로 전면 교체하고 기존 워크플로 플러그인과 공존시킨다. README는 auto-flow를 plan-workflow·pr-workflow를 쓰지 않는 상태에서 사용하도록 안내한다.
- **모양**:

  | 플러그인 | 처리 |
  | --- | --- |
  | auto-flow | 이름을 유지하고 내용을 새 루프로 전면 교체한다. 스킬은 이슈를 만드는 `create-issue`와 루프의 진입점 `run-issue`, `plan-issue`, `resolve-issue`, `review-issue` 다섯이고 이슈 라벨은 `auto-flow`다. |
  | plan-workflow | 그대로 둔다. 기존 사용자가 계속 쓴다. |
  | pr-workflow | 그대로 둔다. 기존 사용자가 계속 쓴다. |
  | agent-wiki | 유지한다. add의 게시 방식만 바꾸고, plan-workflow의 작업 기록을 입력으로 받는 기존 동작은 남긴다. |
  | better-communication | 그대로 둔다. |
- **이유**: `auto-flow`는 이미 마켓에 등록된 이름이고 0.4.0의 운영 문서도 추적 라벨로 `auto-flow`를 썼다. 새 이름의 플러그인을 추가하는 안은 버렸다. 기존 auto-flow를 어차피 지워야 하고 설치 명령만 달라진다. plan-workflow와 pr-workflow를 이번에 제거하는 안은 사용자가 공존으로 바꿨다. 기존 사용자가 계속 쓸 수 있어야 하고 삭제는 공지와 완전한 대체 뒤에 한다.
- **적용 범위**: `auto-flow/`, 두 마켓 파일의 auto-flow 항목, `README.md`, `tests/`의 auto-flow 검사.

### 이슈 생성 스킬

- **바꾸는 것**: 이슈를 만드는 `create-issue` 스킬을 더한다. 응대 봇이나 이슈 담당 봇, 사용자가 요청을 받아 루프가 바로 다룰 수 있는 이슈를 만든다. 처음에는 범위 밖에 두었다가 구현 뒤에 사용자가 추가하기로 했다.
- **모양**:

  | 항목 | 내용 |
  | --- | --- |
  | 받는 것 | 요청 원문(붙여 넣은 글, 대화, 메시지 위치)과 만들 곳(프로젝트, 이슈 유형). 만들 곳은 호출할 때 받은 값, 실행자 지침, 환경 문서 순으로 찾고 어디에도 없으면 묻는다. |
  | 만드는 조건 | 요청에서 "원하는 결과"를 찾을 수 있어야 만든다. 찾을 수 없으면 만들지 않고 요청자에게 물을 질문을 돌려준다. 원하는 결과는 분명한데 세부 정책이 비어 있으면 그대로 만들고, 빈 부분은 검토 단계가 미결 사항으로 다룬다. |
  | 중복 확인 | 만들기 전에 같은 요청의 열린 이슈를 검색한다. 있으면 만들지 않고 그 이슈를 알린다. |
  | 관계자 | "요청" 절에 `관계자` 줄을 둔다. 환경 문서가 정한 곳에서 요청자, 결정할 사람, 대상 서비스의 담당을 찾고, 정한 곳이 없으면 요청 원문에 드러난 사람만 적는다. 찾지 못한 역할은 "미정"으로 둔다. 검토 단계는 미결 사항의 답할 사람을 여기서 찾는다. |
  | 결함 제보의 빠진 정보 | 결함 제보인데 관찰한 현상, 기대한 결과, 발생한 환경과 조건이 원문에 없으면 이슈를 만들고 빠진 것을 미결 사항에 질문으로 적는다. 답할 사람은 요청자이고 막힌 것에 "생성 시 확인"이라고 적는다. 확인 요청은 하지 않는다. |
  | 본문 | 템플릿 아홉 절을 쓰고 "요청" 절과 위의 질문만 채운다. 요청자, 요청일, 요청이 온 곳, 관계자, 원하는 결과, 하지 않을 것, 배경, 기한을 정리해 적고 원문은 본문에 붙이지 않는다. 원문을 다시 볼 곳이 없으면 댓글로 남긴다. `auto-flow` 라벨을 붙이고 상태는 검토로 둔다. |
  | 쓰지 않는 것 | 완료 조건과 계획은 쓰지 않는다. 요청자가 적은 원인과 해결 방법은 "요청자가 본 원인과 해결 방법"에 따로 적고, 요청에 없는 내용은 추측으로 채우지 않는다. |
  | 끝 | 이슈 키와 위치, 미정으로 남은 관계자, 미결 사항에 적은 질문을 알리고 멈춘다. 검토는 이어서 시작하지 않는다. |

  이 요청이 개발 요청인지 가르는 일, Teams 같은 곳에서 요청을 읽어 오는 일, 요청자에게 결과를 알리는 일은 스킬이 하지 않고 호출하는 쪽에 둔다.
  검토 단계는 "생성 시 확인"으로 적힌 질문을 계획을 세우면서 가른다. 코드, 문서, 이슈 호스트의 기록으로 직접 확인할 수 있으면 확인한 내용을 근거와 함께 적고 줄을 지운다. 답에 따라 완료 조건이나 계획이 달라지지 않으면 줄을 지운다. 답이 있어야 정할 수 있으면 줄을 남기고 답할 사람에게 확인을 요청하며, 그 뒤는 다른 미결 사항과 같이 답 확인으로 처리한다.
- **이유**: 봇이 이슈를 만들 때 따를 절차가 없으면 봇마다 본문을 다르게 쓰고 첫 검토 실행이 매번 템플릿으로 바꿔야 한다. 원하는 결과가 불분명한 요청을 일단 만들고 미결 사항에 올리는 안은 버렸다. 응대 봇은 요청자와 대화 중이라 그 자리에서 묻는 편이 빠르고, 무엇을 원하는지 모르는 이슈가 쌓이지 않는다. `run-issue`가 이슈가 없을 때 만들게 하는 안도 두지 않았다. 한 단계는 스킬 하나로 대응해야 봇에게 그 일만 맡길 수 있다. 관계자를 찾는 방법은 환경마다 달라(회사는 Teams·Bitbucket·Jira, 개인은 GitHub, 다른 회사는 Slack·GitHub) 스킬에 넣지 않고 환경 문서에 둔다. 결함 제보에서 빠진 정보를 호출한 쪽에 알리기만 하는 안은 사용자의 제안으로 바꿨다. 이슈에 적어 두어야 추적되고, 생성 단계는 코드를 보지 않아 그 질문이 정말 필요한지 알 수 없으므로 물을지는 검토 단계가 정한다. 중복 검색에서 나온 관련 이슈의 링크를 따로 적는 안은 넣지 않았다. 같은 요청이면 만들지 않고 그 이슈를 알리는 것으로 충분하다.
- **적용 범위**: `auto-flow/skills/create-issue/SKILL.md`, 이슈 템플릿의 "요청" 절과 "미결 사항" 절, 공통 문서, 검토 단계 문서, `auto-flow/README.md`, `README.md`, `tests/`의 auto-flow 검사.

### 환경 문서

- **바꾸는 것**: 환경마다 다른 도구와 절차를 `references/environment.md` 한 장에 모은다. 지금까지는 공통 절차에 "실행자의 지침이나 프로젝트 문서를 따른다"는 문단만 있었고, 무엇을 정해야 하는지는 적혀 있지 않았다.
- **모양**: 문서는 아래 다섯 절이며 절마다 그 환경에서 무엇을 쓰는지를 적는다.

  | 절 | 정하는 것 |
  | --- | --- |
  | 1. 이슈 | 호스트, 읽기·쓰기·검색·라벨·댓글에 쓸 도구, 본문 서식, 이슈를 만들 곳(프로젝트와 유형) |
  | 2. PR | 호스트, 조회·생성·코멘트에 쓸 도구, 원본 저장소와 베이스 브랜치 |
  | 3. 대화 | 요청 원문을 읽는 곳, 사람에게 확인을 요청하는 수단 |
  | 4. 관계자 | 요청자, 결정할 사람, 서비스 담당을 찾는 곳 |
  | 5. 이슈 상태 | 호스트의 상태 전환을 누가 언제 하는가 |

  이 저장소의 배포판은 GitHub 기준으로 채우고, 다른 환경(사내판의 Teams·Bitbucket·Jira 등)은 이 파일만 바꾼다. 스킬과 단계 문서는 도구 이름을 직접 적지 않고 이 문서의 절 번호를 가리키므로 절의 제목과 번호는 배포판 사이에 같게 둔다. 실행자의 지침이나 프로젝트 문서가 같은 항목을 정했으면 그쪽이 우선하고, 어디에도 정의가 없는 항목은 세션에 있는 도구로 진행한다. 받은 이슈나 PR이 문서가 적은 호스트와 다른 호스트의 것이면 그 항목에는 문서를 적용하지 않고 세션에 있는 도구로 진행한다.
- **이유**: 같은 저장소의 pr-workflow(`references/host.md`)와 agent-wiki(`references/publish.md`)가 쓰는 방식이며 사내판은 그 파일만 바꿔 쓴다. 양식만 플러그인에 두고 값은 봇 지침에 적는 안은 버렸다. 도구는 봇마다가 아니라 환경마다 같아서 봇 지침마다 같은 내용을 반복해 적게 된다.
- **적용 범위**: `auto-flow/references/environment.md`, 공통 문서, 해결 단계 문서, `create-issue`, `auto-flow/README.md`, `README.md`, `tests/`의 auto-flow 검사.

(`~/.orca/bots/*/SOUL.md`, `orca automations list --json`)

- 사용자가 계획 기록의 참고로 든 문서는 강의 정리 "AI와 함께 개발하고 학습하는 방법"이다. 최소 문서를 스펙(무엇을 만드는가, 번호를 붙인 인수 조건), ADR(왜 그렇게 결정했는가, 맥락·대안·선택과 이유), 플랜(어떤 순서와 조건으로 끝내는가, 간결한 작업 순서·완료 조건·관련 인수 조건)으로 나눈다. 요구 문장은 누가 어떤 조건에서 무엇을 해야 하는지 한 문장에 하나씩 적고, 정해지지 않은 정책은 AI가 채우지 않고 확인 질문으로 남긴다. 문서가 길거나 초기에 질문이 쏟아지면 이해하지 않고 승인하기 쉽다고 경고한다. (사내 위키의 강의 정리 문서, 2026-11-20 정리판)

(사내 제품 레포들의 `.devcenter/workspace/progress/*/feedback.md`와 `.ai-docs/workspace/*/feedback.md`)
- 이 계획을 Codex와 Opus 에이전트가 각각 검토했고(2026-11-25) 받아들인 지적은 합의의 해당 단위에 반영했다. 사용자가 지적의 수용 판단을 맡겼다(위임). 받아들이지 않은 지적은 다음과 같다. 봇의 변경을 본문 대신 댓글로만 남기자는 안은 본문 하나로 상태를 관리한다는 합의와 어긋나 저장 뒤 확인으로 대신했다. 미결 사항 표에 종류 칸을, 레포 줄에 대기 칸을, 작업 단위 표에 칸 셋을 더하자는 안은 표가 넓어져 답할 사람 칸의 표기와 단계 칸의 괄호, 검토 지침으로 대신했다. 구판의 `auto-flow` 라벨이 붙은 이슈가 새 루프에 잘못 선택될 수 있다는 지적은 그런 이슈가 0건이라 받지 않았다(`labels = "auto-flow"` 조회).
- 스킬 문서 초안을 쓰고 과거에 해결된 실제 이슈 넷으로 가상 실행을 했다(2026-11-25). 과거 시점의 레포 사본과 파일로 만든 가상 이슈·PR·위키에서 PM 봇과 담당자 봇을 Opus로 돌렸고, 미결 사항에는 실제 기록을 아는 가상 사용자가 그때의 결정대로 답했다. 에이전트 실행은 86회였다. 사례 A(프론트 레포 하나)와 사례 B(백엔드 레포 하나, 사용자의 PR 변경 요청 포함)는 완료까지 갔다. 사례 C(레포 넷, 사람이 실행할 SQL 포함)는 코드 레포 둘은 완료됐지만 사람이 실행할 SQL만 있는 레포가 머지 대기에서 완료로 갈 경로가 없어 멈췄다. 사례 D(프론트와 백엔드 레포)는 사람의 로컬 화면 확인을 기다리는 상태가 문서에 없어 해결과 리뷰를 오가다 멈췄고, 같은 실행이 다섯 번 헛돌았다. 실제 작업과 비교하면 범위와 판정 기준은 네 건 모두 대체로 같았다. 실제 작업의 교정 기록과 같은 실수는 두 건에서 되풀이됐다. 사례 B의 대상 범위 누락은 실제와 같이 사용자의 PR 확인에서 드러났고, 사례 D의 화면 선택 결함은 사람의 확인이 오지 않아 PR에 남았다. 평가에서 나온 문서 수정은 초안에 반영했다. 그 가운데 합의한 동작을 바꾸는 세 가지(사람의 머지 전 확인은 리뷰 통과를 막지 않음, 머지 뒤 확인이 남은 완료의 표시, PR 없는 산출물의 경로)는 사용자가 확인해 합의의 해당 단위에 반영했고, 나머지 문서 수정은 사용자에게 보고한 뒤 해당 단위에 적었다. 고친 문서로 멈췄던 두 건을 다시 돌려 확인하지는 않았다. (가상 실행 평가 `EVAL.md` 네 건, 스킬 문서 초안, 사용자 확인 2026-11-25)
- 이슈 템플릿의 개정안을 Opus 에이전트가 가상 실행 네 건의 실제 본문과 대조해 검토했다(2026-11-25, 지적 28건). 처음에는 Codex에 맡겼으나 시간이 오래 걸려 사용자가 Opus로 바꾸게 했다. 받아들인 것은 합의의 "이슈 본문의 구성과 두 수준의 계획", "결정 절과 관련 정책 절", "에이전트 개선 피드백"에 적었다. 받아들이지 않은 것은 다음과 같다. 옛 판 템플릿으로 쓴 이슈를 옮기는 절차는 그런 이슈가 가상 실행에만 있어 두지 않았다. 검토 담당과 레포별 서비스 담당을 적을 칸은 이력과 레포의 담당 줄로 알 수 있어 더하지 않았다. Jira 문법 대응을 환경 문서로 옮기는 안은 이 배포판의 환경 문서가 GitHub 기준이라 Jira 이슈에서 쓸 수 없게 되므로 템플릿에 두었다. (리뷰 결과, 가상 실행 본문과 평가)
- 위키 레포 지도의 노드는 `remote`, `defaultBranch`, `status`, `stack`, `summary`, `responsibilities`, `hosts` 일곱 키이며 담당자 정보는 없다. (`agent-wiki/references/doc-contract.md` 9장, 사내 위키의 `registry.json`)
- pr-workflow는 `references/host.md`에, agent-wiki는 `references/publish.md`에 호스트 절차를 모아 두고, 사내판 agent-wiki는 `publish.md`만 Bitbucket 절차로 바꿔 쓴다. 교체 전의 auto-flow 0.4.0은 `references/operations-environments.md`에 사내 Teams·Jira·Orca·Bitbucket 절차를 직접 적었다. (`pr-workflow/references/host.md`, 사내판 `plugins/agent-wiki/references/publish.md`, 커밋 `93c6713`)
- plan-workflow는 SessionStart 훅으로 작업 기록 규약을 세션에 주입한다. 저장소 테스트는 이 훅과 auto-flow의 이슈 양식을 검사한다. (`plan-workflow/hooks/session_start.sh`, `tests/test_plugins.py`)

- `python3 tests/check_codex.py`가 통과한다. 실제 Codex 로더로 설치를 확인한다.
- `claude plugin validate`로 Claude 패키지와 마켓 매니페스트를 검사한다.
- 사용자가 지정한 실제 이슈 하나로 검토부터 머지 대기까지 루프를 돌려 보고, 드러난 문제를 고친 뒤 끝낸다. 그 이슈에는 본문 갱신, 라벨, PR이 실제로 생긴다. 위 세 검사는 패키지가 깨지지 않았는지만 확인하고 계획의 질과 이슈 기록이 기대에 맞는지는 보여 주지 못한다.

## 범위 밖

- plan-workflow와 pr-workflow의 삭제는 이번에 하지 않는다. 사용자들에게 공지하고 auto-flow로 완전히 대체된 뒤에 한다.
- 리뷰에서 실제 런타임 테스트로 검증하는 일은 이번에 넣지 않는다. 나중에 추가될 수 있다.
- 완료된 이슈들의 교정 기록을 모아 반복되는 오판과 번복을 찾는 개선 루프 스킬은 이번에 만들지 않는다. 새 루프를 거친 이슈의 교정 기록이 쌓인 뒤 그 내용을 보고 설계한다. 이번에는 교정 기록과 완료된 이슈를 찾을 수단까지만 마련한다.
- Teams 연동과 미결 사항의 담당자 확인 요청은 이번 루프에서 다루지 않는다.
- 이슈를 만들 때 요청이 실행자의 업무 범위에 드는지 판정하는 일은 넣지 않는다. 판정의 근거가 될 위키가 부실하면 구분할 수 없다. 범위 밖 요청은 검토 단계에서 인수 조건마다 맡을 레포를 정할 때 드러난다. (사용자 확인 2026-11-25)
