# auto-flow 개발 스킬과 직접 호출 검증

## 의도

이전 대화를 모르는 담당자도 Jira 조건이나 PR을 받아 요청한 개발 작업 하나를 수행할 수 있어야 한다. 계획을 쓰거나 조정해도 기존 요청과 조건 번호가 보존되고, 수정본이 이미 게시된 PR은 회신만 복구할 수 있으면 된다.

## 확인한 사실

기준 커밋 `c0a96ff`에는 `auto-flow` 계획 스킬 세 개가 있다. `references/plan-record.md`는 조건 번호를 유지하라고 하지만 AC-11의 계획 양식은 없고, `tests/test_plugins.py`의 설치 계약도 계획 스킬 세 개만 열거한다.

## 합의

### Jira 계획과 개발 작업의 독립 호출

- 바꾸는 것 — AC-11 양식을 신규·기존 계획과 사본에 적용하고 AC-14~20의 개발 작업을 직접 호출할 수 있게 한다.
- 모양 — 코드 변경은 일반 구현과 수용한 지적 수정을 받는다. 레포 테스트, PR 게시, 코드 결함 리뷰, 지적 판정, 스레드 회신은 각각 하나의 스킬이다. Jira 조건, 계획·코드 판본, PR 및 스레드 위치가 인계 근거다.
- 이유 — 호출자가 사람이 만든 산출물을 넘기거나 실패한 게시만 재시도할 때 선행 작업을 다시 실행할 필요가 없다. 역할 배정과 도구 선택은 공통 업무의 책임 밖에 둔다.
- 적용 범위 — `AUTO-FLOW-SPEC.md`의 AC-01~03, AC-11~20 및 `AUTO-FLOW.md`의 3A에 적용한다.

## 검증

`python3 -m unittest discover -s tests`로 패키지 계약을 확인한다. 임시 설치 환경에 `agent-wiki`와 `auto-flow`만 등록하고 계획 작성·조정, 새 세션의 구현, 사람의 변경에 대한 테스트와 PR 리뷰, 지적 판정·수정, 최신 head 재리뷰, 답글 복구를 직접 실행한다. 결과는 AC, 입력·출력 판본, 상태 변화와 증거 위치에 연결하고 모의 Jira·PR과 실제 Git·테스트를 구분한다.

### 격리 실행 결과

[실행 근거](evidence.json)의 `runs`에서 표의 이름으로 요청·세션·응답을, `observations`에서 본문·패치·원격 판본·답글 변화를 찾을 수 있다. 신규 계획, 사람이 만든 PR, 신규 PR 게시 사례는 서로 다른 모의 호스트를 썼다. 각 실행의 `auto_flow_files_sha256`으로 리뷰 전·후 설치본을 구분할 수 있다.

Git 체크아웃·커밋·로컬 bare 원격으로의 push, 코드와 테스트 실행, Codex 설치·스킬 호출은 실제로 수행했다. Jira 본문·댓글·근거 링크, PR 생성·스레드·장애 응답은 로컬 모의 호스트가 제공했다. 운영 Jira의 서식 변환과 권한, 실제 PR 호스트의 쓰기·알림, 병합과 Teams 전송은 이 검증에서 확인하지 않았다.

첫 사본 시험에서 계획 스킬이 입력 파일을 편집했고, 첫 코드 변경 응답에는 미커밋 판본을 다시 대조할 지문이 빠졌다. 두 지침을 고친 뒤 최종 설치본에서 사본 보존과 변경 파일 해시를 재검증했다. 패키지 테스트 14개, 전체 및 두 플러그인 전용 Codex 로더 검사, Claude 플러그인·마켓플레이스 매니페스트 검사가 통과했다. Claude에서는 스킬의 대화 동작을 별도로 실행하지 않았다.

PR 게시만 요청한 첫 실행에서는 모의 Jira에도 조건 링크 두 건을 썼다. 독립 리뷰에서 이 동작을 확인해 쓰기 목적지를 제한하고 같은 요청으로 다시 실행했다. 표에는 수정 후 실측한 결과를 실었다.
