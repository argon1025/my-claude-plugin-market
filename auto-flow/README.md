# auto-flow

이슈 하나를 검토, 해결, 리뷰, 머지 대기, 완료 순서로 진행하는 플러그인입니다. 계획과 진행을 모두 이슈 본문에 기록하므로, 다음 실행자는 사람이든 봇이든 이슈만 읽고 이어 갑니다. 훅이 없어 스킬을 호출할 때만 동작합니다.

| 스킬 | 하는 일 | 쓰는 쪽 |
| --- | --- | --- |
| `create-issue` | 요청을 받아 이슈를 만듦. 템플릿을 적용하고 "요청" 절을 채운 뒤 멈춤. 원하는 결과가 불분명하면 만들지 않고 요청자에게 물을 질문을 돌려주며, 같은 요청의 열린 이슈가 있으면 그 이슈를 알림 | 응대 봇, 이슈 담당 봇, 직접 쓰는 사용자 |
| `run-issue` | 이슈의 상태를 읽고 검토, 해결, 리뷰를 차례로 이어 가다가 사람을 기다리는 지점에서 멈춤 | 직접 쓰는 사용자, 혼자 다 맡는 봇 |
| `plan-issue` | 검토 단계를 맡음. 요청을 번호 붙인 완료 조건으로 만들고 레포를 나누며, 미결 사항을 관리하고 검토를 끝낼지 판정함. 담당이 따로 없는 레포는 레포별 계획까지 씀 | 이슈 담당 봇 |
| `plan-issue-detail` | 한 레포의 레포별 계획만 씀. 그 레포의 코드를 따라가 현재 동작, 작업 단위, 검증을 적고 멈춤 | 레포 담당자 봇 |
| `resolve-issue` | 한 레포의 해결 단계만 수행함. 계획을 현재 코드와 대조하고, 구현·검증한 뒤 PR을 올림. 리뷰 지적의 반영도 여기서 함 | 레포 담당자 봇 |
| `review-issue` | 한 레포의 리뷰 단계만 수행함. 코드, 위키와 다른 내용, 계획과 기록의 실수를 점검함 | 리뷰를 맡은 봇 |

## 설치

```
/plugin marketplace add argon1025/my-claude-plugin-market
/plugin install auto-flow@my-claude-plugin-market
```

같은 마켓의 plan-workflow와 pr-workflow를 설치하지 않은 상태에서 씁니다. plan-workflow의 세션 훅은 계획을 저장소의 `plan.md`에 기록하라고 주입하고, 두 플러그인의 스킬은 "계획 세워줘", "PR 리뷰해줘" 같은 요청에 auto-flow의 스킬과 함께 반응합니다.

## 전제 조건

- **이슈·PR 도구**: 이슈와 PR을 읽고 쓸 도구가 세션에 있어야 함. 이 배포판의 [환경 문서](references/environment.md)는 GitHub와 `gh` 기준임. 해당 호스트를 다룰 도구가 없으면 스킬이 시작하지 않고 그 사실을 알림
- **저장소 체크아웃**: 해결과 리뷰는 대상 레포의 체크아웃에서 수행함
- **위키(선택)**: agent-wiki가 있으면 계획과 리뷰의 근거로 위키를 읽고, 확정된 정책과 완료된 이슈의 지식을 `add`로 반영함. 없으면 그 일을 건너뜀

## 루프

| 상태 | 하는 일 | 넘어가는 조건 |
| --- | --- | --- |
| 검토 | 계획을 세우고 미결 사항을 관리함 | 미결 사항이 0건이고 계획이 끝내는 조건을 채우면 해결로 |
| 해결 | 계획대로 구현·검증하고 PR을 올림 | PR을 올리면 리뷰로 |
| 리뷰 | 코드, 위키와 다른 내용, 계획의 실수를 점검함 | 차단 지적이 있으면 해결로, 없으면 머지 대기로 |
| 머지 대기 | 사용자의 머지를 기다림. 사람이 실행할 것이 있으면 그 실행을 기다림 | 머지되고, 실행할 것은 실행했다고 알리면 완료로 |
| 완료 | 끝남 | |

검토는 이슈 전체에 하나이고, 해결부터는 레포마다 단계를 가집니다. 이슈는 `create-issue`로 만들거나 직접 만들며, 상태는 이슈가 만들어진 뒤부터 관리합니다.

사람을 기다리는 지점은 세 곳입니다. 미결 사항의 답, 계획을 세울 때의 질문, PR 머지입니다. 계획 전체의 승인, PR 게시 전의 승인, 리뷰 코멘트 게시 전의 승인은 받지 않습니다. 스킬은 PR을 승인하거나 머지하지 않고, 호스트의 이슈 상태(Jira 워크플로 전환, 이슈 닫기)도 바꾸지 않습니다.

## 호출

`create-issue`에는 요청 원문을, 나머지 스킬에는 이슈 키나 URL을 함께 줍니다. `plan-issue-detail`, `resolve-issue`, `review-issue`는 레포를 함께 받습니다.

| 런타임 | 예 |
| --- | --- |
| Claude Code | `/auto-flow:create-issue` 뒤에 요청 원문, `/auto-flow:run-issue ABC-123`, `/auto-flow:resolve-issue ABC-123 shop-api` |
| Codex | `$` 선택기에서 auto-flow의 `run-issue`를 고른 뒤 `ABC-123`을 적음 |

"ABC-123 진행해줘", "이 이슈 리뷰해줘"처럼 말로 요청해도 해당 스킬이 선택됩니다.

## 봇 구성

스킬은 환경을 가정하지 않으므로 누가 어느 스킬을 부를지는 쓰는 쪽이 정합니다.

| 구성 | 부르는 스킬 |
| --- | --- |
| 직접 호출 | 사용자가 `run-issue`로 한 세션에서 이어 감. 리뷰는 서브에이전트에 맡겨짐 |
| 역할을 나눈 봇(권장) | 이슈 담당 봇이 `plan-issue`, 레포 담당자 봇이 자기 레포에 `plan-issue-detail`과 `resolve-issue`, 리뷰 봇이 `review-issue` |
| 응대 봇을 더한 구성 | 위 구성에 더해, 응대 봇이 `create-issue`로 이슈를 만듦. 요청을 읽어 오는 일과 미결 사항의 답·결과를 요청자와 주고받는 일은 플러그인 밖임 |

### 역할을 나눈 봇

여러 레포에 걸친 이슈는 레포마다 코드를 따라가야 계획을 쓸 수 있습니다. 한 세션이 모든 레포의 계획을 쓰면 읽을 코드가 많아지므로, 이슈 전체 계획과 레포별 계획을 다른 봇이 맡습니다.

| 봇 | 스킬 | 시작하는 때 | 멈춘 뒤 넘기는 곳 |
| --- | --- | --- | --- |
| 이슈 담당 | `plan-issue` | 이슈를 지정한 검토 요청, 정기 실행 | 레포별 계획과 구현은 레포 담당자에게, 리뷰는 리뷰 봇에게 |
| 레포 담당자 | `plan-issue-detail`, `resolve-issue` | 이슈 담당이나 리뷰 봇의 넘김 | 계획을 채웠거나 미결 사항을 적었으면 이슈 담당에게, PR을 올렸으면 리뷰 봇에게 |
| 리뷰 | `review-issue` | 레포 담당자의 넘김 | 차단 지적이 있으면 레포 담당자에게. 없으면 사람의 머지를 기다림 |

1. 이슈 담당이 완료 조건을 쓰고 레포를 나눈 뒤, 레포 절의 담당 줄에 레포 담당자를 적음. 사람에게 물을 것은 미결 사항에 적고 답을 기다림
2. 이슈 전체 계획의 미결 사항이 풀리면 이슈 담당이 미결 사항에 "{레포}의 레포별 계획 필요"를 올리고 레포 담당자에게 넘김. 레포 사이에 주고받는 값이 있으면 값을 정의하는 레포가 먼저임
3. 레포 담당자가 `plan-issue-detail`로 계획을 채우고 그 줄을 지움. 사람의 결정이 필요하거나 완료 조건을 고쳐야 하면 미결 사항에 적고 멈춤
4. 미결 사항이 0건이 되면 이슈 담당이 끝내는 조건을 확인해 단계를 해결로 바꾸고, 레포 담당자가 `resolve-issue`로 구현해 PR을 올림
5. 리뷰 봇이 `review-issue`로 리뷰함. 차단 지적은 미결 사항이 아니라 "리뷰 기록"에 적히고, 레포 담당자가 `resolve-issue`로 반영함

- **정기 실행은 이슈 담당만**: 미결 사항의 답, PR의 머지, PR에 남긴 변경 요청, 리뷰를 통과한 뒤의 새 커밋은 `plan-issue`가 시작할 때 본문에 반영함. 나머지 봇은 넘김을 받았을 때만 시작함
- **넘김**: 스킬은 멈출 때 다음에 어느 단계를 어느 레포에 대해 누가 수행하면 되는지 알림. 봇은 그 내용대로 다음 봇을 부름
- **레포 담당자는 레포 단위로**: 계획, 브랜치, PR이 레포 단위이므로 한 레포는 한 봇이 맡음. 한 봇이 여러 레포를 맡아도 되며(서비스별 백엔드 담당, 프론트 담당 등), 화면과 서버가 한 레포에 있으면 그 레포를 통째로 한 봇에 둠
- **리뷰 봇은 구현하지 않은 봇**: 리뷰는 구현한 맥락을 물려받지 않은 쪽이 해야 함

봇마다 다른 것은 봇의 지침에 둡니다.

- **이슈 고르기**: 정기 실행에서 어떤 이슈를 다룰지. 루프가 다루는 이슈에는 `auto-flow` 라벨이 붙고 본문 첫 줄에 상태가 있음
- **담당 범위**: 맡은 레포와 그 체크아웃 경로. 이슈 담당은 레포마다 어느 봇이 담당자인지
- **넘기는 수단**: 다음 봇을 부르는 방법. 런타임마다 다름
- **겹쳐 실행하지 않기**: 본문에는 지금 수행 중이라는 표시가 없음. 같은 이슈의 같은 레포를 수행 중인 실행이 있는지 확인한 뒤 시작하게 함
- **멈춘 실행 찾기**: 실행이 도중에 끊기면 단계가 그대로 남음. 이슈 담당의 정기 실행이 "이력"의 마지막 줄 뒤로 진행이 없는 레포를 찾아 다시 넘기거나 사람에게 알리게 함
- **리뷰 회차의 상한**: 같은 지적이 3회차에도 열려 있으면 스킬이 미결 사항으로 올림. 회차마다 새 지적이 나와 리뷰가 이어지는 경우에 몇 회차에서 사람에게 알릴지

## 환경

환경마다 다른 것은 [환경 문서](references/environment.md) 한 장에 모아 둡니다. 스킬과 단계 문서는 도구 이름을 직접 적지 않고 이 문서의 절을 가리킵니다.

| 절 | 정하는 것 |
| --- | --- |
| 1. 이슈 | 호스트, 읽기·쓰기·검색·라벨·댓글에 쓸 도구, 본문 서식, 이슈를 만들 곳 |
| 2. PR | 호스트, 조회·생성·코멘트에 쓸 도구, 원본 저장소와 베이스 브랜치 |
| 3. 대화 | 요청 원문을 읽는 곳, 사람에게 확인을 요청하는 수단 |
| 4. 관계자 | 요청자, 결정할 사람, 대상 서비스의 담당을 찾는 곳 |
| 5. 이슈 상태 | 호스트의 이슈 상태를 누가 언제 바꾸는가 |

이 배포판의 값은 GitHub 기준입니다. Jira·Bitbucket·Teams나 Slack을 쓰는 환경에서는 이 파일만 그 환경의 내용으로 바꾸고 절의 제목과 번호는 그대로 둡니다. 플러그인을 고칠 수 없으면 봇의 지침이나 프로젝트 문서에 같은 항목을 적습니다. 지침과 프로젝트 문서가 이 문서보다 우선하고, 어디에도 없는 항목은 세션에 있는 도구로 진행합니다.

## 이슈를 만들 때

`create-issue`가 [이슈 템플릿](references/issue-template.md)의 "요청" 절(요청자와 요청일, 요청이 온 곳, 관계자, 원하는 결과, 하지 않을 것, 배경, 기한)을 채워 만듭니다. 요청 원문은 본문에 붙이지 않고 정리해 적습니다. 만들기 전에 같은 요청의 열린 이슈가 있는지 검색하고, 요청이 업무 범위에 드는지는 판정하지 않습니다. 결함 제보에 현상, 기대한 결과, 발생 환경이 빠져 있으면 이슈를 만들고 빠진 것을 미결 사항에 질문으로 적습니다. 그 질문을 실제로 물을지는 검토 단계가 정합니다. 직접 만들 때도 "요청" 절만 채우면 됩니다. 템플릿 없이 쓴 이슈도 받으며, 첫 실행이 기존 본문을 "요청" 절로 정리해 템플릿으로 바꿉니다.
