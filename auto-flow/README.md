# auto-flow

이슈 하나를 검토중, 검토완료, 개발완료, 완료 순서로 진행하는 플러그인입니다. 계획과 진행은 이슈 본문에, 구현 결과와 리뷰는 PR에 기록하므로, 다음 실행자는 사람이든 봇이든 이슈와 PR만 읽고 이어 갑니다. 본문 첫 줄의 상태가 지금 누가 본문을 고칠 차례인지를 정하고, 상태마다 본문을 고치는 스킬은 하나입니다. 훅이 없어 스킬을 호출할 때만 동작합니다.

| 스킬 | 다루는 이슈 | 하는 일 | 쓰는 쪽 |
| --- | --- | --- | --- |
| `create-issue` | 아직 없는 이슈 | 요청을 받아 템플릿을 적용한 이슈를 만들고 멈춤. 원하는 결과가 불분명하면 만들지 않고 요청자에게 물을 질문을 돌려주며, 같은 요청의 열린 이슈가 있으면 그 이슈를 알림 | 커뮤니케이션 봇, 직접 쓰는 사용자 |
| `plan-issue` | 검토중 | 요청을 번호 붙인 완료 조건으로 만들고, 누가 어떤 순서로 무엇을 하는지와 모든 레포의 계획을 씀. 미결 사항이 없어지면 바뀐 정책을 위키에 반영하고 검토완료로 바꿈 | 계획 봇 |
| `resolve-issue` | 검토완료 | 계획이 지금도 맞는지 확인하고 "진행" 표의 순서대로 한 행씩 구현·검증해 PR을 올리고, 사용자가 할 일은 요청한 뒤 멈춤. 계획이 맞지 않으면 미결 사항에 행을 더해 검토중으로 되돌리고, 마지막 행 뒤 개발완료로 바꿈 | 개발 봇 |
| `fix-issue` | PR이 열려 있는 이슈 | PR 코멘트 가운데 변경을 요구하는 의견을 이전 맥락과 코드로 검토해 고치거나, 이유를 적어 고치지 않음. 답은 PR에 남김 | 수정 봇 |
| `close-issue` | 개발완료 | 머지와 사람의 확인을 본문에 반영하고, 모두 끝났으면 완료로 바꿈 | 정리 봇 |
| `review-issue` | 요청받은 PR | 한 레포의 PR을 리뷰해 지적을 PR 코멘트로 남김. 요청받았을 때만 수행함 | 직접 쓰는 사용자, 리뷰 봇 |
| `run-issue` | 검토중, 검토완료 | 한 세션에서 검토와 개발을 차례로 이어 가다가 사람을 기다리는 지점에서 멈춤 | 직접 쓰는 사용자 |

## 설치

```
/plugin marketplace add argon1025/my-claude-plugin-market
/plugin install auto-flow@my-claude-plugin-market
```

같은 마켓의 plan-workflow와 pr-workflow를 설치하지 않은 상태에서 씁니다. plan-workflow의 세션 훅은 계획을 저장소의 `plan.md`에 기록하라고 주입하고, 두 플러그인의 스킬은 "계획 세워줘", "PR 리뷰해줘" 같은 요청에 auto-flow의 스킬과 함께 반응합니다.

## 전제 조건

- **이슈·PR 도구**: 이슈와 PR을 읽고 쓸 도구가 세션에 있어야 함. 이 배포판의 [환경 문서](references/environment.md)는 GitHub와 `gh` 기준임. 해당 호스트를 다룰 도구가 없으면 스킬이 시작하지 않고 그 사실을 알림
- **저장소 체크아웃**: 개발, 수정, 리뷰는 대상 레포의 체크아웃에서 수행함. 검토는 계획할 레포의 코드를 읽을 수 있어야 함
- **위키(선택)**: 세션에 위키 문서가 있으면 계획과 리뷰의 근거로 읽음. 검토 단계는 검토완료로 바꾸기 직전에, 그 계획에서 바뀌거나 새로 정해진 정책을 위키에 반영함. 반영에는 같은 마켓의 agent-wiki(`add`)를 쓰고, 쓸 수 없으면 건너뛴 뒤 그 사실을 알림

## 루프

| 상태 | 본문을 고치는 스킬 | 하는 일 | 넘어가는 조건 |
| --- | --- | --- | --- |
| 검토중 | `plan-issue` | 이슈 전체 계획과 레포별 계획을 쓰고 미결 사항을 관리함 | 미결 사항이 0건이고 끝내는 조건을 채우면, 바뀐 정책을 위키에 반영하고 검토완료로 |
| 검토완료 | `resolve-issue` | "진행" 표의 순서대로 구현·검증해 PR을 올리고, 사용자가 할 일을 요청함 | 레포 행은 PR을 올렸고 사용자 행은 완료면 개발완료로 |
| 개발완료 | `close-issue` | 머지와 사람의 확인을 본문에 반영함 | 모든 PR이 머지되고 확인이 끝나면 완료로 |
| 완료 | 없음 | | |

- **상태가 차례를 정함**: 스킬은 자기 상태가 아닌 이슈를 고치지 않고 멈춤. 봇끼리 일을 넘기는 메시지가 필요 없고, 같은 본문을 두 실행이 동시에 저장하지 않음
- **검토중으로 되돌리기**: 개발, 수정, 정리 가운데 어느 단계든 계획을 바꿔야 풀리는 문제를 만나면 미결 사항에 행을 더하고 상태를 검토중으로 바꿈
- **PR에서 일하는 스킬**: `fix-issue`와 `review-issue`는 PR 코멘트로 일하고 본문을 고치지 않음
- **한 번에 한 행**: 여러 레포에 걸친 이슈도 한 실행이 "진행" 표의 순서대로 맡음. 한 행이 끝나면 할 수 있는 다음 행을 이어 가고, 앞 PR의 머지나 사용자의 실행을 기다려야 하면 멈춤
- **위키는 계획이 끝날 때**: 정책을 바꾸거나 새로 정한 완료 조건은 구현 전에 위키에 반영함. 다른 단계는 위키를 읽기만 함
- **담당자가 자기 자신인 이슈만**: 스킬은 시작할 때 이슈의 담당자를 확인하고, 다른 사람의 이슈는 고치지 않음. 같은 플러그인을 여러 사람이 함께 쓸 수 있음

사람을 기다리는 지점은 네 곳입니다. 미결 사항의 답, 사용자가 하는 단계(배포, SQL 실행 등), PR 머지, 사람이 확인하기로 한 완료 조건입니다. 계획 전체의 승인과 PR 게시 전의 승인은 받지 않습니다. 스킬은 PR을 승인하거나 머지하지 않고, 호스트의 이슈 상태(이슈 닫기, 워크플로 전환)도 환경 문서가 정하지 않는 한 바꾸지 않습니다.

## 이슈 본문

본문은 상태 줄과 여덟 절입니다. 사람은 위에서 "진행"까지만 읽으면 됩니다.

| 절 | 담는 것 |
| --- | --- |
| 상태 줄 | 검토중, 검토완료, 개발완료, 완료 중 하나 |
| 요청 | 무엇을 바꾸는지 한 줄 |
| 완료 조건 | 요구, 하지 않을 것, 결정, 바뀌는 정책을 한 표에. 행마다 번호와 상태(확정, 통과) |
| 미결 사항 | 답을 받아야 정할 수 있는 것. 행마다 내용, 권장안, 답변, 선택 이유 |
| 진행 | 레포와 사용자가 어떤 순서로 무엇을 하는지, 시작 조건, 상태, PR. 운영 환경의 일은 넣지 않음 |
| 레포별 계획 | 레포마다 현재 동작과 바꿀 내용 |
| 확인 방법과 근거 | 완료 조건의 번호마다 확인 방법과 기록(근거, 답, 위키 반영, 확인 결과) |
| 세부 담당자 정보 | 역할, 이름, 근거. 요구사항 이슈와 관련 이슈의 담당자에서 찾음 |
| 관련 자료 | 요구사항 이슈, 규격, 관련 이슈의 링크. 요청 원문은 붙이지 않음 |

미결 사항의 답은 답하는 사람이 그 행의 답변 칸에 `{이름}: {답}`으로 직접 적습니다. 답이 채워지면 검토 단계가 완료 조건에 반영하고 그 행을 지웁니다. 스킬은 행마다 답할 사람을 지정하지 않고, 알리는 댓글이나 멘션도 남기지 않습니다. 구현 결과, 실행한 검증, 리뷰 지적은 본문에 적지 않고 PR에 둡니다. 사람이 실행할 SQL도 본문에 적지 않고 그 데이터를 가진 레포에 파일로 올려 PR로 리뷰받습니다. 이슈가 맡는 범위는 개발 브랜치 머지와 검증 환경 반영·확인까지이며, 운영 환경의 배포와 데이터 반영은 계획에 넣지 않습니다. 형식은 [이슈 템플릿](references/issue-template.md)에 있습니다.

## 호출

`create-issue`에는 요청 원문을, 나머지 스킬에는 이슈 키나 URL을 함께 줍니다. `fix-issue`와 `review-issue`는 레포를 함께 줄 수 있습니다.

| 런타임 | 예 |
| --- | --- |
| Claude Code | `/auto-flow:create-issue` 뒤에 요청 원문, `/auto-flow:run-issue ABC-123`, `/auto-flow:review-issue ABC-123 shop-api` |
| Codex | `$` 선택기에서 auto-flow의 `run-issue`를 고른 뒤 `ABC-123`을 적음 |

"ABC-123 진행해줘", "이 이슈 리뷰해줘"처럼 말로 요청해도 해당 스킬이 선택됩니다.

## 봇 구성

스킬은 환경을 가정하지 않으므로 누가 어느 스킬을 부를지는 쓰는 쪽이 정합니다.

| 구성 | 부르는 스킬 |
| --- | --- |
| 직접 호출 | 사용자가 `run-issue`로 한 세션에서 검토와 개발을 이어 감. 리뷰가 필요하면 다른 세션에서 `review-issue`를 부름 |
| 상태별 봇(권장) | 계획 봇이 `plan-issue`, 개발 봇이 `resolve-issue`, 수정 봇이 `fix-issue`, 정리 봇이 `close-issue`를 각자의 주기로 부름 |
| 리뷰 봇, 커뮤니케이션 봇을 더한 구성 | 위 구성에 더해, 리뷰 봇이 요청받은 PR에 `review-issue`를 부르고, 커뮤니케이션 봇이 `create-issue`로 이슈를 만들며 미결 사항의 답을 받아 옴 |

### 상태별 봇

주기마다 자기 상태의 이슈를 찾아 일하는 봇입니다.

| 봇 | 스킬 | 고르는 이슈 | 한 번의 실행이 끝나는 곳 |
| --- | --- | --- | --- |
| 계획 | `plan-issue` | 검토중 | 미결 사항을 남기고 멈추거나, 바뀐 정책을 위키에 반영하고 검토완료로 바꿈 |
| 개발 | `resolve-issue` | 검토완료 | 할 수 있는 행의 PR을 올린 뒤, 앞 PR의 머지나 사용자의 실행을 기다리며 멈춤. 마지막 행 뒤 개발완료로 바꿈 |
| 수정 | `fix-issue` | 검토완료나 개발완료이고 열린 PR이 있는 이슈 | 변경을 요구하는 코멘트마다 고치거나, 고치지 않는 이유를 PR에 답함 |
| 정리 | `close-issue` | 개발완료 | 머지와 사람의 확인을 반영하고, 모두 끝났으면 완료로 바꿈 |

주기 없이 필요할 때만 일하는 봇을 더 둘 수 있습니다.

| 봇 | 하는 일 | 시작하는 때 |
| --- | --- | --- |
| 리뷰 | `review-issue`로 한 레포의 PR을 리뷰해 지적을 PR 코멘트로 남김. 지적의 반영은 수정 봇이 함 | 사용자가 PR을 지정해 요청했을 때 |
| 커뮤니케이션 | 받은 요청을 `create-issue`로 이슈로 만듦. 미결 사항을 "세부 담당자 정보"의 사람에게 묻고, 받은 답을 그 행의 답변·선택 이유 칸에 적음. 요청을 읽어 오고 사람에게 묻는 수단은 플러그인 밖임 | 요청을 받았을 때, 미결 사항에 답이 빈 행이 있을 때 |

- **넘김이 없음**: 봇끼리 메시지를 주고받지 않음. 각 봇은 자기 주기에 자기 상태의 이슈를 찾아 일하고 끝냄. 차례는 본문의 상태 줄이 정함
- **담당자가 자기 자신인 이슈만**: 봇은 자기 계정이 담당자인 이슈만 다룸. 여러 사람이 같은 프로젝트에서 각자의 봇을 돌려도 서로의 이슈를 고치지 않음
- **이슈의 개발은 한 봇이**: 여러 레포에 걸친 이슈도 개발 봇 하나가 "진행" 표의 순서대로 맡음. 레포마다 새 컨텍스트(워커, 서브에이전트)에 구현을 맡기더라도 본문은 개발 봇 하나만 저장함. 레포 담당자 봇을 따로 두지 않음
- **깨어날 때마다 이슈에서 다시 시작**: 봇은 앞선 대화의 기억에 기대지 않고 이슈와 PR을 읽고 시작함. 한 대화를 오래 이어 가면 읽을 것이 계속 늘어남
- **리뷰는 요청받았을 때만**: 어느 봇도 리뷰를 자동으로 부르지 않음. 리뷰 없이 머지되는 PR도 정리 봇이 머지만 보고 마무리함. 리뷰는 구현한 봇과 다른 컨텍스트에서 수행함
- **미결 사항의 답은 답변 칸으로만**: 사람이든 커뮤니케이션 봇이든 답변·선택 이유 칸만 채움. 그 답을 완료 조건에 옮기는 일은 계획 봇의 다음 주기가 함

### 이슈 하나의 흐름

두 레포를 고치고 사람이 SQL을 실행해야 하는 이슈를 예로 든 것입니다.

| 순서 | 누가 | 하는 일 | 끝난 뒤 상태 |
| --- | --- | --- | --- |
| 1 | 사용자나 커뮤니케이션 봇 | `create-issue`로 이슈를 만들고 담당자를 지정함 | 검토중 |
| 2 | 계획 봇 | 완료 조건과 "진행" 표를 쓰고, 정할 수 없는 것을 미결 사항에 권장안과 함께 적은 뒤 멈춤 | 검토중 |
| 3 | 사용자나 커뮤니케이션 봇 | 미결 사항의 답변 칸에 답을 적음 | 검토중 |
| 4 | 계획 봇 | 답을 완료 조건에 반영하고 그 행을 지움. 레포별 계획을 쓰고, 바뀐 정책을 위키에 반영함 | 검토완료 |
| 5 | 개발 봇 | 첫 레포에 SQL 파일을 더한 PR과 둘째 레포의 PR을 차례로 올리고, 머지를 기다리며 멈춤 | 검토완료 |
| 6 | 사용자, 수정 봇 | PR에 코멘트가 달리면 수정 봇이 고치거나 이유를 답함. 사용자가 머지하고 검증 환경에 배포함 | 검토완료 |
| 7 | 개발 봇 | 머지를 반영하고, 머지된 SQL 파일의 위치와 실행 순서, 기대값을 적어 실행을 요청한 뒤 멈춤 | 검토완료 |
| 8 | 사용자 | SQL을 실행하고, 그 행을 완료로 바꾸거나 결과를 봇에게 알림 | 검토완료 |
| 9 | 개발 봇 | 알려 준 결과를 기대값과 맞춰 보고 그 행을 완료로 바꿈 | 개발완료 |
| 10 | 사용자, 정리 봇 | 사용자가 확인한 것을 기록 칸에 적으면 정리 봇이 완료 조건을 통과로 바꿈 | 완료 |

어느 단계든 계획을 바꿔야 풀리는 문제를 만나면 미결 사항에 행을 더하고 검토중으로 되돌리며, 2번부터 다시 이어집니다.

### 봇의 지침

봇마다 다른 것은 봇의 지침에 둡니다. 아래는 상태별 봇의 지침 예시이며, `{}` 안은 환경에 맞게 채웁니다.

```text
{주기}마다 아래를 수행한다.
1. auto-flow 환경 문서 1절의 "루프가 다루는 이슈"를 찾는다. 담당자가 자기 자신인 이슈만 나온다.
2. 본문 첫 줄의 상태가 {맡은 상태}인 이슈만 고른다. 이 봇이 이미 수행 중인 이슈는 건너뛴다.
3. 이슈마다 새 대화에서 {스킬}을 그 이슈에 수행한다. 앞선 대화를 이어 쓰지 않는다.
4. 스킬의 실행 보고를 {사용자에게 전하는 곳}에 전한다. 다른 봇을 부르지 않는다.
```

| 봇 | 맡은 상태 | 스킬 | 지침에 더 둘 것 |
| --- | --- | --- | --- |
| 계획 | 검토중 | `plan-issue` | 계획할 레포의 체크아웃 경로. 위키에 반영하는 수단을 쓸 수 있는지 |
| 개발 | 검토완료 | `resolve-issue` | 레포마다의 체크아웃 경로와, 레포마다 새 컨텍스트에 구현을 맡기는 방법. 사용자가 실행을 마쳤다고 알리는 곳 |
| 수정 | 검토완료, 개발완료 | `fix-issue` | 레포마다의 체크아웃 경로. "진행" 표에 PR 올림인 행이 있는 이슈만 고르게 함 |
| 정리 | 개발완료 | `close-issue` | 완료로 바꾼 뒤 호스트의 이슈 상태를 바꿀지 |
| 리뷰 | 없음 | `review-issue` | 주기를 두지 않고 요청받았을 때만 수행함. 구현한 봇과 다른 컨텍스트 |
| 커뮤니케이션 | 없음 | `create-issue` | 요청을 읽어 오는 곳, 미결 사항을 누구에게 어떤 수단으로 물을지. 본문에서는 답변·선택 이유 칸만 고침 |

- **겹쳐 실행하지 않기**: 본문에는 지금 수행 중이라는 표시가 없음. 같은 이슈를 수행 중인 자기 실행이 있으면 새로 시작하지 않게 함
- **알림**: 스킬은 미결 사항이나 사용자가 할 일을 댓글이나 멘션으로 알리지 않음. 실행 보고를 전하는 곳을 지침에 정하거나, 커뮤니케이션 봇이 맡음

## 환경

환경마다 다른 것은 [환경 문서](references/environment.md) 한 장에 모아 둡니다. 스킬과 단계 문서는 도구 이름을 직접 적지 않고 이 문서의 절을 가리킵니다.

| 절 | 정하는 것 |
| --- | --- |
| 1. 이슈 | 호스트, 읽기·쓰기·검색·라벨·댓글에 쓸 도구, 본문 서식, 이슈를 만들 곳 |
| 2. PR | 호스트, 조회·생성·코멘트·답글에 쓸 도구, 원본 저장소와 베이스 브랜치 |
| 3. 대화 | 요청 원문을 읽는 곳, 사람에게 알리는 수단 |
| 4. 관계자 | "세부 담당자 정보"에 적을 사람을 찾는 곳 |
| 5. 이슈 상태 | 호스트의 이슈 상태를 누가 언제 바꾸는가 |

이 배포판의 값은 GitHub 기준입니다. Jira·Bitbucket·Teams나 Slack을 쓰는 환경에서는 이 파일만 그 환경의 내용으로 바꾸고 절의 제목과 번호는 그대로 둡니다. 플러그인을 고칠 수 없으면 봇의 지침이나 프로젝트 문서에 같은 항목을 적습니다. 지침과 프로젝트 문서가 이 문서보다 우선하고, 어디에도 없는 항목은 세션에 있는 도구로 진행합니다.

## 이슈를 만들 때

`create-issue`가 [이슈 템플릿](references/issue-template.md)을 적용해 "요청"의 한 줄, 요청의 원하는 결과와 하지 않을 것을 옮긴 완료 조건의 행, "세부 담당자 정보", "관련 자료"의 링크를 채워 만듭니다. 담당자는 요청에 적힌 요구사항 이슈와 관련 이슈의 담당자에서 찾습니다. 요청 원문은 본문에도 댓글에도 붙이지 않습니다. 만들기 전에 같은 요청의 열린 이슈가 있는지 검색하고, 요청이 업무 범위에 드는지는 판정하지 않습니다. 결함 제보에 현상, 기대한 결과, 발생 환경이 빠져 있으면 이슈를 만들고 빠진 것을 미결 사항에 적습니다. 그 질문을 실제로 물을지는 검토 단계가 정합니다. 템플릿 없이 쓴 이슈도 받으며, 검토 단계가 기존 본문의 요구를 완료 조건으로 옮기고 본문을 템플릿으로 바꿉니다. 바꾸기 전의 본문은 호스트의 변경 이력에 남습니다.
