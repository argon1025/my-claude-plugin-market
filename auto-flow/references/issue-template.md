# 이슈 템플릿

이슈 본문 하나에 요청, 완료 조건, 진행, 계획을 둡니다. 사람은 위에서 "진행"까지만 읽으면 무엇이 정해졌고 누가 무엇을 할 차례인지 알 수 있어야 하고, 다른 세션의 에이전트는 이 본문만 읽고 이어 갈 수 있어야 합니다. 구현 결과와 리뷰는 본문이 아니라 PR에 둡니다.

| 알고 싶은 것 | 보는 곳 |
| --- | --- |
| 지금 누가 일할 차례인가 | 맨 위의 상태 줄 |
| 무엇이 정해졌고 무엇이 아직 정해지지 않았는가 | "완료 조건" |
| 어느 순서로 누가 무엇을 하고 어디까지 왔는가 | "진행" |
| 무엇을 어떻게 바꾸는가 | "레포별 계획" |
| 왜 그렇게 정했고 무엇으로 확인하는가 | "확인 방법과 근거" |
| 구현 결과, 실행한 검증, 리뷰 | 그 레포의 PR |

쓰는 규칙은 네 가지입니다.

- **한 곳에만**: 같은 사실은 한 곳에만 적음. 요구, 하지 않을 것, 질문, 답, 결정, 바뀌는 정책은 모두 "완료 조건"의 한 행과 "확인 방법과 근거"의 같은 번호 행에 모음
- **절은 그대로**: 상태 줄과 아래 일곱 절을 이 순서로 두고, 내용이 없는 절도 제목과 표의 머리줄은 남김
- **고를 수 있는 값은 머리줄에**: 상태처럼 값이 정해진 칸은 머리줄의 괄호에 고를 수 있는 값을 적고, 칸에는 그 가운데 하나만 적음. 표의 빈 칸은 `-`로 채움
- **호스트의 서식으로**: 아래는 마크다운임. 마크다운을 쓰지 않는 호스트에서는 같은 구조를 그 호스트의 문법으로 옮김. Jira 위키 문법이면 절 제목 `h2.`, 레포 제목 `h3.`, 목록 `*`, 굵게 `*글*`, 코드 `{{글}}`, 표의 머리줄 `||`와 행 `|`, 칸 안의 줄바꿈 `\\`를 씀

```markdown
상태(검토중, 검토완료, 개발완료, 완료): 검토중

## 요청
{무엇을 바꾸는지 한 줄}

## 완료 조건
| 번호 | 상태(미정, 확정, 통과) | 내용 |
| --- | --- | --- |

## 진행
| 순서 | 대상 | 할 일 | 시작 조건 | 상태(대기, 진행 중, PR 올림, 머지됨, 완료) | PR |
| --- | --- | --- | --- | --- | --- |

## 레포별 계획

## 확인 방법과 근거
| 번호 | 확인 방법 | 기록 |
| --- | --- | --- |

## 세부 담당자 정보
| 역할 | 이름 |
| --- | --- |

## 관련 자료
- 요청 원문:
```

## 절마다 적는 것

### 상태 줄

본문의 첫 줄입니다. 값마다 본문을 고치는 스킬이 하나씩 정해져 있어, 이 줄이 지금 누가 일할 차례인지를 정합니다. 맡는 스킬과 넘어가는 조건은 [공통 절차](common.md) 2절에 있습니다.

| 값 | 뜻 |
| --- | --- |
| 검토중 | 계획을 세우는 중이거나 미정 행의 답을 기다림 |
| 검토완료 | 계획이 끝남. "진행" 표의 순서대로 개발함 |
| 개발완료 | "진행" 표의 모든 행이 PR을 올렸거나 끝남. 머지와 사람의 확인을 기다림 |
| 완료 | 끝남 |

### 요청

무엇을 바꾸는지 한 줄로 적습니다.

```markdown
## 요청
주문 내역 화면에 환불 상태 필터 추가
```

- **한 줄만**: 원하는 결과와 하지 않을 것은 여기에 적지 않고 "완료 조건"의 행으로 적음. 배경과 요청자가 본 원인은 원문에 두고, 계획에 필요한 사실만 "레포별 계획"의 현재 동작에 적음
- **호스트가 관리하는 값**: 요청자, 요청일, 기한처럼 이슈 호스트의 필드에 있는 값은 본문에 다시 적지 않음
- **원문**: 본문에 붙이지 않고 "관련 자료"에 위치를 적음

### 완료 조건

이 이슈가 끝났다고 말하려면 참이어야 하는 것과, 그것을 정하려고 물어야 하는 것을 한 표에 적습니다. 요청의 원하는 결과, 하지 않을 것, 사람이 내린 결정, 바뀌는 정책, 레포 사이에 주고받는 값이 모두 이 표의 행입니다.

```markdown
| 번호 | 상태(미정, 확정, 통과) | 내용 |
| --- | --- | --- |
| AC-1 | 통과 | 환불 요청은 결제 후 7일 안에만 접수되어야 한다 |
| AC-2 | 확정 | 주문 응답의 `refundStatus`에는 환불 상태 코드가 실려야 한다 |
| AC-3 | 미정 | 부분 환불된 주문을 환불 상태 필터에 포함할지 |
| AC-4 | 확정 | 환불 알림 메일의 문구는 이 이슈에서 바꾸지 않는다 |
```

- **상태**: 셋 중 하나만 적음

  | 값 | 뜻 |
  | --- | --- |
  | 미정 | 답을 받아야 정할 수 있음. 한 행이라도 있으면 이슈는 검토중임 |
  | 확정 | 정해졌고 아직 확인하지 않았거나, 확인할 것이 없음 |
  | 통과 | "확인 방법과 근거"에 적은 방법대로 확인됨 |

- **내용**: 한 줄로 적음. 미정이면 질문을, 확정과 통과면 요구를 "해야 한다" 또는 "해서는 안 된다"로 적음. 하지 않을 것은 "…은 이 이슈에서 바꾸지 않는다"로 적음. "할 수 있다"는 허용인지 능력인지 갈리므로 쓰지 않음. 값, 문구, 식별자, 오류 메시지는 요청에 적힌 그대로 옮김
- **내용에 적지 않는 것**: 질문의 배경과 선택지, 기존 기준, 답, 정한 사람, 확인 방법과 결과는 "확인 방법과 근거"의 같은 번호 행에 적음
- **행으로 만드는 것**: 요청에서 나온 요구 하나에 행 하나. 나온 곳이 없는 조건을 관행이나 추측으로 더하지 않음. 그 안에서의 구현 방식(어느 클래스와 메서드, 내부 구조, 이름)은 행으로 만들지 않고 "레포별 계획"의 바꿀 내용에 적음
- **번호**: `AC-1`부터 매기고 다시 매기지 않으며, 지운 번호를 다시 쓰지 않음. 미정 행이 확정으로 바뀌어도 번호는 그대로임
- **바꾸는 쪽**: 행을 만들고 미정을 확정으로 바꾸는 것은 검토 단계임. 이미 충족된 요구를 근거와 함께 통과로 적는 것도 검토 단계임. 확정을 통과로 바꾸는 것은 그 조건을 확인한 개발 단계와, 사람의 확인을 반영하는 정리 단계임. 개발·수정·정리 단계는 계획을 바꿔야 풀리는 문제를 만났을 때 미정 행을 더할 수 있음

### 진행

누가 어떤 순서로 무엇을 하는지와 어디까지 왔는지를 한 표에 적습니다. 레포가 하는 일과 사람이 직접 하는 일을 같은 표에 순서대로 둡니다.

```markdown
| 순서 | 대상 | 할 일 | 시작 조건 | 상태(대기, 진행 중, PR 올림, 머지됨, 완료) | PR |
| --- | --- | --- | --- | --- | --- |
| 1 | shop-api | 주문 응답에 환불 상태 추가 | - | 머지됨 | #128 |
| 2 | 사용자 | 스테이징에 shop-api 배포 | 1번 머지 | 완료 | - |
| 3 | shop-web | 환불 상태 필터 추가 | 2번 완료 | 진행 중 | - |
```

- **대상**: 레포 이름, 또는 사람이 직접 하는 일이면 `사용자`. 배포, 발행, SQL 실행, 설정 변경처럼 코드로 올리지 않는 일이 사용자 행임
- **할 일**: 한 줄. 자세한 내용은 "레포별 계획"에 둠
- **시작 조건**: `-`이면 앞 행들이 PR을 올렸거나 끝난 뒤에 시작함. 앞 행의 머지나 완료가 있어야 하면 `1번 머지`, `2번 완료`처럼 적고, 다른 이슈에 걸려 있으면 그 이슈와 조건을 적음
- **상태**: 다섯 중 하나만 적음

  | 값 | 뜻 |
  | --- | --- |
  | 대기 | 시작하지 않음 |
  | 진행 중 | 레포 행은 구현하는 중, 사용자 행은 요청했고 실행을 기다리는 중 |
  | PR 올림 | PR이 열려 있음 |
  | 머지됨 | PR이 베이스 브랜치에 머지됨 |
  | 완료 | PR 없이 끝남. 사용자 행과, 산출물이 PR이 아닌 레포 행에 씀 |

- **PR**: PR의 번호나 위치. 없으면 `-`
- **순서**: 값을 정의하는 레포를 받아 쓰는 레포보다 앞에 둠. 한 이슈에서는 한 번에 한 행만 진행함
- **바꿀 것이 없는 레포**: 행을 만들지 않음
- **바꾸는 쪽**: 행을 만드는 것은 검토 단계, 상태와 PR 칸을 채우는 것은 개발 단계, 머지를 확인해 적는 것은 개발 단계와 정리 단계임. 사용자 행은 실행한 사람이 직접 완료로 바꿔도 됨

### 레포별 계획

"진행" 표의 레포마다 절 하나를, 먼저 시작하는 레포부터 둡니다.

```markdown
### shop-api
- 기준 커밋: {계획을 쓸 때 본 커밋}
- 현재 동작: {진입점에서 소비자까지, 코드 위치와 함께}
- 바꿀 내용: {무엇을 어떤 모양으로 바꾸는지} (AC-2)
```

- **현재 동작**: 요구가 닿는 경로를 코드 위치와 함께 적음. 문서나 요청의 문장만으로 적지 않음
- **바꿀 내용**: 구현 코드를 미리 쓰지 않음. 여러 가지면 목록으로 나누고 항목마다 관련 완료 조건의 번호를 괄호에 적음. 그 안에서 에이전트가 정한 구현 방식과 이유도 여기에 적음
- **적지 않는 것**: 브랜치, 실행한 명령과 출력, 변경 전부터 실패하던 검증, 범위 밖에서 본 것은 PR 본문에 둠. 확인 방법은 "확인 방법과 근거"에 둠

사용자 행 가운데 실행할 내용이 한 줄로 끝나지 않는 것(SQL, 등록할 값)은 그 행의 절을 따로 둡니다. 데이터를 바꾸는 것은 [데이터 변경 체크리스트](checklists/data-change.md)를 따릅니다.

```markdown
### 사용자: 스테이징에 환불 상태 코드 등록
- 사전 확인: {실행 전에 볼 조회와 기대값. 기대와 다르면 멈춤}
- 실행할 내용: {그대로 실행할 수 있는 SQL이나 등록할 값}
- 사후 확인: {실행 뒤에 볼 조회와 기대값}
- 되돌리는 방법:
```

### 확인 방법과 근거

완료 조건의 행마다 무엇으로 확인하는지와, 그 행이 왜 그렇게 정해졌는지를 적습니다. 완료 조건 표를 짧게 두려고 나눈 절이므로 번호로 짝을 맞춥니다.

```markdown
| 번호 | 확인 방법 | 기록 |
| --- | --- | --- |
| AC-1 | 개발: 환불 접수 서비스 테스트 | 계획 근거: 기존에는 기간 제한이 없음(환불 정책 문서 2장)<br>홍길동 답: 7일로 함<br>개발 확인: PR #128 |
| AC-3 | - | 계획 질문: 지금은 전액 환불만 `REFUNDED`로 저장함. 안 1 포함(목록에 부분 환불도 나옴), 안 2 제외(지금과 같음). 추천은 안 1 |
```

- **번호**: 완료 조건의 번호. 확인 방법도 기록도 없는 행은 만들지 않음
- **확인 방법**: 누가 무엇을 보면 통과와 실패가 갈리는지를 한 줄로 적음. 개발 단계가 PR을 올리기 전에 실행하는 확인은 `개발: {테스트나 명령이 가르는 것}`, 사람이 보는 확인은 `사용자: {무엇을 어떤 데이터로 보고 무엇이 보이면 통과인지}`로 적음. 확인할 것이 없는 행은 `-`. 명령 전체와 출력은 PR 본문에 둠
- **기록**: `{누가} {무엇}: {내용}`을 한 줄에 하나씩 적음. 누가는 사람의 이름이나 단계의 이름(계획, 개발, 수정, 정리)이고, 무엇은 질문, 근거, 답, 확인 중 하나임

  | 줄 | 적는 것 |
  | --- | --- |
  | `{단계} 질문:` | 미정 행의 확인된 사실, 고를 수 있는 안과 각 안의 결과, 추천이 있으면 추천 |
  | `계획 근거:` | 요청의 어느 대목에서 나왔는지, 기존 기준과 그 출처(정책 문서, 코드 위치) |
  | `{이름} 답:` | 미정 행의 답. 답하는 사람이 여기에 직접 적음 |
  | `{단계} 확인:` | 확인한 결과가 있는 곳(PR, 코드 위치) |
  | `{이름} 확인:` | 사람이 본 것 |

- **적지 않는 것**: 무엇을 언제 했는지 같은 진행 경과는 적지 않음. 이 칸에는 그 조건의 질문, 근거, 답, 확인만 둠
- **생성 시 확인**: 이슈를 만들 때 결함 제보에서 빠진 정보를 미정 행으로 적었다는 표시임. 기록 칸에 "생성 시 확인"이라고 적혀 있으면, 실제로 물을지는 검토 단계가 가름

### 세부 담당자 정보

이 이슈에 관계된 사람을 역할과 이름으로 적습니다.

```markdown
| 역할 | 이름 |
| --- | --- |
| 기획 | 홍길동 |
| 개발 | 김철수 |
```

- **찾는 곳**: [환경](environment.md) 4절. 찾지 못한 역할은 행을 만들지 않고, 커밋 이력이나 과거 이슈로 추정하지 않음
- **쓰임**: 미정 행을 누구에게 물을지는 이 표를 보고 사람이나 알림을 맡은 실행자가 정함. 완료 조건의 행마다 답할 사람을 지정하지 않음

### 관련 자료

```markdown
- 요청 원문: {원문이 있는 대화, 메시지, 댓글의 위치}
- {규격, 기획서, 관련 이슈의 링크}
```

- **요청 원문**: 완료 조건이 요청과 다르게 읽히면 원문이 기준임. 원문을 다시 볼 곳이 없으면(위치 없이 붙여 넣은 요청, 기존 본문을 덮어쓰는 변환) 원문을 `[auto-flow] 요청 원문`으로 시작하는 댓글로 먼저 남기고 그 댓글의 위치를 적음

## 템플릿이 없는 이슈

본문의 첫 줄이 상태 줄이 아닌 이슈는 본문을 위 구조로 바꿉니다. 원문은 본문에 남기지 않으므로 아래를 지킵니다.

- 기존 본문을 `[auto-flow] 요청 원문` 댓글로 먼저 남기고 "관련 자료"에 그 위치를 적음
- "요청"에 무엇을 바꾸는지 한 줄로 적고, 본문에 있던 링크와 첨부는 "관련 자료"로 옮김
- 댓글에서 이미 정해진 것은 완료 조건의 확정 행으로 적고, 기록 칸에 정한 사람과 그 댓글의 위치를 적음
- 요청자가 물은 것은 완료 조건의 미정 행으로 적음

`auto-flow` 라벨을 붙이고 상태를 검토중으로 둡니다. 나머지 행은 검토 단계가 채웁니다.
