# 리뷰 단계

한 레포의 PR이 머지돼도 되는지 점검하는 단계입니다. 요청받았을 때만 수행합니다. 다른 스킬이 이 단계를 부르지 않으며, 리뷰 없이 머지되는 PR도 있습니다. 대상은 세 가지입니다. 코드에 결함이 있는가, 변경이 완료 조건과 계획대로인가, PR 본문의 기록이 사실인가. 레포 하나를 단위로 수행하며 코드는 고치지 않습니다.

구현한 맥락을 물려받지 않은 쪽이 리뷰합니다. 구현한 세션이 이어서 리뷰하지 않습니다. 구현자의 설명과 "통과했다"는 기록은 확인할 주장으로 다룹니다.

이 단계는 PR에서 일합니다. 지적은 PR 코멘트로 남기고, 이슈 본문과 상태는 고치지 않습니다([공통 절차](common.md) 2·5절). 지적을 반영하는 일은 [수정](stage-fix.md)이 합니다.

## 1. 준비

- **스냅샷**: PR의 head 커밋과 베이스를 고정하고 그 커밋의 변경을 봄. 작업 트리가 아니라 그 커밋을 읽음
- **범위**: 재리뷰면 앞 리뷰 요약에 적힌 커밋 이후의 변경과, `[auto-flow 리뷰]` 지적 가운데 `[auto-flow 수정]` 답이 달린 것을 봄. 처음이면 전체 변경을 봄. 바이너리, lockfile, 순수 삭제·개명은 건너뛰고 건너뛴 것을 알림
- **읽을 것**: 이슈의 완료 조건과 "확인 방법과 근거", 이 레포의 "레포별 계획", PR 본문. 변경이 닿는 주제의 위키 문서(있을 때). [공통 체크리스트](checklists/common.md)와 해당 스택의 체크리스트([Java·Spring](checklists/java-spring.md), [NestJS](checklists/nestjs.md), [TypeScript·React](checklists/typescript-react.md)), 데이터를 바꾸는 산출물이면 [데이터 변경 체크리스트](checklists/data-change.md)
- **검증을 다시 돌릴 때**: head 커밋을 별도의 임시 체크아웃에 꺼내 실행함. 테스트가 잘못된 구현에서 실패하는지 보려고 그 체크아웃에서 변경을 되돌려 볼 수 있으며, 되돌린 것은 커밋하지 않고 체크아웃째 지움

## 2. 코드

변경을 파일별로 보며 아래를 찾습니다. 확인하지 못해 확신이 없는 것은 지적하지 않습니다.

- **버그**: 추가·수정된 코드 자체의 결함
- **사이드이펙트**: 이 PR이 그대로 나가면 달라지는 기존 동작. 바뀐 공개 시그니처, 응답 필드, 이벤트, 설정 키마다 기존 소비처를 검색해 확인함. 같은 API나 공용 코드를 부르는 다른 화면과 다른 레포도 봄
- **완료 조건이 실제로 성립하는가**: 이 PR이 구현하는 완료 조건마다 변경 뒤의 경로를 진입점에서 끝까지 따라가 봄. 이 PR이 고치지 않은 코드(기본값, 화면의 선택 처리, 뒤따르는 검사)가 그 조건이 만드는 상황에서 조건을 깨면 지적하고, 위치는 그 코드로 적음. 허용 범위나 규칙이 바뀌었는데 그 규칙을 설명하는 문구가 옛 내용으로 남았는지도 봄
- **계획과 다름**: 완료 조건이나 레포별 계획에 없는 동작이 들어갔거나, 계획한 것과 다르게 구현됨. PR 본문이 계획과 다르게 한 점으로 밝히고 완료 조건을 건드리지 않는 것은 지적하지 않음
- **구조**: 의미가 바뀐 변수·메서드의 이름이 그대로 남았는가. 새 타입의 위치가 기존 패키지의 의존 방향을 뒤집는가
- **위키의 정책**: 코드가 위키의 유효한 정책을 어기면 지적함. 위키는 고치지 않음

## 3. 기록의 사실 여부

아래는 에이전트가 반복해 틀린 지점입니다. PR 본문과 이슈에 적힌 내용을 실제와 대조합니다.

- **검증**: PR 본문에 적힌 검증이 실제로 실행된 것인가. 그 검증은 잘못 구현했을 때 실패하는가. 통과로 적힌 완료 조건이 실제로 확인된 것인가
- **영향 범위**: 바뀐 공용 코드의 다른 호출부가 빠지지 않았는가. PR 본문의 영향도에 빠진 소비처가 없는가
- **프레임워크 동작**: 변경이 기대는 프레임워크·라이브러리 동작이 확인된 것인가, 가정인 채로 남았는가
- **계획의 문장**: 레포별 계획의 현재 동작이 그 코드 위치에서 실제로 그런가. 코드는 맞고 계획의 문장만 틀렸으면 지적하지 않고 리뷰 요약에 한 줄로 알림

## 4. 등급과 코멘트

| 등급 | 기준 |
| --- | --- |
| Blocker | 그대로 나가면 기존 소비처나 사용자가 깨지거나, 새 기능이 오동작하거나 보안이 노출됨 |
| Bug | 잘못 동작하지만 위만큼 치명적이지 않음. 완료 조건을 가르는 유일한 검증이 잘못 구현해도 통과하는 경우도 여기에 듦 |
| 개선 | 결함이 아닌 설계·관례·성능 제안 |

- **지적 하나에 코멘트 하나**: `[auto-flow 리뷰] {등급} — {무엇이 왜 문제이고 어느 방향으로 고칠지}`를 한두 문장으로 씀. 코드 줄에 달 수 있으면 그 줄에 달고, 아니면 파일과 줄을 본문에 적음
- **재리뷰**: 답이 달린 지적마다 확인함. 고친 커밋에서 실제로 해결됐거나 고치지 않은 이유를 코드에서 확인해 받아들이면 그 스레드에 `[auto-flow 리뷰] 확인함`을 달고, 아니면 남은 이유를 적음. 같은 지적을 세 번째 리뷰에서도 받아들일 수 없으면 더 되풀이하지 않고 요약에 양쪽 근거를 적어 사람의 판단에 맡김
- **요약 코멘트**: 리뷰마다 `[auto-flow 리뷰] 요약`으로 시작하는 코멘트 하나를 남김. 리뷰한 head 커밋, 등급별 지적 수, 머지 전에 사람이 확인할 완료 조건을 적음. 지적이 없으면 "지적 없음"이라고 적음

## 5. 끝

실행 보고에 리뷰한 커밋, 등급별 지적과 위치를 적고 멈춥니다. PR을 승인하거나 머지하지 않으며, 머지할지는 사람이 정합니다.
