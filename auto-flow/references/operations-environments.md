# 운영 환경별 연결

호출 범위와 조직이 설정한 프로젝트·저장소·대화·배정처 안에서 필요한 절만 사용한다. 이 지침은 스케줄러를 설치하지 않는다. 주기와 담당은 각 환경의 호출자가 정한다.

## 사내 Teams 접수와 회신

- 단건은 지정한 원래 대화와 메시지부터 읽는다. 정기 접수 담당은 본인에게 온 1:1, 그룹의 본인·팀 멘션, 지정된 팀 채팅의 미처리 요청을 확인한다. 검색 결과는 대화를 찾는 용도로만 쓰고 Graph에서 원문, 인용한 메시지, 이어진 보충·정정, 이미 받은 답을 읽는다. 공유·종료·이미 해결된 문의는 새 개발 요청에 넣지 않는다.
- 연결된 `msgraph_api`의 `GET /chats/{chatId}/messages/{messageId}` 또는 대화 메시지 목록을 사용한다. 원문부터 회신까지 필요한 구간의 페이지를 읽는다. 링크 또는 chat ID와 message ID 쌍을 보존한다. 대화 본문은 요청의 근거로 취급하고 자격 증명·인증번호를 Jira나 답장에 옮기지 않는다.
- 정책 답변은 위키의 적용 조건·판본, 진행 사실은 Jira와 실제 PR·배포 기록을 대조한다. 팀에 명시적으로 개발을 요청하면 Jira 연결 대상이다. 원인 조사나 일반 문의로는 자동 추적을 시작하지 않는다.
- 답장·질문·결과 전송을 맡았을 때만 원래 채팅에 쓴다. 계약 소유자에게 묻는 경우는 지정된 소유자의 연락 경로를 사용한다. `teams_send_chat_message`에 해당 chat ID를 주고, 그룹에서 요청자에게 답하면 원문 멤버의 ID로 멘션한다. 1:1은 멘션을 생략한다. 응답의 메시지 ID와 대화를 다시 확인한다. 단독 요청으로 다른 채팅에 요약을 전송하지 않는다.

## 사내 Jira 추적과 상태

- 개발 등록은 지정 프로젝트에서 원문 링크와 요청·완료 조건으로 검색한다. 재제보는 닫힌 이슈도 포함한다. 자동 추적 대상에는 `auto-flow` 라벨을 추가하고 원래 메시지로 돌아갈 링크를 이슈에 남긴다. 기존 라벨·본문을 보존한다. 생성 요청에 가능한 필드를 함께 넣고, 응답 유실 후에는 같은 메시지와 조건으로 검색해 생성·라벨·연결 중 빠진 부분만 채운다.
- 입력 없는 진행 확인은 운영 대상 프로젝트에서 `labels = "auto-flow" AND statusCategory != Done`에 해당하는 전체 페이지를 읽는다. 이슈 키를 주면 라벨과 무관하게 해당 건만 조회한다. 안내 대상 확인의 출발점은 원래 요청자의 **아직 안내하지 않은 결과**다. 완료 이슈라도 안내가 남았으면 원래 문의와 연결된 이슈·PR을 조회한다.
- 현재 상태·조건별 근거와 프로젝트의 전환 기준을 읽고 `jira_get_transitions`에서 해당 이슈에 허용된 전환 ID를 확인한다. 전환 요청에는 그 ID를 쓰고 `jira_get_issue`와 변경 이력에서 도착 상태를 확인한다. 상태 이름이나 '완료'에 해당하는 전환 ID를 프로젝트 간에 복사하지 않는다.

## 사내 Orca 배정

운영자가 지정한 Orca 환경·담당과 이슈의 조건별 담당 레포를 대조한다. 기존 배정은 해당 환경의 `orca reference find <이슈 키> --json`과 `orca orchestration task-list --run <run> --full --json` 또는 대상 봇 대화에서 찾는다. 작업공간이 같다는 사실만으로 해당 담당에게 전달됐다고 판단하지 않는다.

기존 봇에 인계할 때는 대상 봇·대화를 식별해 `orca orchestration send`로 범위와 근거를 전달한다. 태스크 배정 방식이면 기존 태스크를 찾고 없을 때 생성한 뒤 지정 수신처에 `orca orchestration dispatch`한다. 응답이 끊기면 생성된 태스크와 dispatch·메시지 이력을 각각 읽어 수신처까지 전달됐는지 확인한다. 대기 중 담당자가 바뀌면 기존 대화·작업 링크와 아직 필요한 회신을 넘긴다. 정책 변경은 영향받는 기존 담당의 대화에 영향 조건과 멈출 범위만 보낸다.

## 사내 Bitbucket 병합과 정기 조회

초기 자동 병합은 요청과 계획이 병합까지 맡긴 `develop` 대상에 적용한다. 다른 대상 브랜치에는 이 규칙을 적용하지 않는다. 사람 병합 모드에서는 PR·검토한 head·네 조건의 근거를 지정된 사람에게 보내고 실제 병합은 Bitbucket에서 확인한다.

PR 원본의 대상·소스 커밋, 리뷰·차단 지적·승인과 병합 가능 여부를 조회한다. 자동 실행은 **확인한 PR 판본에 결합된** 병합 기능을 사용한다. 예를 들어 Bitbucket Data Center REST에서는 PR의 `fromRef.latestCommit`과 `version`을 함께 읽고 해당 PR의 `merge` 요청에 version을 전달한다. 충돌이면 새로 조회한다. 연결이 조회·승인만 지원하면 병합 실행 권한·경로 미확인을 반환한다. 승인을 생성해 조건을 채우지 않는다. [Bitbucket Data Center PR API](https://developer.atlassian.com/server/bitbucket/rest/v900/api-group-pull-requests/)

정기 안내 담당은 두 곳에서 후보를 찾는다. 먼저 대상 레포의 `develop` 병합 이력에서 연결 PR·이슈를 따라가 사람이 병합한 변경도 찾는다. 또 접수 때 남긴 대기 문의 위치나 대상 프로젝트 Jira의 원문 대화 링크를 따라가, 요청자가 기다린 결과와 기존 답장을 대조한다. 이 경로는 머지 시각이나 Jira 미완료 필터로 자르지 않는다. 두 경로에서 찾은 같은 원문은 한 번만 확인한다. 새 머지가 0건이어도 PR 검토·QA 배포·기능 검증을 기다리는 문의를 다시 본다.

## 배포 근거

- **사내 VDI**에서는 프로젝트 위키의 확인 경로를 따른다. 자동 조회가 불가능하면 Jira 조건의 서비스·환경·대상 변경에 연결된 확인 대화와 회신을 먼저 읽는다. 확인 요청을 맡았고 아직 요청이 없으면 PR·필요 버전·환경을 명시해 한 번 묻고 이슈 조건에서 메시지를 찾도록 연결한다. 링크 저장만 실패하면 기존 대화에서 요청을 찾아 링크만 보완한다. “배포했습니다”라는 회신도 질문·응답자·시점을 대조해 어떤 환경의 어느 버전을 확인한 것인지 특정한다.
- **GitHub Actions**를 쓰는 프로젝트는 위키나 배포 설정에서 해당 서비스의 배포 workflow·대상 environment를 찾는다. 예를 들어 `gh run view <run-id> -R <owner/repo> --json headSha,conclusion,jobs,url`로 job을 찾고, 배포 기록·job 로그에서 실제 배포된 아티팩트 버전과 대상 환경, 성공을 대조한다. 재사용 빌드나 수동 배포면 실행의 head와 아티팩트 판본이 다를 수 있다. 빌드·테스트만 통과했거나 deploy job이 생략된 실행은 배포 근거가 될 수 없다. 이후 롤백·재배포가 있으면 현재 환경의 버전을 확인한다.
- 특정 배포 환경이 조건에 없고 로컬 실연동으로 충분하면 배포 확인을 선행 조건으로 추가하지 않는다.
